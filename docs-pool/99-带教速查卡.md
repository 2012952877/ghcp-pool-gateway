# 带教速查卡

> 这份是**给辅导者自己看的**，不是给被辅导方的交付物。
> 目的是让你在现场不用翻长文档，也不会讲错关键结论。

---

## 一、开场十分钟怎么讲

按这个顺序，不要先讲实现细节：

1. **先讲问题**：一个 Copilot 账号额度有限、会被限流、挂了就全断。
2. **再讲方案**：把 N 个账号组成池，对外只暴露一个 key，内部自动分摊和切换。
3. **最后讲边界**：这套东西**不改变** GitHub 侧的授权关系，账号还是那些账号，只是调度方式变了。

一句话总结给对方：

> 「对外一个 key，对内一批账号，谁忙了自动换谁，挂了自动跳过。」

## 二、部署顺序（现场就照这个走）

| # | 阶段 | 大致耗时 | 卡点风险 |
|---|---|---|---|
| 1 | 建资源组 + VM（含 cloud-init 装 Docker） | 5 分钟 | 订阅权限不够 |
| 2 | **开 NSG：网卡层 + 子网层都要** | 3 分钟 | **最容易漏子网层** |
| 3 | 上传源码、写 `.env`、生成 SSO 自签证书 | 10 分钟 | 漏证书 → SSO CrashLoop |
| 4 | 构建镜像（首次较慢） | 15–25 分钟 | 磁盘/网络慢 |
| 5 | 启动全栈，等 8 个容器 healthy | 3 分钟 | LiteLLM 首启要等 DB 迁移 |
| 6 | Caddy 签证书、验证 HTTPS | 2 分钟 | 域名解析没生效 |
| 7 | 导入账号、建池、加成员 | 5 分钟 | 忘了先建 SSO 用户 |
| 8 | 建虚拟 key、端到端冒烟 | 3 分钟 | — |

> 第 4 步最长。可以在等构建时讲架构，别干等。

## 三、五个必须讲对的技术点

这几条对方一定会问，讲错会很尴尬。

### 1. prompt 缓存怎么生效

由**客户端**驱动，网关侧不需要配置：

> 需要带 `cache_control: {"type":"ephemeral"}`，且内容达到模型的最小可缓存长度。
> Claude Code 自带，客户直接用不需要做什么；自研应用要自己加。

命中情况在 Console 的 Request Stats 里看 `Cache input` / `Cache write` 两列。

### 2. LiteLLM 这一层负责什么

认证与配额。使用方持虚拟 key 访问，`trusted_identity_hook` 从 key 的
`metadata.trusted_user_id` 解析身份并注入下游，客户端自带的身份头会被丢弃。
每把 key 的 rpm / tpm / 预算 / 并发各自独立。

Proxy 是内部服务，只负责账号池调度，端口绑 `127.0.0.1`。
职责分离，讲的时候按这个说，别把它讲成「一道墙挡着一个洞」。

**所以 Proxy 的 3000 端口绝不能暴露公网。**

现场可以演示：拿虚拟 key 加一个伪造的 `X-User-Identity: xxx`，
结果仍然按 key 配置的池走 —— 头被丢掉了。

### 3. 三种策略怎么选

| 场景 | 选 |
|---|---|
| 多个租户/多人共用一个池 | `least-loaded`（默认） |
| 要按会话审计追溯 | `sticky-affinity` |
| 客户端用了 `/responses` 的 `previous_response_id` | `sticky-affinity`（有状态，换账号会断） |

### 4. 一个人用一个会话，加账号**不会**降低单账号 RPM

粘性策略下，一段会话固定绑一个账号。加账号只增加**总额度**和**冗余**，
不会摊薄单个会话的速率。

要摊薄必须有**多个并发会话**，或者改用 `least-loaded`。

### 5. 冷启动自动开通 vs 批量导入

- 上游原生的「冷启动自动开通」是为**一人一号**设计的
- **池化模型下账号是基础设施**，一次性批量建好即可，不需要按用户触发
- 演示环境用的是**导入已有 token**（路线 A），没有 EMU 企业也能跑

## 四、现场翻车预案

| 症状 | 八成是 | 30 秒处理 |
|---|---|---|
| 浏览器/curl 返回 000 | NSG 被订阅策略清了 | 查**子网 NSG**，补 80/443/22 |
| TCP 连上又断 | 同上，某一层规则缺失 | 两层 NSG 都查 |
| SSH 连不上但 HTTPS 通 | 只有 22 端口规则被删 | 补 22 |
| SSO 容器 CrashLoop | 缺 `/certs/idp-cert.pem` | 生成自签证书 |
| 导入账号报 `SSO user not found` | 忘了先建 SSO 用户 | 先 `POST /api/users` |
| 导入报 `csvText is required` | 传了 JSON 数组而不是 CSV | 表头必须是 `name,copilotOauthToken` |
| 调用返回 403 | 用 master key 直接推理了 | 必须用虚拟 key |
| 调用返回 401 | 没带 key 或 key 错 | 检查 `x-api-key` |
| 返回 `refusal` | 提示词被误判 | 换自然文本，别用重复模板 |

> **别改 hosts 文件。** 中国区代理软件的 Fake-IP 是必需的，
> 强制解析到真实 IP 反而连不上。打不开先查 NSG。

## 五、演示脚本（15 分钟）

```
1. 打开 Console → Account Pools
   「这就是账号池，现在有 2 个账号在池里，都是可用状态」

2. 展开池 → 指着策略下拉框
   「这里能选分配策略，默认是最少使用，负载最均匀」

3. 切到 Request Stats
   「每条请求都记了实际用的是哪个账号、属于哪个池」

4. 命令行发一个请求（用虚拟 key）
   回到 Request Stats 刷新 →「看，落到了 demo01」

5. 再发几个 →「轮流落在两个账号上，这就是分摊」

6. 回到 Account Pools，点某个成员的「移出」
   再发请求 →「现在全部落到剩下那个，池子自动收敛」

7. 把成员加回来
   「加账号是热操作，不用重启任何服务」
```

## 六、交付前自查

- [ ] 8 个容器全部 healthy
- [ ] `https://api.<host>/health/liveliness` 返回 200
- [ ] `https://console.<host>` 能登录
- [ ] Console 的 Account Pools 页能看到池和成员
- [ ] 用虚拟 key 发请求返回 200
- [ ] Request Stats 里能看到 `pool_id` 归因
- [ ] 对方**自己动手**建过一把虚拟 key
- [ ] 对方**自己动手**往池里加过/移出过成员
- [ ] `.env` 已交接，且**没有**提交到任何仓库
- [ ] 告知对方：订阅策略可能会清 NSG，给了排查顺序

## 七、别承诺的事

- ❌ 不要说「这是官方支持的用法」——`api.githubcopilot.com` 是未公开文档化的端点
- ❌ 不要替客户判断席位共享的许可问题——让他们走自己的法务
- ❌ 不要保证 token 永不过期——导入模式下 token 有有效期
- ❌ 不要说「100 个账号就能扛 100 倍并发」——取决于并发会话数，不是账号数
