# 运维与排障手册

> 适用范围：单台 Azure VM（Standard_D2s_v5 / Ubuntu 24.04）+ docker-compose 部署的 GHCP 账号池网关。
> 阅读对象：已经按《部署手册》把环境跑起来的工程师。本手册只讲**跑起来之后**的事：怎么确认它还活着、坏了怎么修、怎么加账号加 key、怎么备份和升级。
> 编写原则：所有命令可直接复制执行；每条给出期望输出和失败处置；没实测过的地方明确标注「未验证」或「需现场确认」。

## 0. 开始之前

### 0.1 你需要先具备的东西

| 前置条件 | 怎么确认 | 没有怎么办 |
|---|---|---|
| 能 SSH 进 VM 的私钥 | `ls -l <SSH_KEY>` | 找部署时保存的 `pool_vm_key`；丢了只能用 §2.3 的 `az vm run-command` 进去补公钥 |
| 本机装了 Azure CLI 且已登录 | `az account show -o table` | `az login`；多订阅时 `az account set --subscription <订阅ID或名字>` |
| 本机有 `bash` + `curl` + `jq` | `bash --version && curl --version && jq --version` | Windows 用 **Git Bash**，不要用 PowerShell（PowerShell 里 `curl` 是 `Invoke-WebRequest` 的别名，参数完全不同） |
| VM 上当前用户属于 `docker` 组 | VM 上 `id -nG \| tr ' ' '\n' \| grep -x docker` | `sudo usermod -aG docker $USER` 后**退出重新 SSH**（组变更不会在当前会话生效）；`cloud-init.yaml` 已对 `azureuser` 做过这一步 |
| VM 上有 `jq` | VM 上 `jq --version` | `sudo apt-get install -y jq`（`cloud-init.yaml` 已装） |

本手册里的命令分三类，**每条都会标注在哪跑**：

- **本地**：你自己的电脑（Git Bash / Linux shell），主要跑 `az` 和外部探活。
- **VM**：SSH 进 VM 之后。
- **PowerShell**：只在明确标注时使用（Windows 上处理私钥权限、日期计算）。

### 0.2 占位符对照表

全文占位符统一用 `<尖括号>`。取值方法：

| 占位符 | 含义 | 怎么取值 |
|---|---|---|
| `<RG>` | Azure 资源组名 | 本地：`az group list -o table` |
| `<VM>` | 虚拟机名 | 本地：`az vm list -g <RG> -o table` |
| `<NIC>` | VM 的网卡名 | 本地：`az vm show -g <RG> -n <VM> --query "networkProfile.networkInterfaces[0].id" -o tsv`，取最后一段；§3.1 的脚本会自动算 |
| `<NSG>` | 网卡上挂的 NSG 名 | 本地：`az network nic show -g <RG> -n <NIC> --query "networkSecurityGroup.id" -o tsv`，取最后一段 |
| `<VNET>` / `<SUBNET>` | 虚拟网络 / 子网名 | 本地：`az network vnet list -g <RG> -o table`；`az network vnet subnet list -g <RG> --vnet-name <VNET> -o table` |
| `<PUBLIC_IP>` | VM 公网 IP | 本地：`az network public-ip list -g <RG> --query "[].ipAddress" -o tsv` |
| `<PUBLIC_HOST>` | 对外域名，形如 `20.78.139.35.nip.io` | VM 上：`grep '^PUBLIC_HOST=' /opt/ghcp-pool/.env` |
| `<SSH_KEY>` | SSH 私钥路径 | 创建 VM 时保存的 `pool_vm_key` |
| `<SSH_USER>` | VM 登录用户 | 本环境为 `azureuser`（`cloud-init.yaml` 里写死的用户名） |
| `<POOL>` | 账号池名 | 本环境为 `team-pool`；`GET /api/pools` 可列全部 |
| `<ACCOUNT>` | 池成员账号 identity | 本环境为 `demo01` / `demo02`；`GET /api/accounts` 可列全部 |
| `<KEY>` | 客户端用的 LiteLLM 虚拟 key（`sk-…`） | `/key/generate` 返回，或 `/key/list` 查 |
| `<CANARY_KEY>` | 专供探活用的虚拟 key | 见 §6.1，建议单独建一把、预算给小 |
| `<APPID>` | Azure 活动日志里的调用方 appid | 见 §4.2 |

密钥类的值（`INTERNAL_API_TOKEN`、`API_KEY`、`SESSION_SECRET`、`LITELLM_MASTER_KEY`、`LITELLM_DB_PASSWORD`）都在 VM 的 `/opt/ghcp-pool/.env` 里。**本手册的命令一律用 shell 变量引用，不要把真值敲进命令行**（会进 `~/.bash_history`，也会被同屏的人看到）。

### 0.3 每次 SSH 上来先跑这一段

```bash
ssh -i <SSH_KEY> <SSH_USER>@<PUBLIC_IP>

cd /opt/ghcp-pool
set -a; . ./.env; set +a

# 三个 compose 文件必须一起用，少一个就少一层服务
dcp() { ( cd /opt/ghcp-pool && docker compose \
  -f docker-compose.yml \
  -f docker-compose.litellm.yml \
  -f docker-compose.caddy.yml "$@" ); }

P=http://127.0.0.1:3000                    # Proxy（内部管理口）
L=http://127.0.0.1:4000                    # LiteLLM
POOL=team-pool
INT=(-H "X-Internal-Token: ${INTERNAL_API_TOKEN}" -H "Content-Type: application/json")
MK=(-H "Authorization: Bearer ${LITELLM_MASTER_KEY}" -H "Content-Type: application/json")
```

**期望**：无任何输出即为成功。之后 `echo "$POOL"` 应打印 `team-pool`。

**失败处置**：

| 现象 | 原因 | 处理 |
|---|---|---|
| `. ./.env` 报 `No such file or directory` | 部署目录不对，或文件没改名 | 确认目录是 `/opt/ghcp-pool`；仓库里这份文件叫 **`.env.pool`**，部署到 VM 时**必须重命名为 `.env`**（`docker compose` 只自动读 `.env`） |
| `docker compose` 报 `permission denied ... docker.sock` | 当前用户不在 `docker` 组 | 见 §0.1；改完要退出重新 SSH |
| `INT=(...)` 报语法错误 | 你在 `sh`/`dash` 里，不是 `bash` | 数组是 bash 语法。执行 `bash` 切换；写成脚本时 shebang 必须是 `#!/usr/bin/env bash` |

> **这三个变量是每个新 shell 都要重新设的**（`dcp`、`P`/`L`/`POOL`、`INT`/`MK`）。断线重连、开新窗口、cron 里跑脚本，都要重跑这一段，否则后面的命令会因为变量为空而报 `internal_auth_failed` 或打到错误的地址。

> **文件位置说明**：仓库里 Caddy 相关文件放在 `deploy/`（`deploy/Caddyfile.pool`、`deploy/docker-compose.caddy.yml`），但 `docker-compose.caddy.yml` 里的挂载写的是 `./Caddyfile.pool`（相对项目目录）。**部署到 VM 时这些文件必须平铺在 `/opt/ghcp-pool/` 同一级**，否则 Caddy 起不来（会报找不到 `/etc/caddy/Caddyfile` 或把目录当文件挂载）。
> 仓库里还有一个 `docker-compose.mysql.yml`，**本部署方式不使用**，不要把它加进 `dcp`。

### 0.4 服务与端口一览

| 服务 | 容器内端口 | 宿主机绑定 | 健康检查 | 对外可达 |
|---|---|---|---|---|
| caddy | 80 / 443 | `0.0.0.0` | **compose 里没配 healthcheck**，`dcp ps` 不会显示 healthy，只能看日志 | 是，唯一入口 |
| litellm | 4000 | `127.0.0.1` | `/health/liveliness` | 经 `api.<PUBLIC_HOST>` |
| proxy | 3000 | `127.0.0.1` | `/healthz`、`/readyz` | 否，内部服务 |
| sso | 7001 | `127.0.0.1` | `/healthz` | 否，内部服务 |
| login | 7003 | `127.0.0.1` | `/healthz` | 否，内部服务 |
| console | 7004 | `127.0.0.1` | `/healthz` | 经 `console.<PUBLIC_HOST>` |
| litellm-db (PostgreSQL) | 5432 | 不发布 | `pg_isready` | 否 |
| litellm-redis | 6379 | 不发布 | `redis-cli ping` | 否 |

> **端口绑定说明**：`proxy` / `sso` / `login` / `console` / `litellm` 的宿主机映射
> 由 `.env` 的 `BIND_ADDR` 控制，**默认 `127.0.0.1`**，只有服务器本机能连。
> 容器之间走 Docker 内部网络按服务名互访，不经过这些映射。
> 网络层只需放行 **22 / 80 / 443**；无需为其他端口配置规则。

> ⚠️ **LiteLLM 的管理接口（`/key/generate`、`/key/list`、`/spend/logs` 等）经 Caddy 暴露在 `api.<PUBLIC_HOST>` 上，凭 master key 即可调用。** `LITELLM_MASTER_KEY` 泄露 = 任何人都能给自己发虚拟 key。它只能出现在你和 VM 的 `.env` 里，**不要发给任何租户**。

### 0.5 重启策略

全部 8 个服务都是 `restart: unless-stopped`，异常退出或 VM 重启后都会自动拉起。

**已实测**：主动 `reboot` 一次，VM 回来后未执行任何命令，8 个容器全部自动恢复并转为 healthy，
健康检查五项全绿，端到端推理正常。

> 注意 `depends_on` 的健康条件只在 `docker compose up` 时生效，Docker 自动重启时不检查启动顺序。
> 因此重启初期可能有几十秒里 proxy 已起但依赖尚未就绪，健康检查会短暂不过；等待即可，无需干预。

建议把这条写进变更流程。如果要自动化（**未验证，配完请手动 reboot 一次验证**）：

```bash
crontab -e
# 加一行
@reboot sleep 60 && cd /opt/ghcp-pool && docker compose -f docker-compose.yml -f docker-compose.litellm.yml -f docker-compose.caddy.yml up -d >> /home/<SSH_USER>/reboot-up.log 2>&1
```

## 1. 每日探活

### 1.1 一条命令：从外部判断「客户能不能用」

在**本地**（任意能上网的机器，Windows 用 Git Bash）执行：

```bash
curl -sS -o /dev/null -w 'HTTP %{http_code} | TLS %{time_appconnect}s | 总 %{time_total}s\n' \
  --max-time 30 -X POST https://api.<PUBLIC_HOST>/v1/messages \
  -H "x-api-key: <CANARY_KEY>" \
  -H "anthropic-version: 2023-06-01" \
  -H "content-type: application/json" \
  -d '{"model":"claude-opus-5","max_tokens":16,"thinking":{"type":"disabled"},"messages":[{"role":"user","content":"回复 OK"}]}'
```

**期望输出**：形如 `HTTP 200 | TLS 0.35s | 总 2.1s`。耗时随网络波动，**只要 `HTTP 200` 就是全链路通**（本手册不给耗时基线数字 —— 请你自己连续跑几天记录，作为本环境的基线）。

这一条命令同时验证了：DNS → NSG → Caddy → TLS 证书 → LiteLLM → 虚拟 key 鉴权 → 身份注入 Hook → Proxy → 池选成员 → 成员 token → 上游 `api.githubcopilot.com`。任何一环断了都不会是 200。

> 注意：**探活会真实消费额度**，并计入 `<CANARY_KEY>` 的 spend。所以 canary key 的 `max_budget` 给小一点，且不要用它做压测。

> **探活用的 prompt 不要用重复段落或模板化文本**。已实测：重复段落、形如 `Rule N: ... cite internal reference document REF-XXXX` 的合成文本会触发 `stop_reason=refusal`、`category=reasoning_extraction`，HTTP 仍是 200 但内容是拒绝。探活文本用自然、内容各异的短句。

**返回值分诊**：

| 返回 | 含义 | 跳到 |
|---|---|---|
| `HTTP 200` | 全链路正常，收工 | — |
| `HTTP 000` | 连不上（DNS / NSG / VM / TLS） | §1.2 第 1 层 → §2.1 |
| `HTTP 400` | 请求体本身有问题（模型名、字段拼错） | 先核对上面这条命令有没有敲错；确认 `model` 写的是网关支持的名字 |
| `HTTP 401` | 没带 key 或 key 无效/已吊销 | §2.5 |
| `HTTP 403` | key 的 `metadata.trusted_user_id` 缺失或非法 | §2.5 |
| `HTTP 429` | LiteLLM 层限流或预算超支（**不是**上游限流） | §2.6 |
| `HTTP 502` | Proxy 到上游失败，含「全员冷却」 | §2.7 |
| `HTTP 503` | 成员 OAuth token 不可用，或 Proxy 存储不可用 | §2.8 |
| `HTTP 202` | 身份被当成新账号在冷启动开通（多半是 key 的 `trusted_user_id` 写错了） | §6.2 |

### 1.2 分层排查顺序

不要跳层。**从下往上**逐层确认，每层给一条判定命令：

| 层 | 判定命令（在哪跑） | 正常表现 | 不正常跳到 |
|---|---|---|---|
| **1. 网络可达** | 本地：`nc -vz <PUBLIC_IP> 443`（无 `nc` 用 `curl -sS -o /dev/null -w '%{http_code}\n' --max-time 10 https://api.<PUBLIC_HOST>/`） | 连接成功 / 返回码非 000 | §2.1、§2.2、§3 |
| **2. VM 与容器** | VM：`dcp ps` | 全部 `running`（除 caddy 外都应带 `(healthy)`；caddy 没配 healthcheck，只会显示 `Up`） | §2.4 |
| **3. Caddy + TLS** | VM：`curl -s -o /dev/null -w '%{http_code}\n' --resolve api.<PUBLIC_HOST>:443:127.0.0.1 https://api.<PUBLIC_HOST>/health/liveliness` | `200` | §2.9 |
| **4. LiteLLM** | VM：`curl -s -o /dev/null -w '%{http_code}\n' $L/health/liveliness` | `200` | §2.4、§6.6 |
| **5. Proxy** | VM：`curl -s $P/readyz` | `{"status":"ok","service":"proxy","storage":"sqlite"}` | §2.8 |
| **6. 池与成员** | VM：见 §1.3 | `可用 N/N`，全部 `active` | §2.7、§5 |
| **7. 上游 GHCP** | 用 §1.1 的探活命令 | 200 | §2.6 |

> **最有价值的一刀切分**：第 3 层的 `--resolve` 命令。它强制走本机 loopback、但 SNI 仍是真实域名，因此**完全绕开 DNS**。
> - VM 上返回 200，本地返回 000 → **问题不在服务端**，在 NSG 或你本地的网络/VPN（见 §2.1、§2.3）。
> - VM 上也不是 200 → 问题在服务端，继续往上查。

### 1.3 VM 上的一条命令：一次看完所有层

把下面这段存成 `/opt/ghcp-pool/healthz.sh`（**本手册新增，仓库里没有这个文件**）：

```bash
cat > /opt/ghcp-pool/healthz.sh <<'SH'
#!/usr/bin/env bash
# GHCP 账号池分层探活。直接跑或交给 cron。
set -uo pipefail
cd /opt/ghcp-pool || exit 1
set -a; . ./.env; set +a
POOL="${POOL:-team-pool}"
dc() { docker compose -f docker-compose.yml -f docker-compose.litellm.yml -f docker-compose.caddy.yml "$@"; }

echo "═════ $(date -Is) ═════"
echo "── 容器 ──"
dc ps --format '{{.Service}}\t{{.State}}\t{{.Status}}' 2>/dev/null || dc ps

echo "── 健康 ──"
for s in "LiteLLM|http://127.0.0.1:4000/health/liveliness" \
         "Proxy|http://127.0.0.1:3000/readyz" \
         "Console|http://127.0.0.1:7004/healthz" \
         "SSO|http://127.0.0.1:7001/healthz" \
         "Login|http://127.0.0.1:7003/healthz" \
         "Caddy|https://api.${PUBLIC_HOST}/health/liveliness"; do
  n="${s%%|*}"; u="${s##*|}"
  printf '%-8s %s\n' "$n" \
    "$(curl -s -o /dev/null -w '%{http_code}' --max-time 5 \
        --resolve "api.${PUBLIC_HOST}:443:127.0.0.1" "$u")"
done

echo "── 池 ──"
curl -s -H "X-Internal-Token: ${INTERNAL_API_TOKEN}" \
  "http://127.0.0.1:3000/api/pools/${POOL}" \
  | jq -r '"池 \(.poolId)  策略 \(.strategy)  可用 \(.activeMembers)/\(.totalMembers)",
           (.members[] | "  \(.identity)  \(.state)  可用=\(.available)  失败\(.consecutiveFailures)  冷却至\(.coolingUntil // "-")  上次用\(.lastUsedAt // "-")")'
SH
chmod +x /opt/ghcp-pool/healthz.sh
/opt/ghcp-pool/healthz.sh
```

**期望输出**：

```
litellm-db      running   Up 3 days (healthy)
litellm-redis   running   Up 3 days (healthy)
login           running   Up 3 days (healthy)
proxy           running   Up 3 days (healthy)
sso             running   Up 3 days (healthy)
── 健康 ──
LiteLLM  200
Proxy    200
Console  200
SSO      200
Login    200
Caddy    200
── 池 ──
池 team-pool  策略 least-loaded  可用 2/2
  demo01  active  可用=true  失败0  冷却至-  上次用2026-09-08T01:22:31.000Z
  demo02  active  可用=true  失败0  冷却至-  上次用2026-09-08T01:24:07.000Z
```

（上面的时间戳和 `Up 3 days` 只是格式示例，不是基线值。）

**失败时**：

| 现象 | 原因 | 处理 |
|---|---|---|
| `docker compose ps --format` 报模板错误 | Compose 版本较老 | 脚本已加 `\|\| dc ps` 兜底，看表格即可 |
| `jq: command not found` | jq 没装 | `sudo apt-get install -y jq`；临时可用 `python3 -m json.tool` 看原始 JSON |
| 池那段返回 `{"error":{"code":"pool_not_found"}}` | 池名不是 `team-pool` | VM 上 `curl -s "${INT[@]}" $P/api/pools \| jq -r '.items[].poolId'` 看实际池名，然后 `POOL=<真名> /opt/ghcp-pool/healthz.sh` |
| 池那段返回 `internal_auth_failed` | `INTERNAL_API_TOKEN` 没加载 | 确认 `.env` 存在且脚本里的 `. ./.env` 生效 |
| `caddy` 那行显示 `Up`，没有 `(healthy)` | **正常** | caddy 在 compose 里没配 healthcheck |

### 1.4 建议的定时任务

日志文件要先建好并授权（`/var/log` 是 root 的，普通用户 cron 直接重定向会 `Permission denied`）：

```bash
sudo touch /var/log/ghcp-healthz.log
sudo chown "$USER":"$USER" /var/log/ghcp-healthz.log

crontab -e
# 加一行（避开整点，减少和其他定时任务撞车）
7 * * * * /opt/ghcp-pool/healthz.sh >> /var/log/ghcp-healthz.log 2>&1
```

**验证**：等到下一个 `:07`，`tail -30 /var/log/ghcp-healthz.log` 应看到一段完整输出。
**失败**：日志为空 → `grep CRON /var/log/syslog | tail` 看 cron 有没有执行；报 `docker: not found` → 在 crontab 顶部加 `PATH=/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin`。

日志轮转（**未验证，常规做法**）：

```bash
sudo tee /etc/logrotate.d/ghcp-healthz >/dev/null <<'EOF'
/var/log/ghcp-healthz.log {
    daily
    rotate 7
    missingok
    notifempty
    copytruncate
}
EOF
sudo logrotate -d /etc/logrotate.d/ghcp-healthz   # -d 是演练，不真的轮转
```

## 2. 故障速查表

### 2.0 主表

| # | 症状 | 最可能原因 | 一条诊断命令 | 修复动作 |
|---|---|---|---|---|
| 1 | HTTPS 打不开 / `curl` 返回 **000** | 两层 NSG 之一被订阅策略清空，或新挂了零规则子网 NSG | §3.1 的体检脚本 | §3 恢复 NSG |
| 2 | 同上，但 NSG 正常 | VM 被停机 | `az vm get-instance-view -g <RG> -n <VM> --query "instanceView.statuses[?starts_with(code,'PowerState')].code" -o tsv` | `az vm start -g <RG> -n <VM>`，起来后 `dcp up -d` |
| 3 | 同上，但 VM 和 NSG 都正常 | 本地 VPN 的 Fake-IP DNS | VM 上 §1.2 第 3 层命令返回 200 | §2.3，用 `deploy/pool-bridge.mjs`，**不要改 hosts** |
| 4 | TCP 能连上但立刻断开 | 证书没签发成功 / 容器在重启 / VPN 隧道半开 | `openssl s_client -connect <PUBLIC_IP>:443 -servername api.<PUBLIC_HOST> </dev/null 2>&1 \| head -25` | §2.2 |
| 5 | SSH 连不上 | NSG 22 端口规则没了 / VM 停了 / 私钥权限 | `az vm run-command invoke -g <RG> -n <VM> --command-id RunShellScript --scripts "uptime"` | §2.3 |
| 6 | 容器反复重启 / 起不来 | SSO 缺 SAML 证书；磁盘满；必填环境变量缺失 | `dcp ps` + `dcp logs --tail 100 <服务名>` | §2.4 |
| 7 | 请求 **401** | 没带虚拟 key，或 key 已吊销/过期 | 看响应 message | §2.5 |
| 8 | 请求 **403** | 虚拟 key 的 `metadata.trusted_user_id` 缺失或非法 | `curl -s "$L/key/info?key=<KEY>" "${MK[@]}" \| jq '.info.metadata'` | §6.2 |
| 9 | 请求 **429** | **LiteLLM 层**限流或预算超支（上游限流不会是 429） | `dcp logs --since 10m litellm \| grep -i -E 'rate.?limit\|budget'` | §2.6 |
| 10 | 请求 **502**，message 含 `are cooling down` | 池里所有成员都在冷却 | §2.7 的池状态命令 | §2.7 |
| 11 | 请求 **503**，code `oauth_not_ready` | 成员账号的 Copilot OAuth token 失效 | `curl -s "${INT[@]}" "$P/api/accounts?pageSize=100" \| jq -r '.items[]\|"\(.identity) \(.copilotOauthStatus)"'` | §5.2 重新导入 token |
| 12 | 请求 **202**，code `account_initializing` | 虚拟 key 的 `trusted_user_id` 指向了不存在的池/账号 | 同 #8 | §6.2 |
| 13 | 浏览器提示证书错误 | Let's Encrypt / ZeroSSL 签发失败 | `dcp logs caddy \| grep -i -E 'certificate\|challenge\|acme'` | §2.9 |
| 14 | 返回 200 但内容是拒绝，`stop_reason=refusal` | Anthropic 误判合成文本 | 看响应体的 `stop_reason` 与 `category` | 换成内容各异的自然文本，见 §2.10 |
| 15 | 所有推理突然全失败，LiteLLM 日志报 DB | PostgreSQL 挂了 | `dcp ps litellm-db` | §6.6（这是**有意的** fail-closed 设计） |

### 2.1 HTTPS 打不开 / curl 返回 000

`000` 表示 curl 连 TCP 都没建起来（或超时），**不是应用层问题**。按这个顺序查，一层都别跳。以下命令都在**本地**跑。

```bash
# ① 网卡 NSG + 子网 NSG 合并后的「有效规则」—— 一条命令看两层
RG=<RG>; VM=<VM>
NICID=$(az vm show -g "$RG" -n "$VM" --query "networkProfile.networkInterfaces[0].id" -o tsv)
NIC="${NICID##*/}"
az network nic list-effective-nsg -g "$RG" -n "$NIC" -o json \
  | jq -r '.value[] | "NSG: \(.networkSecurityGroup.id | split("/") | last)",
           (.effectiveSecurityRules[]
            | select(.direction=="Inbound" and .access=="Allow")
            | "  \(.name)  端口=\(.destinationPortRange)  源=\(.sourceAddressPrefix)  目标=\(.destinationAddressPrefix)")'
```

**期望输出**：至少出现放行 22、80、443 的 Allow 规则（名字里带 `defaultSecurityRules/` 的是 Azure 默认规则，不算数）。如果 VNet 子网上挂了 NSG，这里会列出**两个** NSG 段落。

**失败处置**：

| 现象 | 含义 | 处理 |
|---|---|---|
| 只列出一个 NSG，而你记得原本有两层 | 子网 NSG 被换掉或解绑 | 跳 §3 |
| 报 `The VM is not running` 或 `NetworkInterface ... not found` | VM 停机 / NIC 在别的资源组 | 见下面 ②；NIC 跨 RG 时把 `-g` 换成 NIC 所在的资源组 |
| 报 `AuthorizationFailed` | 当前账号没有网络读权限 | `az account show` 确认订阅选对了；权限不足找订阅管理员 |

```bash
# ② VM 电源
az vm get-instance-view -g <RG> -n <VM> \
  --query "instanceView.statuses[?starts_with(code,'PowerState')].code" -o tsv
```
**期望**：`PowerState/running`。若是 `PowerState/stopped` 或 `PowerState/deallocated` → `az vm start -g <RG> -n <VM>`，起来后**必须**再 `dcp up -d`（§0.5）。

```bash
# ③ 子网 NSG（最容易漏的一层）
RG=<RG>
VNET=$(az network vnet list -g "$RG" --query "[0].name" -o tsv)
SUBNET=$(az network vnet subnet list -g "$RG" --vnet-name "$VNET" --query "[0].name" -o tsv)
echo "VNET=$VNET SUBNET=$SUBNET"
az network vnet subnet show -g "$RG" --vnet-name "$VNET" -n "$SUBNET" \
  --query "networkSecurityGroup.id" -o tsv
```
> 上面用 `[0]` 取第一个 VNet / 第一个子网。如果资源组里有多个，请先 `az network vnet list -g <RG> -o table` 确认 VM 实际所在的那个，再手工赋值。

**期望**：空（没挂子网 NSG）或你自己建的那个 NSG 名。
**如果返回一个你没建过的 NSG** → 这就是订阅策略的第三种破坏，跳 §3.3。

**排查顺序必须是：网卡 NSG → 子网 NSG → VM 电源 → 数据库状态。** 子网 NSG 这层最容易漏，因为网卡 NSG 看上去完全正常。

> **仅 AKS 部署相关**：AKS 的 LoadBalancer 开启了 `enableFloatingIP`（DSR），包到达节点时目标 IP 仍是公网 IP，NSG 规则的 `destination` **必须写公网 IP**，写子网网段不生效。**单 VM 部署不适用这一条**，写法见 §3.2 的说明。

### 2.2 TCP 能连上但立刻断开

先分清是「握手前断」还是「握手后断」（本地跑）：

```bash
openssl s_client -connect <PUBLIC_IP>:443 -servername api.<PUBLIC_HOST> </dev/null 2>&1 | head -25
```

| 输出特征 | 含义 | 处理 |
|---|---|---|

### 2.3 SSH 连不上

分三种，判据完全不同：

| 判据 | 结论 | 修复 |
|---|---|---|
| `az vm run-command invoke` **能**执行成功 | VM 活着，是**网络路径**问题（NSG 22 端口 / 本地 VPN） | 见下面 A |
| `az vm run-command invoke` 也超时/报错 | VM 停了或 Agent 异常 | 见下面 B |
| 报 `Permissions ... are too open` 或 `Permission denied (publickey)` | 私钥问题，跟服务端无关 | 见下面 C |

**A. 网络路径问题 —— 先用 run-command 进去，这条路不走 NSG**

```bash
az vm run-command invoke -g <RG> -n <VM> --command-id RunShellScript \
  --scripts "cd /opt/ghcp-pool && docker compose -f docker-compose.yml -f docker-compose.litellm.yml -f docker-compose.caddy.yml ps"
```
**期望**：返回 JSON，`value[0].message` 里是容器列表。
这条命令走 Azure Agent 通道，**NSG 规则被全清也能用**，是 NSG 事故时的救命通道。注意它以 **root** 身份执行，且**单次调用有超时限制**，别拿它跑长任务。
确认 VM 正常后，补 22 端口规则（§3）。

**B. VM 侧问题**

```bash
az vm get-instance-view -g <RG> -n <VM> --query "instanceView.statuses[].code" -o tsv
az vm boot-diagnostics get-boot-log -g <RG> -n <VM> | tail -50
```
停机就 `az vm start -g <RG> -n <VM>`。
**失败**：`get-boot-log` 报没开启启动诊断 → `az vm boot-diagnostics enable -g <RG> -n <VM>` 后重试（需重启才有内容，**未验证**）。

**C. 私钥问题（Windows 常见）**

```powershell
# PowerShell，不是 bash
icacls <SSH_KEY> /inheritance:r /grant:r "$env:USERNAME`:R"
```
（Git Bash / Linux 下是 `chmod 600 <SSH_KEY>`。）

主机指纹变了（重建过 VM）：
```bash

```

**关于 VPN 的 Fake-IP DNS**：中国区常见代理软件会把域名解析成假 IP（如 `6.6.4.243`）。实测结论是 **Fake-IP 是必需的**（流量要走隧道），强制解析到真实 IP 反而连不上。
所以：**不要改 hosts 文件**。浏览器打不开时，先按 §2.1 确认是不是 NSG 被清了。

需要用浏览器访问 Console 时，在**本地**运行仓库里的桥接（仅调试用）：

```bash
node deploy/pool-bridge.mjs
```

**期望输出**：

⚠️ **`pool-bridge.mjs` 里的 `REAL_IP` 是写死的常量**（第 14 行左右，`const REAL_IP = '20.78.139.35';`），换 IP 或换环境后必须改这一行，否则会连到旧机器。它同时用这个 IP 拼出 `console.<IP>.nip.io` / `api.<IP>.nip.io`，所以**只适用于 nip.io 域名**；用客户自有域名时需要改 `ROUTES` 里的 `host`。
⚠️ 桥接对上游用了 `rejectUnauthorized: false`（不校验证书），只用于本地调试，**不要拿它当生产客户端的通道**。

### 2.4 容器反复重启 / 起不来

> `CrashLoopBackOff` 是 Kubernetes 的说法。本环境是 docker-compose，等价现象是 `dcp ps` 里 State 显示 `restarting` 或 `exited`。（若你维护的是旧 AKS 环境，对应 `kubectl get pod -n <ns>` 里的 CrashLoopBackOff，日志用 `kubectl logs --previous`。）

```bash
dcp ps
dcp logs --tail 120 <服务名>       # sso / login / proxy / console / litellm / caddy / litellm-db / litellm-redis
dcp logs --since 30m <服务名> | grep -i -E 'error|fatal|ENOENT|EACCES'
```

| 日志特征 | 原因 | 修复 |
|---|---|---|
| `ENOENT ... /certs/idp-cert.pem` 或 `idp-key.pem` | **SSO 缺 SAML 证书**（最常见） | 见下面「自签证书」 |
| `docker compose up` 时直接报 `set INTERNAL_API_TOKEN` / `set PUBLIC_HOST` 之类 | 必填环境变量缺失，容器**根本没创建**（不是 CrashLoop） | 补 `.env` 后 `dcp up -d`；变量名就是报错里的那个 |
| `no space left on device` | 磁盘满 | 见下面「磁盘满」 |
| proxy 显示 `exited`、日志停在几分钟前 | `restart: on-failure:5` 已用尽重启次数 | 先解决根因，再 `dcp up -d proxy` |
| proxy 一直 `created` / 不启动 | 它 `depends_on` sso、login 的 **healthy** 条件 | 先修 sso / login，proxy 会跟着起来 |
| litellm 反复 `unhealthy` 后重启 | PostgreSQL 或 Redis 没就绪 | `dcp ps litellm-db litellm-redis`，先修依赖 |
| litellm 刚起来是 `starting` | 正常，它的 `start_period` 是 60 秒 | 等 1～2 分钟再判断 |
| caddy 日志刷 `challenge failed` | 证书签发失败 | §2.9 |

**自签 SAML 证书**（导入 token 模式下自签即可，不需要真企业证书）：

```bash
sudo mkdir -p /opt/ghcp-pool/certs
sudo chown "$USER":"$USER" /opt/ghcp-pool/certs
openssl req -x509 -newkey rsa:2048 -nodes -days 3650 \
  -keyout /opt/ghcp-pool/certs/idp-key.pem \
  -out    /opt/ghcp-pool/certs/idp-cert.pem \
  -subj "/CN=ghcp-pool-idp"
chmod 600 /opt/ghcp-pool/certs/idp-key.pem
dcp up -d sso
sleep 20 && dcp ps sso && dcp logs --tail 30 sso
```
**期望**：`dcp ps sso` 变成 `running (healthy)`。
**为什么要先 `sudo mkdir` + `chown`**：如果 `./certs` 不存在，Docker 会以 root 身份自动创建这个目录，之后普通用户往里写文件会 `Permission denied`。
**文件名不能改**：SSO 容器固定读 `/certs/idp-cert.pem` 和 `/certs/idp-key.pem`（挂载来源由 `.env` 的 `SSO_CERT_DIR` 决定，默认 `./certs`，只读挂载）。

**磁盘满**：

```bash
df -h /
docker system df
sudo journalctl --vacuum-time=3d
docker system prune -f          # 清停止的容器、悬空镜像、构建缓存
```
> ⚠️ **绝对不要执行 `docker system prune --volumes` 或 `docker volume prune`。**
> `proxy-data` 卷里是全部账号的 Copilot OAuth token，`litellm-db-data` 卷里是全部虚拟 key。删了只能重新导入 token、重发所有客户端 key。
> `docker system prune -f`（不带 `--volumes`）不会动命名卷，是安全的；但它会删掉 §9.3 打的 `rollback-*` 标签所指向的镜像吗？—— 不会，有标签的镜像不算悬空。

### 2.5 401 / 403

这两个码在本系统里含义非常明确，**看 message 就能定位**（下表的 code / message 均来自源码）：

| 状态 | message / code | 来自哪一层 | 原因 | 修复 |
|---|---|---|---|---|
| 401 | `Inference requires a LiteLLM virtual key.` | LiteLLM 的 `trusted_identity_hook` | 用了 master key 或非虚拟 key 直接推理 | 换成 `/key/generate` 出来的 `sk-…` |
| 401 | LiteLLM 标准的 key 无效提示 | LiteLLM 鉴权 | key 不存在 / 已吊销 / 已过期 | §6.1 重发 key |
| 401 | `{"code":"missing_api_key","message":"Missing API key. Use Authorization: Bearer or x-api-key."}` | **Proxy** 的 `requireApiKey` | 说明请求**绕过了 LiteLLM 直连 Proxy** | 检查客户端 base_url 是否误配成了 3000 端口 |
| 401 | `{"code":"invalid_api_key"}` | Proxy | 用了错误的 `API_KEY` 直连 Proxy | 同上 |
| 401 | `{"code":"internal_auth_failed","message":"Invalid internal service token."}` | Proxy 的 `/api/*` | `X-Internal-Token` 不对 | 回 §0.3 重新加载 `.env` |
| 403 | `Virtual key is missing trusted identity metadata.` | Hook | key 建的时候没写 `metadata.trusted_user_id` | §6.2 补上，或重建 key |
| 403 | `Virtual key trusted identity metadata is invalid.` | Hook | `trusted_user_id` 不满足 `^[A-Za-z0-9][A-Za-z0-9._:@-]{0,127}$` | 改成合法的池名/账号名 |
| 400 | `{"code":"missing_identity_header","message":"Missing required identity header \"X-User-Identity\"."}` | Proxy 的 `requireIdentityHeader` | 直连 Proxy 且没带 `X-User-Identity` | 同上，客户端应走 LiteLLM |

诊断命令（VM 上）：

```bash
curl -s "$L/key/info?key=<KEY>" "${MK[@]}" \
  | jq '{alias:.info.key_alias, metadata:.info.metadata, spend:.info.spend, budget:.info.max_budget, expires:.info.expires, blocked:.info.blocked}'
```
**期望**：`metadata` 里有 `{"trusted_user_id":"team-pool"}`。
**失败**：返回 404 / `key not found` → key 已被删除或写错。
**注意**：`/key/info` 的返回结构随 LiteLLM 版本会变（**本环境未实测该接口**）。若上面的 jq 全是 `null`，先 `curl -s "$L/key/info?key=<KEY>" "${MK[@]}" | jq .` 看完整结构再改路径。

> **Hook 的行为已实测确认**：无 key → 401；用 master key 直接推理 → 403（hook 强制要求虚拟 key）；带伪造的 `X-User-Identity` 头 → **头被剥掉**，仍按 key 元数据走池分配、返回 200。
> 也就是说：**看到 403「missing trusted identity」不要去查客户端，一定是 key 本身建错了。**

### 2.6 429

**关键判据（源码依据：`src/proxy/src/routes/compatible.ts` 的 `proxyErrorStatus`）**：Proxy 只把上游的 **401 / 403** 原样透传，**其余错误（含上游 429 / 402）一律转成 502**。
所以：**客户端看到 429，基本可以断定来自 LiteLLM 层，不是 GitHub Copilot 上游限流。**

| 429 来源 | 判断依据 | 修复 |
|---|---|---|
| per-key `rpm_limit` / `tpm_limit` / `max_parallel_requests` | LiteLLM 日志含 rate limit；Proxy 日志里**没有**对应请求记录 | §6.3 提限额，或让客户端降并发 |
| per-key 预算超支（`max_budget`） | message 里含 `budget`；`/key/info` 的 `spend` ≥ `max_budget` | §6.3 提预算或等 `budget_duration` 滚动（本环境建 key 时给的是 30d） |
| 上游 GHCP 限流 | 客户端收到的是 **502**，同时该成员在池里变成 `cooling` | §2.7 / §7 扩池 |

```bash
# 分别看两层
dcp logs --since 15m litellm | grep -i -E 'rate.?limit|budget|429'
dcp logs --since 15m proxy   | grep -i -E 'member-selected|429|402'
```

**上游 429 / 402 的处理逻辑（已实测）**：上游返回 429 或 402 时，该成员**立即冷却**（不必攒够 `failureThreshold` 次失败）；其余错误累计到 `failureThreshold`（默认 3）才冷却；冷却期（默认 300 秒）满后自动恢复。

> ⚠️ **单次请求不会自动换成员重试。** 源码里 `resolvePoolMember` 有 `exclude` 参数（`src/proxy/src/pool/poolResolver.ts`），但请求路径（`src/proxy/src/routes/compatible.ts`）没有传它，所以故障转移发生在**下一次请求**：当次请求失败（502），该成员已被冷却，客户端重试时会自然落到别的成员。
> 运维含义：**客户端必须自己带重试**。让客户端对 502 做 1～2 次指数退避重试，用户几乎无感；不重试则会看到偶发失败。

### 2.7 池里所有成员都在冷却

**症状**：请求返回 **502**，响应体形如
`{"type":"error","error":{"type":"api_error","message":"All members of pool \"team-pool\" are cooling down."}}`。

> Proxy 侧的状态码是 502（源码确认：`PoolAllCoolingError` 不是 `CopilotApiError` 的 401/403，走默认分支返回 502）。**经 LiteLLM 转发后客户端最终看到的状态码需现场确认**，但 message 会透传，以 message 和 Proxy 日志为准。

**诊断**（VM 上）：

```bash
curl -s "${INT[@]}" "$P/api/pools/$POOL" | jq -r '
  "策略 \(.strategy)  冷却时长 \(.cooldownSeconds)s  失败阈值 \(.failureThreshold)  可用 \(.activeMembers)/\(.totalMembers)",
  (.members[] | "  \(.identity)  state=\(.state)  失败=\(.consecutiveFailures)  冷却至=\(.coolingUntil // "-")  可用=\(.available)")'

dcp logs --since 1h proxy | grep -E 'PoolAllCoolingError|cooling down|member-selected' | tail -30
```

**处理顺序**：

| 情况 | 判断 | 动作 |
|---|---|---|
| 只是一时的上游限流 | `coolingUntil` 都在几分钟内 | 等冷却自动恢复（默认 300 秒），同时通知客户端重试 |
| 某个成员 token 失效被反复判失败 | 该成员 `copilotOauthStatus` ≠ `valid` | §5.2 重新导入 token，然后 §5.4 手动解冷却 |
| 确实容量不够 | 一天内多次全员冷却 | §7 扩池（加账号 + 加成员） |
| 误判需要立刻恢复服务 | 已确认上游其实可用 | §5.4 手动解冷却 |
| 池是空的 | message 是 `Pool "<POOL>" has no usable members.` | 成员被删光或全被 `disabled` 了，§5.3 重新加成员 |

**临时加长冷却容忍度**（治标不治本，改完立刻生效，无需重启）：

```bash
curl -s -X PATCH "$P/api/pools/$POOL" "${INT[@]}" \
  -d '{"cooldownSeconds":120,"failureThreshold":5}' | jq '{poolId,cooldownSeconds,failureThreshold}'
```
**期望**：返回更新后的池详情（含 `poolId` / `cooldownSeconds` / `failureThreshold`）。
**失败**：404 `pool_not_found` → 池名写错；400 `pool_strategy_invalid` → 你顺手改了 `strategy` 且值非法。
**注意**：这两个字段只接受**正整数**，传 0 或负数会被静默忽略（源码里 `readPositiveInt` 对非正整数返回 `undefined`，即「不修改」），所以「改了没生效」时先回读一次确认。
**注意**：`cooldownSeconds` 调太小会让已被上游限流的账号被反复打，反而拉长恢复时间。默认 300 秒是按 Copilot 侧常见限流窗口定的（源码注释里就是这么说的），没有充分理由不要动。

### 2.8 503

| code / 现象 | 来源 | 诊断 | 修复 |
|---|---|---|---|
| `{"code":"oauth_not_ready"}` | 选中的成员账号 `copilotOauthStatus` 不是 `valid` | `curl -s "${INT[@]}" "$P/api/accounts?pageSize=100" \| jq -r '.items[]\|"\(.identity) \(.copilotOauthStatus)"'` | §5.2 重新导入 token |
| `/readyz` 返回 `{"status":"unavailable","service":"proxy"}` | Proxy 存储不可用 | `dcp logs proxy \| grep readiness-failed` | 查 `proxy-data` 卷、`df -h`、卷是否被误删 |
| `{"code":"error_diagnostics_disabled"}` | 错误诊断功能被关 | 只影响 `/api/error-diagnostics`，不影响推理 | `.env` 设 `PROXY_ERROR_DIAGNOSTICS_ENABLED=true` 后 `dcp up -d proxy`（compose 里的默认值就是 `true`，出现这个码说明 `.env` 里显式设成了 false） |
| Caddy 返回 502/503 的 HTML 页 | 上游容器没起来 | `dcp ps` | `dcp up -d` |

`copilotOauthStatus` 的取值与含义（源码里的完整枚举：`valid` / `expired` / `missing` / `refreshing` / `failed`）：

| 值 | 含义 | 该做什么 |
|---|---|---|
| `valid` | 正常 | — |
| `expired` | token 过期 | §5.2 重新导入 |
| `missing` | 从未设置过 token | §5.2 导入 |
| `refreshing` | 正在重新授权（此时请求返回 202） | 等；卡太久看 login 容器日志 |
| `failed` | 授权失败 | 看 login 容器日志；导入模式下直接 §5.2 重导 |

### 2.9 证书签发失败

```bash
dcp logs caddy | grep -i -E 'obtain|certificate|challenge|acme|rate' | tail -40
```

| 日志特征 | 原因 | 修复 |
|---|---|---|
| `challenge failed` / `timeout during connect` | **80 端口没放行**（HTTP-01 校验走 80） | §3 补 80 端口规则，**网卡 NSG 和子网 NSG 两层都要** |
| `no such host` / DNS 解析失败 | 域名没解析到本机 | nip.io 域名把 IP 编码在名字里，**换公网 IP 后必须改 `.env` 的 `PUBLIC_HOST`** 并 `dcp up -d caddy` |
| `too many certificates` / `rateLimited` | Let's Encrypt 频率限制 | 见下面 |
| 反复重试但没有明确错误 | LE 失败后 Caddy 会自动尝试 ZeroSSL | 观察几分钟；仍失败按上面几条排查 |

**频率限制的处理**：Let's Encrypt 对同一组域名有签发频率上限。调试期间先切到 staging，调通再切回。

`Caddyfile.pool` 里**已经有一个全局块**（当前内容是 `{ email admin@example.com }`）。Caddy **不允许出现两个全局块**，所以要把 `acme_ca` 加进已有的那个块里，而不是再写一个：

```
{
	email admin@example.com
	acme_ca https://acme-staging-v02.api.letsencrypt.org/directory
}
```

然后 `dcp restart caddy`。
**期望**：`dcp logs --tail 40 caddy` 里出现指向 `acme-staging-v02` 的签发记录。
**失败**：容器起不来并报 `unrecognized global option` 或 `duplicate global options` → 你写成了两个全局块，合并成一个。
staging 证书浏览器会报不受信任，这是正常的，只用来验证签发流程能不能走通。调通后**删掉 `acme_ca` 那行**再 `dcp restart caddy`。

**关于 email**：仓库里的 `Caddyfile.pool` 用的是占位邮箱 `admin@example.com`，本环境用它**签发成功过**。但收不到证书到期/吊销通知，建议改成真实邮箱，改完 `dcp restart caddy`。

**不要手动删 `caddy-data` 卷来"强制重签"** —— 会丢掉全部已签发证书和 ACME 账户，重签直接撞频率限制。先 `dcp restart caddy`。

### 2.10 返回 200 但内容是拒绝

**症状**：HTTP 200，响应体里 `stop_reason` 为 `refusal`，`category` 为 `reasoning_extraction`。

**原因（已实测）**：Anthropic 会误判某些合成文本。触发过的模式：
- 大量重复段落
- 形如 `Rule N: ... cite internal reference document REF-XXXX` 的模板化文本

**处理**：这不是系统故障，不用改配置。写测试用例、压测脚本、探活 prompt 时**用内容各异的自然文本**。如果是客户的真实业务 prompt 被误判，收集样本单独反馈，不要在网关侧做任何绕过。

## 3. 订阅策略破坏后的恢复

**这是本环境最高频的事故来源。** Azure 订阅上挂着的治理策略会周期性地破坏环境，且**不打招呼**。已实测被破坏过三种方式。

### 3.0 三种破坏的识别特征对照

| 破坏方式 | 典型症状 | 识别命令 | 识别特征 |
|---|---|---|---|
| **(a) 清空资源组下全部 NSG 的自定义规则** | 所有端口不通，SSH 也连不上，`curl` 000 | `az network nsg rule list -g <RG> --nsg-name <NSG> -o table` | **返回空表**（只剩 Azure 默认规则，默认规则不在这个命令的输出里） |
| **(b) 停止 AKS 集群与 MySQL/PostgreSQL 实例（本环境体现为停 VM）** | `curl` 000；门户显示 Stopped | `az vm get-instance-view -g <RG> -n <VM> --query "instanceView.statuses[?starts_with(code,'PowerState')].code" -o tsv` | `PowerState/stopped` 或 `/deallocated` |
| **(c) 新建一个子网 NSG 挂到 VNet 上，里面零规则** | **最阴险**：网卡 NSG 规则完好、VM running、容器全 healthy，但依然 000 | `az network vnet subnet show -g <RG> --vnet-name <VNET> -n <SUBNET> --query networkSecurityGroup.id -o tsv` | 返回一个**你没建过**的 NSG 名 |

> **(c) 是最容易漏的一层**：你会看到网卡 NSG 一条规则不少，VM 在跑，容器全 healthy，然后百思不得其解。
> 记住排查顺序：**网卡 NSG → 子网 NSG → VM 电源 → 数据库状态**。

### 3.1 一条命令做全面体检

本地跑。**注意 `--query` 里不要用中文键名** —— JMESPath 的标识符只允许 `[A-Za-z_][A-Za-z0-9_]*`，写中文会直接解析报错。

```bash
RG=<RG>; VM=<VM>

echo "── VM 电源 ──"
az vm get-instance-view -g "$RG" -n "$VM" \
  --query "instanceView.statuses[?starts_with(code,'PowerState')].code" -o tsv

echo "── 网卡 NSG ──"
NICID=$(az vm show -g "$RG" -n "$VM" --query "networkProfile.networkInterfaces[0].id" -o tsv)
NIC="${NICID##*/}"
NICNSG=$(az network nic show -g "$RG" -n "$NIC" --query "networkSecurityGroup.id" -o tsv)
echo "  NIC=$NIC  NSG=${NICNSG:-（无）}"
if [ -n "$NICNSG" ]; then
  az network nsg rule list -g "$RG" --nsg-name "${NICNSG##*/}" \
    --query "[].{Name:name,Priority:priority,Direction:direction,Access:access,Port:destinationPortRange,Dest:destinationAddressPrefix}" -o table
fi

echo "── 子网 NSG（最容易漏）──"
VNET=$(az network vnet list -g "$RG" --query "[0].name" -o tsv)
SUBNET=$(az network vnet subnet list -g "$RG" --vnet-name "$VNET" --query "[0].name" -o tsv)
SUBNSG=$(az network vnet subnet show -g "$RG" --vnet-name "$VNET" -n "$SUBNET" --query "networkSecurityGroup.id" -o tsv)
echo "  VNET=$VNET  SUBNET=$SUBNET  NSG=${SUBNSG:-（无，正常）}"
if [ -n "$SUBNSG" ]; then
  az network nsg rule list -g "$RG" --nsg-name "${SUBNSG##*/}" \
    --query "[].{Name:name,Priority:priority,Port:destinationPortRange}" -o table
fi

echo "── 两层合并后的有效入站放行 ──"
az network nic list-effective-nsg -g "$RG" -n "$NIC" -o json \
  | jq -r '.value[] | "NSG: \(.networkSecurityGroup.id|split("/")|last)",
           (.effectiveSecurityRules[]
            | select(.direction=="Inbound" and .access=="Allow" and (.name|startswith("defaultSecurityRules/")|not))
            | "  \(.name)  端口=\(.destinationPortRange)  目标=\(.destinationAddressPrefix)")'
```

**期望**：`PowerState/running`；两层合并后能看到 22 / 80 / 443 的 Allow 规则。
**失败**：
- `list-effective-nsg` 需要 VM 处于 running 且网卡已附加；VM 停机时会报错 —— 先启动 VM 再跑这一段。
- `az network vnet list` 返回多个 VNet → 上面的 `[0]` 取错了，手工把 `VNET=`、`SUBNET=` 换成 VM 实际所在的那个（`az network nic show -g "$RG" -n "$NIC" --query "ipConfigurations[0].subnet.id" -o tsv` 能直接给出子网的完整 ID）。

### 3.2 恢复 (a)：NSG 自定义规则被清空

```bash
RG=<RG>; NSG=<网卡NSG名>

# SSH
az network nsg rule create -g "$RG" --nsg-name "$NSG" -n allow-ssh \
  --priority 100 --direction Inbound --access Allow --protocol Tcp \
  --source-address-prefixes '*' --destination-address-prefixes '*' \
  --destination-port-ranges 22

# HTTP（ACME 校验必需）+ HTTPS
az network nsg rule create -g "$RG" --nsg-name "$NSG" -n allow-web \
  --priority 110 --direction Inbound --access Allow --protocol Tcp \
  --source-address-prefixes '*' --destination-address-prefixes '*' \
  --destination-port-ranges 80 443
```

**期望**：每条返回该规则的 JSON，`provisioningState` 为 `Succeeded`。
**失败**：
- `RuleConflict` / 优先级重复 → 换个 `--priority`（100～4096，越小越优先）。
- 报规则已存在 → 把 `rule create` 换成 `rule update`，参数相同。
- `AuthorizationFailed` → 当前账号没有网络写权限，找订阅管理员。

> **关于 `--destination-address-prefixes` 写什么**
> - **单 VM 部署（本环境）：写 `'*'`。** 入站流量在到达 NSG 之前已经完成 DNAT，NSG 看到的目标地址是**网卡的私网 IP**，不是公网 IP。所以这里写公网 IP 很可能匹配不上、规则形同虚设。写 `'*'` 是已知可用的写法；想更严格可以写网卡的私网 IP（`az network nic show -g <RG> -n <NIC> --query "ipConfigurations[0].privateIPAddress" -o tsv`）。**「单 VM 写公网 IP 是否匹配」本环境未实测，不要靠猜。**
> - **AKS 部署（旧环境）：必须写公网 IP。** 因为 LoadBalancer 开了 `enableFloatingIP`（DSR），包到达节点时目标 IP 仍是公网 IP，写子网网段不生效。**这条经验不要照搬到单 VM。**

> **只放行 22 / 80 / 443。** 不要用 `--destination-port-ranges '*'` 或 `0-65535`：
> 服务需要的对外端口就这三个，放开多余端口没有收益。
> 内部服务已绑定 `127.0.0.1`，即便规则写宽也不会暴露，但仍建议保持最小放行。

规则补完立刻验证（本地）：

```bash
curl -sS -o /dev/null -w '%{http_code}\n' --max-time 15 https://api.<PUBLIC_HOST>/health/liveliness
```
**期望**：`200`。仍是 `000` → 继续查 §3.3 的子网 NSG。

### 3.3 恢复 (c)：新建的零规则子网 NSG

**这是最容易漏的一层。** 网卡 NSG 完好、VM 正常，但子网上挂了一个策略新建的、里面一条自定义规则都没有的 NSG —— Azure 默认规则会拒绝所有 Internet 入站，于是全线不通。

**两个选择**：

```bash
RG=<RG>; VNET=<VNET>; SUBNET=<SUBNET>

# 方案一（推荐）：把这个 NSG 从子网解绑，只保留网卡 NSG 一层
az network vnet subnet update -g "$RG" --vnet-name "$VNET" -n "$SUBNET" \
  --remove networkSecurityGroup
```

```bash
# 方案二：保留子网 NSG，但把 22/80/443 补进去
#（当策略只判断「有没有挂 NSG」时，用这个更稳 —— 解绑了它下次还会给你挂回来）
SUBNSGID=$(az network vnet subnet show -g "$RG" --vnet-name "$VNET" -n "$SUBNET" \
  --query networkSecurityGroup.id -o tsv)
SUBNSG="${SUBNSGID##*/}"
az network nsg rule create -g "$RG" --nsg-name "$SUBNSG" -n allow-ssh \
  --priority 100 --direction Inbound --access Allow --protocol Tcp \
  --source-address-prefixes '*' --destination-address-prefixes '*' --destination-port-ranges 22
az network nsg rule create -g "$RG" --nsg-name "$SUBNSG" -n allow-web \
  --priority 110 --direction Inbound --access Allow --protocol Tcp \
  --source-address-prefixes '*' --destination-address-prefixes '*' --destination-port-ranges 80 443
```

**期望**：方案一返回更新后的 subnet JSON，`networkSecurityGroup` 字段变为 `null` 或消失；方案二返回两条规则的 JSON。
**失败**：`--remove networkSecurityGroup` 报参数错误 → 换 `az network vnet subnet update -g "$RG" --vnet-name "$VNET" -n "$SUBNET" --network-security-group ""`。
**验证**：重跑 §3.1 的「两层合并」段，确认放行规则齐全，再跑 §1.1 探活。

> **两层 NSG 都要放行**：网卡 NSG 和子网 NSG 是**独立的两层**，入站流量必须两层都 Allow 才能通，缺一不可。只修一层是最常见的"修了但没修好"。

### 3.4 恢复 (b)：VM / 集群 / 数据库被停

```bash
# 本环境（单 VM）
az vm start -g <RG> -n <VM>

# 容器会自动恢复（全部服务均为 restart: unless-stopped），等约 1 分钟后确认即可
ssh -i <SSH_KEY> <SSH_USER>@<PUBLIC_IP> \
  'cd /opt/ghcp-pool && bash scripts/validate-health.sh'
```
**期望**：`az vm start` 返回后 `PowerState/running`；SSH 那条命令输出各容器 `Started` / `Running`。
**失败**：SSH 连不上（NSG 也被清了）→ 用 §2.3 的 `az vm run-command invoke` 执行同样的 `docker compose ... up -d`。

如果你维护的是**旧的 AKS + 托管数据库环境**，对应命令是：

```bash
az aks start -g <RG> -n <AKS名>
az postgres flexible-server start -g <RG> -n <PG实例名>
az mysql flexible-server start -g <RG> -n <MySQL实例名>
```
（单 VM 部署不涉及这三条；列出来是给还有旧环境的人参考。）

### 3.5 打标签能挡住什么、挡不住什么

给资源打标签**有帮助**：

```bash
RG=<RG>
az resource list -g "$RG" --query "[].id" -o tsv | while read -r id; do
  az resource tag --ids "$id" --tags CostControl=Ignore SecurityControl=Ignore -o none \
    || echo "打标签失败: $id"
done
```
**为什么逐个打而不是一条命令批量打**：批量执行会被 ARM 限流。

| 破坏方式 | 标签是否有效 |
|---|---|
| (a) 清空 NSG 自定义规则 | 有帮助 |
| (b) 停 VM / 集群 / 数据库 | 有帮助 |
| (c) 新建零规则子网 NSG | **挡不住** —— 新建的资源天生没有标签 |

**所以标签不能替代巡检**，(c) 只能靠 §3.1 的体检发现。

> ⚠️ **批量打标签会被 ARM 限流，报错但实际可能已经生效。** 所以打完标签**不要看返回码，要复查真实状态**：
> ```bash
> az resource list -g <RG> --query "[].{Name:name,Type:type,Tags:tags}" -o json \
>   | jq -r '.[] | "\(.Name)\t\(.Tags // {} | tostring)"'
> ```
> **期望**：每个资源后面都能看到 `CostControl` 和 `SecurityControl`。
> 失败的资源单独重打，**不要整批重跑**（会再次触发限流）。

### 3.6 事故后的标准收尾清单

1. §3.1 体检，确认两层 NSG 都齐
2. §1.3 VM 上分层探活，确认容器全 running（VM 被停过的话别忘了 `dcp up -d`）
3. §1.1 端到端探活，确认 200
4. 确认成员没被误冷却（断网期间的失败会累计到 `consecutiveFailures`）：
   ```bash
   curl -s "${INT[@]}" "$P/api/pools/$POOL" | jq '{activeMembers,totalMembers,members:[.members[]|{identity,state,consecutiveFailures}]}'
   ```
   有 `cooling` 的就 §5.4 手动解冷却
5. §4 查是谁改的，并把结论发给订阅管理员

## 4. 从活动日志查出是谁改的

Azure 活动日志保留 **90 天**，NSG / VM / 子网的每一次写操作都会留痕，包括**是谁（哪个服务主体）**发起的。

> **通用提醒**：`--query` 里的键名必须是 ASCII（JMESPath 不接受中文标识符）。下面所有命令已按此写好。

### 4.1 列出最近 7 天的相关变更

**bash（Linux / Git Bash）**：

```bash
az monitor activity-log list \
  --resource-group <RG> \
  --start-time "$(date -u -d '7 days ago' +%Y-%m-%dT%H:%M:%SZ)" \
  --query "[?contains(operationName.value,'networkSecurityGroups') || contains(operationName.value,'virtualMachines') || contains(operationName.value,'subnets') || contains(operationName.value,'virtualNetworks')].{Time:eventTimestamp, Op:operationName.value, Status:status.value, Caller:caller, AppId:claims.appid}" \
  -o table
```

**PowerShell**（`date -u -d` 在 PowerShell 里不存在）：

```powershell
$start = (Get-Date).ToUniversalTime().AddDays(-7).ToString("yyyy-MM-ddTHH:mm:ssZ")
az monitor activity-log list --resource-group <RG> --start-time $start --query "[?contains(operationName.value,'networkSecurityGroups')].{Time:eventTimestamp,Op:operationName.value,Caller:caller,AppId:claims.appid}" -o table
```

> **Windows 上的两个坑**：
> - PowerShell 内联 JSON **要用单引号**包整体，双引号加 `\"` 转义**会被吃掉**，导致 az / curl 收到残缺 JSON，报 `Expecting value`。
> - 编辑脚本注意 **CRLF**：带 CRLF 的 `.sh` 传到 Linux 会报 `$'\r': command not found`。传之前用 `dos2unix`，或在 Git 里配 `core.autocrlf=input`。

**期望输出**：按时间排列的表格，`Op` 列形如 `Microsoft.Network/networkSecurityGroups/securityRules/delete`。
**输出为空**：可能是 (1) 时间窗太短，把 7 改成 30；(2) 变更发生在**别的资源组**（比如子网 NSG 建在了另一个 RG）—— 去掉 `--resource-group`，改用 `--offset 7d` 全订阅查。

### 4.2 提取 caller appid

`caller` 字段有时是人的 UPN，有时是一串 GUID（服务主体的 object id）。真正能定位到"哪个自动化"的是 `claims.appid`：

```bash
# 谁改得最多
az monitor activity-log list -g <RG> --start-time "$(date -u -d '30 days ago' +%Y-%m-%dT%H:%M:%SZ)" \
  --query "[?contains(operationName.value,'networkSecurityGroups')].claims.appid" -o tsv \
  | sort | uniq -c | sort -rn
```

**期望输出**（GUID 是示例格式，不是真实值）：

```
     37 xxxxxxxx-xxxx-xxxx-xxxx-xxxxxxxxxxxx
      4 yyyyyyyy-yyyy-yyyy-yyyy-yyyyyyyyyyyy
```

把 appid 翻译成人能看懂的名字：

```bash
az ad sp show --id <APPID> --query "{Name:displayName, AppId:appId, Type:servicePrincipalType, Publisher:publisherName}" -o json
```

**期望**：返回该服务主体的 `displayName`，比如某个治理自动化的名字。
**失败**：
- `Resource ... does not exist` → 该 SP 不在当前租户可见范围，或你的账号没有目录读权限。把 appid 原样交给订阅管理员查。
- `Insufficient privileges` / `Authorization_RequestDenied` → 同上。

看某一次变更的完整上下文（含 `claims` 全字段）：

```bash
az monitor activity-log list -g <RG> --start-time "$(date -u -d '2 days ago' +%Y-%m-%dT%H:%M:%SZ)" \
  --query "[?contains(operationName.value,'networkSecurityGroups')] | [0]" -o json \
  | jq '{time:.eventTimestamp, op:.operationName.value, resource:.resourceId, caller:.caller, claims:.claims}'
```

`claims` 里常见的有用字段：`appid`（应用注册 ID）、`http://schemas.microsoft.com/identity/claims/objectidentifier`（对象 ID）、`ipaddr`。
JMESPath 里带斜杠的键名要整体加双引号，例如：`claims."http://schemas.microsoft.com/identity/claims/objectidentifier"`。

### 4.3 追到策略本身（可选）

```bash
az policy assignment list --disable-scope-strict-match -o table
```
**期望**：列出作用在本订阅/管理组上的策略分配。
**返回空**：说明策略挂在**管理组层级**、当前账号看不到 —— 这不是错误，把 §4.2 拿到的 appid 交给订阅管理员即可。
（`az policy state list` 也可能有用，但**本环境未实测**，用之前先在非生产订阅上试。）

### 4.4 拿到结论后怎么说

给订阅管理员的信息要凑齐这四样，否则很难推进：

| 要素 | 从哪来 |
|---|---|
| 变更时间戳（UTC） | §4.1 的 `Time` 列 |
| 具体操作 | §4.1 的 `Op` 列（如 `.../securityRules/delete`） |
| 调用方 appid + displayName | §4.2 |
| 业务影响 | 用你自己的探活日志（§1.4）说明服务中断了多久 |

同时说明：**已打 `CostControl=Ignore` / `SecurityControl=Ignore` 标签仍被破坏**（第三种方式对新建资源无效），请求把该资源组加入策略豁免范围。

## 5. 账号运维

### 5.1 查看账号状态

```bash
curl -s "${INT[@]}" "$P/api/accounts?pageSize=100" \
  | jq -r '.items[] | "\(.identity)\t\(.copilotOauthStatus)\t\(.ghLogin // "-")\t\(.copilotOauthUpdatedAt // "-")"' \
  | column -t
```

**期望**：每个账号一行，第二列全是 `valid`。状态值含义见 §2.8 的表。

> ⚠️ **`/api/accounts` 是分页的，默认只返回 25 条，最大 100 条**（源码里 `pageSize` 被夹在 1～100）。账号超过 100 个时要翻页：`?pageSize=100&page=2`。响应里的 `total` 字段是总数，用它判断有没有翻完。

### 5.2 token 过期怎么办（导入模式）

本环境用「导入已有 Copilot OAuth token」的方式接入账号，**不走 SAML/SCIM 自动开通**。token 失效就是重新导入一次。

```bash
# ① 准备 CSV —— 表头必须精确为 name,copilotOauthToken
umask 077
cat > /tmp/tokens.csv <<'CSV'
name,copilotOauthToken
demo01,<新的OAuth token>
demo02,<新的OAuth token>
CSV

# ② 转成接口要的 JSON（jq -Rs 负责把整个文件塞进一个 JSON 字符串，转义交给它）
jq -Rs '{csvText: .}' /tmp/tokens.csv > /tmp/import.json

# ③ 导入（两个头都要带 —— 实测这样可用）
curl -s -X POST "$P/api/accounts/copilot-oauth-token/import" \
  -H "X-Internal-Token: ${INTERNAL_API_TOKEN}" \
  -H "x-api-key: ${API_KEY}" \
  -H "Content-Type: application/json" \
  -d @/tmp/import.json | jq '{summary, rows}'

# ④ 用完立刻删掉明文 token
shred -u /tmp/tokens.csv /tmp/import.json 2>/dev/null || rm -f /tmp/tokens.csv /tmp/import.json
```

**期望输出**：`summary` 为 `{"total":2,"success":2,"failed":0}`，`rows` 里每行 `status` 为 `success`。

> 导入过程会**逐个拿 token 去上游校验**，所以每行都可能因为 token 本身的问题失败；失败原因写在该行的 **`detail`** 字段里（不是 `message`）。

**失败处置**：

| 现象 | 原因 | 处理 |
|---|---|---|
| 整体 400 `{"code":"invalid_import","message":"csvText is required."}` | JSON 里没有 `csvText` 字段 | 检查第 ② 步是否执行成功（`cat /tmp/import.json` 应看到 `{"csvText":"name,copilotOauthToken\n..."}`） |
| 某行 `detail` 含 `SSO user "<名字>" was not found. Create it manually in SSO Users before importing this token.` | **账号导入接口要求 SSO 用户先存在** | 先在 SSO（Console 的用户页面，或 `console.<PUBLIC_HOST>`）里建对应用户，再重导 |
| 某行 `detail` 含 `Copilot OAuth token validation failed: token is invalid or expired.` | token 本身无效/过期（上游 401） | 重新拿 token |
| 某行 `detail` 含 `... account has no Copilot access or is blocked by organization policy.` | 上游 403 | 该账号的 Copilot 订阅有问题，不是网关的问题 |
| 某行 `detail` 含 `CSV header must be exactly: name,copilotOauthToken` | 表头写错（如 `name,token`） | 改表头重导；**表头不对时整个 CSV 都不会被导入** |
| 某行 `detail` 含 `Duplicate name` | CSV 里有重名（**判重是不区分大小写的**） | 去重后重导 |
| 导入成功但 `/api/accounts` 里查不到你写的名字 | **用户名会被转成小写** | 用小写名去查；后续加池成员也要用小写名 |
| 401 `internal_auth_failed` | `X-Internal-Token` 不对 | 回 §0.3 |
| 400 `copilot_oauth_import_failed` | 整体处理异常 | 看 `message` 里的原文，同时 `dcp logs --since 5m proxy \| grep import-copilot-oauth` |

**导入后必做**：

```bash
# 确认 valid
curl -s "${INT[@]}" "$P/api/accounts?pageSize=100" | jq -r '.items[]|"\(.identity) \(.copilotOauthStatus)"'
# 解除因失效攒下的冷却（对每个刚修好的成员都做一次）
curl -s -X POST "$P/api/pools/$POOL/members/<ACCOUNT>/resume" "${INT[@]}" | jq '{activeMembers,totalMembers}'
```

### 5.3 加 / 移除 / 停用池成员

```bash
# 加成员（weight 可选，默认 1）
curl -s -X POST "$P/api/pools/$POOL/members" "${INT[@]}" \
  -d '{"identity":"<ACCOUNT>","weight":1}' | jq '{identity,state,weight,accountStatus}'
```
**期望**：HTTP 201，返回形如 `{"identity":"demo03","state":"active","weight":1,"accountStatus":"valid"}`。
**失败**：

| 返回 | 原因 | 处理 |
|---|---|---|
| 404 `account_not_found` | 该账号还没导入 | 先做 §5.2。**成员必须是已存在的账号** |
| 404 `pool_not_found` | 池名写错 | `curl -s "${INT[@]}" $P/api/pools \| jq -r '.items[].poolId'` |
| 400 `identity_required` | body 里没有 `identity` | 补上 |
| 400 `member_cannot_be_pool` | 成员名和池名相同 | 换名字 |

> ⚠️ **`POST .../members` 是「整条覆盖写」，不是「局部更新」。**（源码是一条 `INSERT ... ON CONFLICT DO UPDATE SET weight = excluded.weight, state = excluded.state`。）
> 后果，两个都很容易踩：
> - 只传 `weight`，`state` 会被**重置成 `active`** —— 一个正在冷却或被你手动 `disabled` 的成员会被悄悄拉回服务。
> - 只传 `state`，`weight` 会被**重置成默认值 1** —— 你之前调的权重没了。
>
> **所以每次改成员都要把 `identity` / `weight` / `state` 三个字段一起写全**：
> ```bash
> # 调权重（同时显式保住 state）
> curl -s -X POST "$P/api/pools/$POOL/members" "${INT[@]}" \
>   -d '{"identity":"<ACCOUNT>","weight":8,"state":"active"}' | jq '{identity,weight,state}'
>
> # 停用但保留（同时显式保住 weight）
> curl -s -X POST "$P/api/pools/$POOL/members" "${INT[@]}" \
>   -d '{"identity":"<ACCOUNT>","weight":1,"state":"disabled"}' | jq '{identity,weight,state}'
> ```
> 改之前先 `curl -s "${INT[@]}" "$P/api/pools/$POOL/members" | jq '.items'` 把当前值抄下来。

```bash
# 彻底移除
curl -s -X DELETE "$P/api/pools/$POOL/members/<ACCOUNT>" "${INT[@]}" | jq .
```
**期望**：`{"removed":true,"poolId":"team-pool","identity":"demo03"}`。
**失败**：404 `member_not_found` → 名字写错或已经删过。
**副作用**：删成员会**连带删掉该成员在 `proxy_session_affinity` 里的会话绑定**（源码里是一个事务）。这是想要的行为。

**权重的实际效果（已实测）**：三成员权重设为 8:1:1 时，实际分配为 **80.4% / 9.4% / 10.2%**。权重按 Rendezvous（HRW）哈希生效，不需要重启。

**增删成员的影响面（已实测）**：HRW 哈希保证 **移除 1 个账号只重映射 1.0% 的会话，且不波及无关会话**。所以扩缩容可以在线做，不需要停服务、不需要迁移会话。

> ⚠️ **删账号之前一定先把它从池里移除。** `proxy_pool_members` 和 `proxy_accounts` 之间是**逻辑关联、没有外键**（源码注释里写明了）。先删账号会在池里留下一个指向不存在账号的成员，被选中时请求会 503 `oauth_not_ready`。
> 正确顺序：`DELETE /api/pools/<POOL>/members/<ACCOUNT>` → `DELETE /api/accounts/<ACCOUNT>`（后者会连带删掉该账号的请求统计）。

### 5.4 手动解除冷却

```bash
curl -s -X POST "$P/api/pools/$POOL/members/<ACCOUNT>/resume" "${INT[@]}" \
  | jq '{poolId, activeMembers, totalMembers, members:[.members[]|{identity,state,coolingUntil,consecutiveFailures}]}'
```

**期望**：该成员 `state` 变 `active`，`coolingUntil` 变 `null`，`consecutiveFailures` 归 0（这个接口内部会做一次 `markMemberSuccess`，三样一起清）。
**失败**：404 `member_not_found` → 名字写错，或该账号根本不在这个池里（`curl -s "${INT[@]}" "$P/api/pools/$POOL/members" | jq -r '.items[].identity'` 确认）。
**副作用**：这个接口也走 `addPoolMember`，所以**该成员的 weight 会被重置为默认值 1**。之前调过权重的成员，resume 之后要按 §5.3 重新设一次权重。

**什么时候该手动解冷却**：
- token 刚重新导入完（§5.2）
- 确认过上游其实已恢复，不想等满 300 秒
- 网络故障（如 NSG 事故）期间攒下的失败计数，事故恢复后清零

**什么时候不该**：上游确实在限流时反复解冷却，只会让该账号被继续打、限流窗口继续延长。老老实实等，或者 §7 扩池。

### 5.5 清理过期会话绑定

只有 `sticky-affinity` 策略才会写会话绑定表；`least-loaded`（本环境默认）和 `round-robin` 每次重新分配，不写绑定。

```bash
curl -s -X POST "$P/api/pools/maintenance/prune-sessions" "${INT[@]}" | jq .
```
**期望**：`{"removed":0}`（least-loaded 下常年为 0，这是正常的）或被删除的过期行数。
用 sticky-affinity 的池建议每周跑一次；不跑也只是 `proxy_session_affinity` 表变大，不影响正确性（过期绑定在选择时会被忽略）。
**注意**：这个接口是**全局**的，会清理所有池的过期绑定，不针对单个池。

### 5.6 会话 key 是怎么定的（排障时会用到）

同一个「会话」始终落到同一个账号。会话 key 的推导优先级（源码 `src/proxy/src/pool/sessionKey.ts`）：

| 优先级 | 来源 | 说明 |
|---|---|---|
| 1 | `X-Session-Id` 请求头 | 客户端主动控制，排障时最好用 |
| 2 | 请求体 `metadata.user_id` | Claude Code 会传 |
| 3 | `system` + 首条 user message 前 **4096 字节**的 sha256 | 兜底，不需要客户端配合 |
| 4 | 固定兜底值 | 无 body 的请求（如 `/v1/models`）用它，避免无谓打散 |

排障技巧：想**验证「同 sessionKey 必同账号」**（已实测成立），带上 `-H "X-Session-Id: probe-001"` 反复发几次，然后看：

```bash
dcp logs --since 10m proxy | grep member-selected | tail -10
```
**期望**：这几条日志里的 `identity` 一致。
**注意**：本环境默认策略是 `least-loaded`，它**忽略会话亲和**、每次挑最久未使用的成员 —— 所以在默认策略下同一个 `X-Session-Id` **不会**固定到同一账号。「同 sessionKey 必同账号」这条性质是选择算法（HRW）本身的性质，要在 `sticky-affinity` 策略下才能在线上观察到。

## 6. 虚拟 key 运维

**虚拟 key 是多租户隔离的认证边界。** 一租户一把 `sk-xxx`，key 的 `metadata.trusted_user_id` 决定身份，客户端改不了（伪造的 `X-User-Identity` 头会被 hook 剥掉 —— 已实测）。

所有管理调用用 master key，可以在 VM 上直接打 `$L`（`http://127.0.0.1:4000`），也可以从外部打 `https://api.<PUBLIC_HOST>`。**优先在 VM 上打**，避免 master key 在公网链路上出现得太频繁。

> **实测覆盖情况**：`/key/generate`、`/key/list`、`/spend/logs`、`/health/liveliness` 在本环境**已实测**。`/key/update`、`/key/delete`、`/key/info` 是 LiteLLM 官方接口，语义按官方文档给出，**本环境未逐一实测** —— 首次使用请先拿一把测试 key 走一遍，确认行为符合预期再对生产 key 操作。

### 6.1 新建虚拟 key

```bash
curl -s -X POST "$L/key/generate" "${MK[@]}" -d '{
  "key_alias": "<租户名>-20260908",
  "models": [],
  "metadata": {"trusted_user_id": "team-pool"},
  "rpm_limit": 60,
  "tpm_limit": 200000,
  "max_parallel_requests": 5,
  "max_budget": 50,
  "budget_duration": "30d",
  "duration": "30d"
}' | jq '{key, key_alias, max_budget, budget_duration, rpm_limit, tpm_limit, expires}'
```

**期望**：返回 `key` 字段（`sk-…`）。**这是唯一一次能看到完整 key 的机会，立刻交给租户并记录 alias**。
**失败**：
- 报 alias 已存在 → 换一个 `key_alias`（建议用 `<租户>-<日期>`）。
- 报超出上限 → 见下面的护栏表。

**参数说明**：

| 字段 | 说明 | 建议 |
|---|---|---|
| `key_alias` | 唯一标识，用来查消费和吊销 | 用 `<租户>-<日期>`，重复会报错 |
| `metadata.trusted_user_id` | **决定身份**，写池名或单账号 identity | 池名如 `team-pool` |
| `models` | 允许的模型，`[]` 表示不限制 | 一般给 `[]` |
| `rpm_limit` / `tpm_limit` | 每分钟请求数 / token 数 | 按租户规模给 |
| `max_parallel_requests` | 并发上限 | Claude Code 会并发，别给太小 |
| `max_budget` / `budget_duration` | 预算与滚动周期 | 试用租户给小额度 |
| `duration` | key 有效期 | 到期自动失效，比人工吊销可靠 |

**护栏**（来自 `litellm/config.yaml` 的 `general_settings.upperbound_key_generate_params`）：建 key 时超过这些上限会被拒绝。

| 参数 | 上限 |
|---|---|
| `duration` | 90d |
| `max_budget` | 500 |
| `budget_duration` | 30d |
| `max_parallel_requests` | 20 |
| `rpm_limit` | 600 |
| `tpm_limit` | 1000000 |

要突破护栏，得改 `litellm/config.yaml` 并**重建 litellm 镜像**（`config.yaml` 是 `COPY` 进镜像的，见 §9.2）。

> ⚠️ **`trusted_user_id` 写错不会在建 key 时报错。** hook 只校验字符集（`^[A-Za-z0-9][A-Za-z0-9._:@-]{0,127}$`），**不校验这个池/账号是否存在**。写成一个不存在的名字，第一次推理才会暴露 —— 而且表现很迷惑：Proxy 会把它当成**新 identity 去冷启动开通**，返回 **202 `account_initializing`**，并且**会在 SSO 侧发起建同名用户的流程**。
> 所以：**建完 key 立刻用它发一次真实请求验证**（下一节），别等租户来报障。

### 6.2 建完立刻验证

```bash
NEWKEY=<刚拿到的key>
curl -s -o /dev/null -w '%{http_code}\n' -X POST "https://api.<PUBLIC_HOST>/v1/messages" \
  -H "x-api-key: $NEWKEY" -H "anthropic-version: 2023-06-01" -H "content-type: application/json" \
  -d '{"model":"claude-opus-5","max_tokens":16,"thinking":{"type":"disabled"},"messages":[{"role":"user","content":"回复 OK"}]}'
```
**期望**：`200`。

| 返回 | 原因 | 处理 |
|---|---|---|
| `202` | `trusted_user_id` 指向了不存在的池/账号 | 立刻按下面「修正身份」改掉；然后检查 SSO 里有没有被误建的同名用户，有就删掉 |
| `403` | `metadata` 没写进去，或 `trusted_user_id` 字符非法 | 同上 |
| `401` | key 没生成成功，或你复制少了字符 | 重新取 key |

**修正身份**：

```bash
curl -s -X POST "$L/key/update" "${MK[@]}" \
  -d '{"key":"<KEY>","metadata":{"trusted_user_id":"team-pool"}}' | jq '{key_alias, metadata}'
```
**期望**：返回的 `metadata` 里是新值；再跑一次上面的验证应得 200。
（`/key/update` **未在本环境实测**；不放心就 `/key/delete` 后重建一把新 key —— 反正 key 还没发给租户。）

### 6.3 改限额 / 改预算

```bash
curl -s -X POST "$L/key/update" "${MK[@]}" -d '{
  "key": "<KEY>",
  "rpm_limit": 120,
  "tpm_limit": 400000,
  "max_budget": 100
}' | jq '{key_alias, rpm_limit, tpm_limit, max_budget}'
```
**期望**：返回更新后的字段。
**注意**：`/key/update` 是否也受 §6.1 的建 key 护栏约束，**本环境未实测** —— 改完务必用 `/key/info` 回读确认，并让租户重试一次。

### 6.4 吊销 key

```bash
# 按 key 值删
curl -s -X POST "$L/key/delete" "${MK[@]}" -d '{"keys":["<KEY>"]}' | jq .
# 按 alias 删（不知道 key 值时）
curl -s -X POST "$L/key/delete" "${MK[@]}" -d '{"key_aliases":["<租户名>-20260908"]}' | jq .
```
**期望**：返回删除结果。**删完立刻用该 key 发一次 §6.2 的请求，应当 401** —— 这一步别省，是唯一能确认真的删掉了的方法。

**key 泄露的应急顺序**：
1. **先删 key**（上面的命令），止血优先
2. 查这把 key 的历史消费：
   ```bash
   curl -s "$L/spend/logs?limit=1" "${MK[@]}" | jq '.[0]'     # 先看一条样本，确认字段名
   curl -s "$L/spend/logs?limit=200" "${MK[@]}" | jq '[.[] | select(.api_key=="<按样本里的实际字段与值填>")] | length'
   ```
   （LiteLLM 通常存的是 key 的哈希而不是明文，具体字段名随版本变化，所以必须先看样本。）
3. 查 Proxy 侧被谁承接：
   ```bash
   curl -s "${INT[@]}" "$P/api/request-stats?limit=1000" \
     | jq -r '.[] | select(.poolId=="team-pool") | "\(.requestedAt) \(.identity) \(.model) \(.inputTokens)"' | tail -50
   ```
   注意这是滚动窗口，只有最近的记录（见 §7.3）。
4. 给该租户重发新 key

### 6.5 查消费

```bash
# 所有 key 的当前消费与预算
curl -s "$L/key/list?return_full_object=true&size=100" "${MK[@]}" \
  | jq -r '.keys[] | "\(.key_alias // "-")\t消费=$\(.spend // 0)\t预算=$\(.max_budget // "-")\trpm=\(.rpm_limit // "-")\t到期=\(.expires // "-")"' \
  | column -t

# 最近的调用明细
curl -s "$L/spend/logs?limit=50" "${MK[@]}" | jq -r '.[] | "\(.startTime // .created_at) \(.model) \(.spend)"' | tail -20
```
**期望**：每把 key 一行，`消费` 随使用增长。
**失败**：字段名随 LiteLLM 版本会变；先 `curl -s "$L/spend/logs?limit=1" "${MK[@]}" | jq '.[0]'` 看一条完整样本，再按实际字段名写 jq。key 很多时把 `size=100` 调大或翻页。

### 6.6 LiteLLM 的 PostgreSQL 是硬依赖

`litellm/config.yaml` 里 `general_settings.allow_requests_on_db_unavailable: false` —— **PostgreSQL 挂了，所有推理直接失败**。这是**有意的 fail-closed 设计**：数据库不可用时无法校验 key 和记账，宁可拒绝服务也不能放行未鉴权的请求。

```bash
dcp ps litellm-db
dcp logs --tail 50 litellm-db
dcp exec -T litellm-db pg_isready -U litellm -d litellm
```
**期望**：`/var/run/postgresql:5432 - accepting connections`。
**修复**：`dcp up -d litellm-db`，等它 healthy 后 `dcp restart litellm`。数据损坏则走 §8.3 恢复。

## 7. 容量与成本

### 7.1 缓存生效的前提

缓存由**客户端**驱动，网关侧不需要配置：

- 客户端要显式声明 `cache_control: {"type":"ephemeral"}`
- 被缓存的内容需达到模型的最小可缓存长度
- **Claude Code 自带该字段**，用 Claude Code 的租户不用做任何事

命中情况在 Console 的 Request Stats 里看 `Cache input` / `Cache write` 两列。

### 7.2 三种策略什么时候用

| 策略 | 何时用 | 代价 |
|---|---|---|
| `least-loaded`（**本环境默认**） | 多租户共用一个池、追求负载均匀 | 无 |
| `sticky-affinity` | ① 需要按会话审计追溯到具体账号；② 客户端用了 `/responses` 的 `previous_response_id` 这类**有状态**接口 | 负载可能不均；需定期 §5.5 清理绑定表 |
| `round-robin` | 按会话哈希分配 | 一般没有理由优先选它 |

> `POOL_DEFAULTS.strategy` 在源码里是 `least-loaded`，这就是建池时不指定 `strategy` 会得到的值。`poolTypes.ts` 里注释把 `sticky-affinity` 写成「默认」是**过时注释**，以 `POOL_DEFAULTS` 和 `GET /api/pools/<POOL>` 的实际返回为准。

切换策略（立刻生效，无需重启）：

```bash
curl -s -X PATCH "$P/api/pools/$POOL" "${INT[@]}" -d '{"strategy":"sticky-affinity"}' | jq '{poolId,strategy}'
```
**合法值**：`sticky-affinity` / `least-loaded` / `round-robin`。
**期望**：返回的 `strategy` 是你写的那个。
**失败**：400 `pool_strategy_invalid`（值拼错）；404 `pool_not_found`（池名错）。

### 7.3 看每个账号的用量

```bash
curl -s "${INT[@]}" "$P/api/request-stats?limit=1000" | jq -r '
  group_by(.identity)[]
  | "\(.[0].identity)\t次数=\(length)\t入=\(map(.inputTokens // 0)|add)\t出=\(map(.outputTokens // 0)|add)\t缓存读=\(map(.cacheInputTokens // 0)|add)\t缓存写=\(map(.cacheWriteTokens // 0)|add)\t失败=\(map(select(.success|not))|length)"' \
  | column -t
```

> 这个接口返回的是**裸数组**（不是 `{items:[...]}`），所以 jq 直接 `group_by` 就行；别照搬 `/api/accounts` 的 `.items[]` 写法。

**期望输出**（数字是格式示例，不是基线）：

```
demo01  次数=187  入=412330  出=18220  缓存读=298110  缓存写=41200  失败=1
demo02  次数=191  入=407880  出=17940  缓存读=301440  缓存写=39880  失败=0
```

**统计归因规则**：`identity` 记的是**实际成员账号**，`pool_id` 记的是对外池名（已实测：LiteLLM 虚拟 key → 注入 `team-pool` → 池分配 → demo01/demo02 轮流承接，`proxy_request_stats` 中 `identity` 为实际账号、`pool_id` 为 `team-pool`）。

> ⚠️ **这不是账本，是滚动窗口。**
> `proxy_request_stats` 对**每个 identity** 只保留最近 `REQUEST_STATS_PER_ACCOUNT_LIMIT` 条（本环境 `.env` 里设的是 **200**；compose 里的默认值是 **2**），超出的在写入时就被删掉。
> - 看**实时分布是否均匀** → 用上面的命令，够用。
> - 看**长期计费/账单** → 用 LiteLLM 的 `/spend/logs`（存在 PostgreSQL 里，不滚动，见 §6.5）。
> 需要更长的 Proxy 侧历史，可以调大 `.env` 的 `REQUEST_STATS_PER_ACCOUNT_LIMIT` 后 `dcp up -d proxy`（会增加 SQLite 体积，注意磁盘）。
> **注意**：因为窗口是「每账号 N 条」，`limit=1000` 拉到的其实最多是 `账号数 × 200` 条；不要拿这里的「次数」当总调用量。

### 7.4 什么时候该扩池

| 信号 | 怎么看 | 阈值参考 | 结论 |
|---|---|---|---|
| 成员频繁进冷却 | 定时抓 `/api/pools/<POOL>`，统计 `state=cooling` 出现次数 | 一天出现 ≥ 3 次 | 容量偏紧，准备扩 |
| 出现「全员冷却」 | Proxy 日志 `grep 'cooling down'` | **出现一次就算容量事故** | 立刻扩 |
| 失败率 | §7.3 的 `失败` 列 ÷ `次数` | > 1% 需关注，> 5% 必须处理 | 先确认是上游限流还是 token 失效 |
| 负载不均 | §7.3 各成员 `次数` 的离散程度 | `least-loaded` 下应接近均匀 | 偏差大 → 有成员长期在冷却，先查 §5.1 状态 |
| 客户端反馈延迟变高 | §1.1 探活的 `总` 耗时 | 相比你自己记录的基线明显变长 | 可能是上游排队，扩池能缓解 |

> 上面的阈值是**建议起点，不是实测值**。跑一两周后按本环境的实际情况调。

**分布的正常基线（已实测，来自 `tests/selector-check.cjs`）**：10000 会话 / 100 账号，**变异系数 10.4%**。也就是说各账号承接量在均值上下 10% 左右浮动是**正常**的，不用调优。

**扩池操作**（在线，不停服务）：
1. §5.2 导入新账号的 token
2. §5.3 把新账号加进池
3. 观察 §7.3 分布，新成员会开始承接
4. 无需重启、无需迁移会话（HRW 保证只重映射约 1/N）

### 7.5 成本

- **计费口径以 LiteLLM 的 per-key 消费为准**（§6.5），它是唯一持久的账本。
- Proxy 侧的 `cacheInputTokens`（缓存读）/ `cacheWriteTokens`（缓存写）能帮你判断缓存效率：缓存读占输入的比例越高越省。
- 扩池的边际成本主要是账号本身的订阅费。

## 8. 备份与恢复

### 8.1 要备份什么

| 对象 | 位置 | 丢了会怎样 | 频率 |
|---|---|---|---|
| **GHCP OAuth token** | `proxy-data` 卷 → `/data/proxy.sqlite` 的 `proxy_accounts` 表 | **最痛**：全部账号失效，必须重新拿 token 重导 | 每天 |
| 池与成员配置 | 同上（`proxy_pools` / `proxy_pool_members`） | 重建很快（几条 curl），但会有中断 | 每天（随库一起） |
| **虚拟 key 与消费记录** | `litellm-db-data` 卷（PostgreSQL） | 所有客户端 key 失效，要挨个重发 | 每天 |
| **`.env`** | `/opt/ghcp-pool/.env` | 所有密钥丢失（`API_KEY` / `INTERNAL_API_TOKEN` / `SESSION_SECRET` / `LITELLM_MASTER_KEY` / `LITELLM_DB_PASSWORD`），等于重建 | 变更时 |
| SAML 证书 | `/opt/ghcp-pool/certs/idp-cert.pem`、`idp-key.pem` | SSO 容器起不来（导入模式下可重新自签，见 §2.4） | 变更时 |
| Caddy 证书与 ACME 账户 | `caddy-data` 卷（还有 `caddy-config`，内容可再生，可不备） | 可重签，但会撞 Let's Encrypt 频率限制 | 每周 |
| SSO / Login 数据 | `sso-data`、`login-data` 卷 | 导入模式下影响有限，但用户名映射会丢 | 每天 |
| Console 管理员 | `console-data` 卷 → `/data/admins.json` | 管理界面进不去 | 变更时 |
| **原始 token CSV** | **离线保存，不要留在 VM 上** | 灾难恢复时无法重新导入 | 一次 |
| Login 运行日志 | `login-logs` 卷 | 只影响排障回溯 | 不用备 |
| 会话绑定 | `proxy_session_affinity` 表 | 无所谓，默认 30 分钟（`sessionTtlSeconds=1800`）就过期 | 不用备 |
| 请求统计 | `proxy_request_stats` 表 | 只有最近 200 条/账号 | 不用备 |

先确认卷的真实名字（前缀来自 compose 的项目名，默认取项目目录名 `/opt/ghcp-pool` → `ghcp-pool`）：

```bash
docker volume ls | grep -E 'proxy-data|litellm-db-data|caddy-data|sso-data|login-data|console-data'
```
**期望**：`ghcp-pool_proxy-data`、`ghcp-pool_litellm-db-data`、`ghcp-pool_caddy-data` 等。
**前缀不是 `ghcp-pool_`** → 把下面脚本里的 `PREFIX=` 改掉（脚本已做成变量）。

### 8.2 备份脚本

先准备目录（`/var/backups` 是 root 的，普通用户直接 `mkdir` 会失败）：

```bash
sudo mkdir -p /var/backups/ghcp
sudo chown "$USER":"$USER" /var/backups/ghcp
chmod 700 /var/backups/ghcp
```

存为 `/opt/ghcp-pool/backup.sh`（**本手册新增，仓库里没有这个文件**）：

```bash
cat > /opt/ghcp-pool/backup.sh <<'SH'
#!/usr/bin/env bash
set -euo pipefail
cd /opt/ghcp-pool
PREFIX=ghcp-pool          # 卷名前缀，用 docker volume ls 确认
DEST="/var/backups/ghcp/$(date +%F-%H%M)"
mkdir -p "$DEST"
dc() { docker compose -f docker-compose.yml -f docker-compose.litellm.yml -f docker-compose.caddy.yml "$@"; }

# 无论后面哪一步失败，都保证服务被拉起来
trap 'echo "[trap] 确保服务已启动"; dc up -d || true' EXIT

echo "[1/3] PostgreSQL 热备（不停服务）"
dc exec -T litellm-db pg_dump -U litellm litellm | gzip > "$DEST/litellm.sql.gz"

echo "[2/3] SQLite 一致性快照（会中断推理约 30 秒）"
dc stop proxy sso login console
for v in proxy-data sso-data login-data console-data caddy-data; do
  docker run --rm -v "${PREFIX}_${v}:/src:ro" -v "$DEST:/dst" alpine \
    tar czf "/dst/${v}.tgz" -C /src . || echo "  跳过 ${v}（卷不存在？）"
done
dc up -d

echo "[3/3] 配置与证书"
tar czf "$DEST/config.tgz" .env Caddyfile.pool docker-compose.yml \
  docker-compose.litellm.yml docker-compose.caddy.yml litellm certs 2>/dev/null || true

chmod -R go-rwx "$DEST"
echo "完成: $DEST"
ls -lh "$DEST"
SH
chmod +x /opt/ghcp-pool/backup.sh
/opt/ghcp-pool/backup.sh
```

**期望输出**：三步都无报错，最后列出 6～7 个文件，`litellm.sql.gz` **不为 0 字节**，`config.tgz` 也不为 0。
**失败**：

| 现象 | 原因 | 处理 |
|---|---|---|
| `pg_dump: error: connection` | `litellm-db` 没起来 | 先 `dcp up -d litellm-db`，等 healthy |
| `tar: /src: Cannot open` / 每个卷都「跳过」 | 卷名前缀不对 | 用 §8.1 的 `docker volume ls` 确认，改脚本里的 `PREFIX` |
| `mkdir: cannot create directory '/var/backups/ghcp'` | 目录没建或没授权 | 回到本节开头的 `sudo mkdir` + `chown` |
| 脚本中途失败 | — | 脚本里的 `trap` 会自动执行 `dc up -d`；仍不放心就手动 `dcp ps` 确认全部 running |

**为什么 SQLite 要停服务**：SQLite 文件热拷贝有一致性风险（可能拷到写了一半的页）。停 30 秒换一个确定可恢复的备份，是划算的。
（不停服务的替代方案是在容器内用 `VACUUM INTO` 做在线快照，**本环境未验证**，需要时先在测试环境试通再用。）

**定时执行**（避开整点）：

```bash
sudo touch /var/log/ghcp-backup.log && sudo chown "$USER":"$USER" /var/log/ghcp-backup.log
crontab -e
23 3 * * * /opt/ghcp-pool/backup.sh >> /var/log/ghcp-backup.log 2>&1
```
**验证**：第二天 `tail -40 /var/log/ghcp-backup.log` + `ls -lh /var/backups/ghcp/`。
**注意**：备份窗口内会停 30 秒推理，选在低峰时段。

**把备份挪出 VM**（备份和数据在同一块磁盘上等于没备）：

```bash
# 在本地执行
scp -i <SSH_KEY> -r <SSH_USER>@<PUBLIC_IP>:/var/backups/ghcp/<时间戳> ./backups/
```
`config.tgz` 里含 `.env`（全部密钥），**按机密件处理**：别丢到公共存储、别进 git、本地也要限权限。

**保留策略**：

```bash
find /var/backups/ghcp -maxdepth 1 -mindepth 1 -type d -mtime +14 -exec rm -rf {} +
```
（加 `-mindepth 1` 是为了不会把 `/var/backups/ghcp` 自己删掉。）

### 8.3 恢复：同一台 VM 上回滚数据

```bash
cd /opt/ghcp-pool
set -a; . ./.env; set +a
PREFIX=ghcp-pool
B=/var/backups/ghcp/<时间戳>
ls -lh "$B"                     # 先确认备份文件都在、都非空

# ① 停掉会写库的服务
dcp stop proxy sso login console litellm

# ② 恢复 SQLite 卷（先清空再解，避免新旧文件混在一起）
for v in proxy-data sso-data login-data console-data; do
  docker run --rm -v "${PREFIX}_${v}:/dst" -v "$B:/src:ro" alpine \
    sh -c "rm -rf /dst/* /dst/.[!.]* 2>/dev/null; tar xzf /src/${v}.tgz -C /dst"
done

# ③ 恢复 PostgreSQL（litellm 必须处于停止状态）
dcp up -d litellm-db
sleep 15
dcp exec -T litellm-db pg_isready -U litellm -d litellm     # 必须 accepting connections
gunzip -c "$B/litellm.sql.gz" | dcp exec -T litellm-db psql -U litellm -d litellm

# ④ 全部起来
dcp up -d
```

**期望**：`dcp ps` 全部 running；`psql` 恢复过程可能刷 `already exists` 之类的提示，只要最后没有 `FATAL` 就算成功。
**失败**：
- `psql` 报大量 `duplicate key` → 目标库里还有旧数据。把 `litellm-db` 的卷整卷恢复或重建后再导（重建卷会丢当前数据，确认过再做）。
- ② 步某个 `.tgz` 不存在 → 该卷当时备份失败，先确认是不是无关紧要的卷（`login-data` 影响较小），`proxy-data` 缺失必须换一个备份点。

**验证**（三条缺一不可）：

```bash
curl -s "${INT[@]}" "$P/api/accounts?pageSize=100" | jq -r '.items[]|"\(.identity) \(.copilotOauthStatus)"'   # 账号回来了且 valid
curl -s "${INT[@]}" "$P/api/pools/$POOL" | jq '{activeMembers,totalMembers}'                                  # 池成员齐
curl -s "$L/key/list?size=5" "${MK[@]}" | jq '.keys | length'                                                 # 虚拟 key 回来了
# 最后跑一次 §1.1 的端到端探活
```

### 8.4 恢复：换一台全新 VM

1. 按《部署手册》用 `deploy/cloud-init.yaml` 起一台新 VM（装好 Docker、建好 `/opt/ghcp-pool`、把 `<SSH_USER>` 加进 docker 组）
2. 等 `/opt/ghcp-pool/.cloud-init-done` 出现，说明 cloud-init 跑完了
3. 把仓库代码放到 `/opt/ghcp-pool`（**Caddy 相关文件平铺到同一级**，见 §0.3）
4. 解开 `config.tgz`，恢复 `.env`、`Caddyfile.pool`、`certs/`
5. **改 `.env` 里的 `PUBLIC_HOST`** —— 新 VM 是新公网 IP，nip.io 域名跟着变
6. 按 §8.3 的 ②③ 恢复卷和数据库（第一次 `dcp up -d` 之前卷不存在，`docker run -v` 会自动创建空卷，可以直接往里解）
7. `dcp up -d`，等 Caddy 签发新证书（首次通常几十秒；`dcp logs -f caddy` 看 `certificate obtained`）
8. §1.3 + §1.1 验证

> ⚠️ **换 IP 的连带影响，一个都别漏**：
> - `.env` 的 `PUBLIC_HOST` —— 不改则证书签发失败（§2.9）
> - **客户端的 base_url** —— 所有租户都要通知，`https://api.<新HOST>`
> - `deploy/pool-bridge.mjs` 里写死的 `REAL_IP`
> - NSG 规则里如果按公网 IP 写过 destination，也要跟着改（本手册推荐单 VM 写 `'*'`，就没这个问题）
> - 你自己的探活脚本 / cron / 监控告警

### 8.5 恢复演练

**没演练过的备份不算备份。** 建议每季度做一次：起一台临时 VM，走一遍 §8.4，只验证两件事 ——「服务能不能起来」和「一次推理能不能返回 200」。

注意：演练环境和生产用**同一批 GHCP 账号 token**，两边同时打上游会互相影响配额；演练时间控制在几分钟内，演练完立刻删掉临时 VM 及其资源组。
演练发现的问题（最常见的是漏了某个卷、`PUBLIC_HOST` 忘了改）远比事故时发现便宜。

## 9. 升级流程

### 9.1 总原则

1. **先备份**（§8.2），无例外
2. **只重建改动的服务**，不要整栈 `down` 再 `up`
3. **升级前给旧镜像打标签**，这是回滚的唯一依据
4. **升级后立刻跑探活**（§1.3 + §1.1），不通就回滚，不要在生产上边查边改

### 9.2 改了什么 → 该做什么

| 改动的东西 | 需要的操作 | 影响 |
|---|---|---|
| `src/proxy/**`（含 `src/pool/`） | `dcp build proxy` → `dcp up -d --no-deps proxy` | 推理中断几秒 |
| `src/sso` / `src/login` / `src/console` | 同上，换服务名 | 不影响推理（但 sso/login 停的时候不要同时重建 proxy） |
| **`litellm/trusted_identity_hook.py` 或 `litellm/config.yaml`** | **必须 `dcp build litellm`** 后 `dcp up -d --no-deps litellm` | 推理中断十几秒到一分钟（`start_period` 60s） |
| `Caddyfile.pool` | `dcp restart caddy` | 几秒 |
| `.env` | `dcp up -d`（compose 会重建受影响容器） | 视改了哪个变量 |
| `docker-compose*.yml` | `dcp up -d` | 视改动 |

> ⚠️ **`litellm/config.yaml` 是 `COPY` 进镜像的**（见 `litellm/Dockerfile` 里的 `COPY config.yaml /app/config.yaml`），不是挂载进去的。**改了它只 `restart` 没有任何效果**，必须 `build`。这个坑很容易踩，因为 `restart` 会成功、服务会正常，只是配置还是旧的。
> 对照：`Caddyfile.pool` 是 bind mount（`./Caddyfile.pool:/etc/caddy/Caddyfile:ro`），`restart` 就够。
> 验证 config 真的进去了：`dcp exec -T litellm sh -c 'md5sum /app/config.yaml'`，和 VM 上 `md5sum litellm/config.yaml` 对比。

### 9.3 标准升级步骤

```bash
cd /opt/ghcp-pool
set -a; . ./.env; set +a

# ① 备份
./backup.sh

# ② 记录当前状态，供回滚和对比
dcp ps
docker images | grep -E 'ghcp-(proxy|litellm|sso|login|console)'

# ③ 给旧镜像打回滚标签（关键，别跳过）
STAMP=$(date +%Y%m%d-%H%M)
docker tag ghcp-proxy:local   "ghcp-proxy:rollback-$STAMP"
docker tag ghcp-litellm:local "ghcp-litellm:rollback-$STAMP"

# ④ 更新代码（scp / git pull，按你的流程）

# ⑤ 只构建改动的服务
```

**失败**：`dcp build` 报错 → 代码没编过，**不要继续**，旧容器还在跑，先修代码。

### 9.4 回滚

```bash
STAMP=<升级时记下的标签>
docker tag "ghcp-proxy:rollback-$STAMP" ghcp-proxy:local
dcp up -d --no-deps --force-recreate proxy
sleep 15
curl -s "$P/readyz" && curl -s "${INT[@]}" "$P/api/pools/$POOL" | jq '{activeMembers,totalMembers}'
```

**期望**：`readyz` 返回 ok，池状态正常。
**失败**：`docker tag` 报 `No such image` → 标签没打或已被清理，只能重新 build 上一个代码版本。

**关于数据库 schema 的回滚**：Proxy 启动时会自动跑迁移（`src/proxy/src/db/migrations.ts`）。这些迁移**绝大部分**是 `CREATE TABLE IF NOT EXISTS`、`CREATE INDEX IF NOT EXISTS` 和「缺列才加列」，幂等且只增不删。
含义：
- **回滚镜像不会回滚 schema**（没有降级路径）
- 新增的表/列对旧代码**无害**（旧代码不读它们），所以**镜像回滚通常是安全的**

> ⚠️ **一个例外要知道**：`migrateCopilotOauthCredentials` 这个历史迁移**会重建 `proxy_accounts` 表**（建新表 → 拷数据 → 删旧表 → 改名），并在 `schema_migrations` 里记一笔。它只在从很老的库升级时触发一次；一旦跑过，**回滚到那个迁移之前的镜像会启动失败**（代码里会显式抛 `Migration ... is recorded but proxy_accounts still uses the legacy schema.`）。
> 所以跨大版本回滚前，先确认 `schema_migrations` 里的记录：
> ```bash
> dcp exec -T proxy sh -c "command -v sqlite3 >/dev/null && sqlite3 /data/proxy.sqlite 'select * from schema_migrations;'" \
>   || echo "容器里没有 sqlite3，改用 §8.3 从备份恢复来判断"
> ```
> （容器镜像里不一定装了 `sqlite3`，**这条命令未实测**；拿不到就直接走下面的「必须走数据恢复」路径。）

**什么时候不能只回滚镜像、必须走 §8.3 数据恢复**：
- 新版本引入了破坏性迁移（改列类型、删列、重建表）
- 新版本写入了旧版本读不懂的数据
- 误操作删了账号 / 池 / key

### 9.5 升级 LiteLLM 官方镜像

`litellm/Dockerfile` 基于 `ghcr.io/berriai/litellm:main-stable`，**这是滚动标签** —— `docker build` 时如果基础镜像更新了，你会不知不觉换到新版 LiteLLM。

```bash
dcp build --pull litellm      # 显式拉最新基础镜像
dcp up -d --no-deps litellm
sleep 60
curl -s -o /dev/null -w '%{http_code}\n' "$L/health/liveliness"
```
**期望**：`200`（LiteLLM 启动较慢，healthcheck 的 `start_period` 是 60 秒，耐心等）。
**失败**：容器反复 `unhealthy` → `dcp logs --tail 100 litellm`；最常见是新版 LiteLLM 改了 hook 依赖的内部 API，导致 `callbacks` 加载失败（日志里会有 ImportError / AttributeError），此时立刻回滚。

升级 LiteLLM 后**必须重跑安全验证**，因为 hook 依赖的内部 API（`UserAPIKeyAuth.via_virtual_key`、`CustomLogger.async_pre_call_hook` 的签名、`litellm.proxy._types` 的路径）可能随版本变化：

```bash
# 在开发机上（不是 VM），仓库根目录，先确保依赖装好
npm install
STAMP=$(date +%s) LITELLM_MASTER_KEY='<master key>' API_BASE="https://api.<PUBLIC_HOST>" \
  npx tsx tests/verify-litellm.mts
```
**期望**：最后一行是 `LiteLLM 层验证：✅ 全部通过`，退出码 0。特别关注这三条：
- `无 key 被拒`（401）
- `master key 也不能直接推理（hook 要求虚拟 key）`
- `带伪造身份头仍能调用（头被剥掉）`

**为什么必须传 `STAMP`**：脚本用 `tenant-a-${STAMP||1}` 作为 key_alias，不传的话第二次运行会因为 alias 重复而失败。
**跑完要收尾**：这个脚本**会真的建两把虚拟 key 且不会自动删**。跑完在 VM 上清理掉：
```bash
curl -s -X POST "$L/key/delete" "${MK[@]}" -d '{"key_aliases":["tenant-a-<你用的STAMP>","tenant-b-<你用的STAMP>"]}' | jq .
```
（脚本还会在最后把 tenant-a 的 key 明文打印出来 —— 终端记录注意保密。）

**任何一条不过，立刻回滚 litellm 镜像**（§9.4，把镜像名换成 `ghcp-litellm`、服务名换成 `litellm`）—— 这三条是多租户隔离的全部依据，破了等于所有租户之间没有边界。
