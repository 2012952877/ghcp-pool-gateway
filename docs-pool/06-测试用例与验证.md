# 06 · 测试用例与验证

本章讲清楚仓库里每个测试脚本**验证什么、怎么跑、期望看到什么、失败了从哪查**，并给出交付验收时的最小必跑集合。

阅读顺序建议：先读 §0 的路径约定（不读会在第一条命令就卡住），再看 §1 分层总览判断你现在处于哪个阶段，然后跳到对应脚本那一节。验收当天照 §6 的清单走。

## 0. 开跑前必须先确认的三件事

### 0.1 脚本的实际位置（第一条命令就会卡在这里）

本章按仓库结构文档写作，即脚本在 `tests/` 目录下。但**本次验证时，除 `verify-litellm.mts` 外的脚本都放在仓库根目录**（开发期遗留）。两种布局的命令不一样，先确认你手上是哪种：

```bash
cd <仓库根目录>          # 包含 package.json 的那一层
ls tests/ 2>/dev/null; ls *.mts *.cjs 2>/dev/null
```

| 你看到的 | 说明 | 本章命令怎么改 |
|---|---|---|
| `tests/` 下有 `selector-check.cjs`、`e2e-pool.mts`、`verify-cloud.mts`、`verify-litellm.mts` | 已整理为文档中的结构 | 照抄，不用改 |
| 根目录下有 `selector-check.cjs` / `e2e-pool.mts` / `verify-cloud.mts`，只有 `tests/verify-litellm.mts` | 本次验证时的实际状态 | 把命令里除 `verify-litellm.mts` 外的 `tests/` 前缀去掉，例如 `node selector-check.cjs` |

> ⚠️ **搬动 `e2e-pool.mts` 时会踩的坑**：它用 ESM 相对导入拿 Proxy 源码：
> `await import('./src/proxy/src/server.js')`、`./src/proxy/src/db/connection.js`、`./src/proxy/src/pool/sessionKey.js`。
> ESM 相对路径是**相对脚本文件自身**的。脚本在仓库根时这三处写 `./src/...` 正确；一旦移进 `tests/`，必须同步改成 `../src/...`，否则报 `ERR_MODULE_NOT_FOUND` 且错误路径里出现 `tests/src/proxy`。
> 而同一个文件里的 `readFileSync('./seed-accounts.json')` 用的是**当前工作目录**，无论脚本放哪儿都必须从仓库根执行。

### 0.2 云上脚本打的是哪个端口

`verify-cloud.mts` 这个脚本打的是 **GHCP Proxy（3000）**，不是 LiteLLM（4000）。它们要自己发 `X-User-Identity`、要调 `/api/pools`、要带 `X-Internal-Token`，这些能力 LiteLLM 层没有（`trusted_identity_hook` 会无条件剥掉身份头）。详见 §2.3——**这是新手最容易花掉一小时的地方**。

### 0.3 这套环境的模型名

四个云上脚本请求体里写死的是 `model: 'claude-opus-5'`。如果你的 LiteLLM `model_list` 或上游没有这个模型，所有推理类断言都会失败（通常是 4xx + `model not found` 一类的错误体）。换环境时要么确认这个模型可用，要么改脚本里的 `model` 字段。

## 1. 测试分层总览

| 层 | 脚本 | 要不要真实 Copilot 账号 | 要不要外网 | 要不要云上环境 | 单次耗时 | 用途 |
|---|---|---|---|---|---|---|
| L0 算法 | `tests/selector-check.cjs` | 否 | 否 | 否 | < 5 秒 | 证明 Rendezvous 选择算法的四条性质 |
| L1 单元 | `src/proxy/src/pool/pool.test.ts` | 否 | 否 | 否 | ~2 秒（实测 duration_ms 1874） | 池解析、粘性、冷却、会话 key 推导 |
| L1 单元 | `src/proxy/src/routes/poolApi.test.ts` | 否 | 否 | 否 | ~1 秒 | 池管理 API 的鉴权与增删改查 |
| L1 回归 | Proxy 全量套件 | 否 | 否 | 否 | ~4 秒（实测 duration_ms 4098） | 确认池化改造没有破坏原有功能 |
| L2 本地端到端 | `tests/e2e-pool.mts` | **是** | **是** | 否 | 1–3 分钟 | 本地起 Proxy，打真实上游，验证全链路 |
| L3 云上 | `tests/verify-cloud.mts` | 是（已部署） | 是 | **是** | 1–3 分钟 | 从客户端侧验证云上池行为 |
| L3 云上 | `tests/verify-litellm.mts` | 是（已部署） | 是 | **是** | 1–2 分钟 | 多租户隔离与身份不可伪造（**安全边界**） |

L0/L1 是**离线**的，任何一台装了 Node 的机器都能跑，接手的工程师第一天就该跑通。
L2 起需要真实 GitHub Copilot 订阅账号的 OAuth token，且**出网要能到 `api.githubcopilot.com`**（中国区通常需要代理）。

## 2. 跑测试前的准备

### 2.1 一次性准备

```bash
cd <仓库根目录>          # 即包含 package.json 的那一层
node -v
npm ci
npm --workspace @ghcp/shared run build
```

| 命令 | 期望 | 失败怎么办 |
|---|---|---|
| `node -v` | 本次验证用的是 **v24.15.0**。更低版本未验证；如果你用的是 v20/v22，跑通了就记下版本号，跑不通先换 v24 排除变量 | — |

|---|---|---|
| `Cannot find module '@ghcp/shared'` | shared 没编译 | 执行上面第 4 行 |
| `ERR_MODULE_NOT_FOUND .../dist/index.js` | 同上 | 同上 |

| `POOL_INTERNAL` | `verify-cloud.mts` | 同一文件里的 `INTERNAL_API_TOKEN` | 同上，所有 `/api/*` 调用返回 401 `internal_auth_failed` |

| `MYSQL_TEST_URL` | MySQL 集成测试（未设时自动跳过） | 见仓库 `README.md` 的 MySQL 测试库章节 | 该测试计入 `skipped 1`，属正常 |

一次性把云上三个值取到本地：

```bash
ssh <VM 登录用户>@<VM 公网 IP> \
  'grep -E "^(API_KEY|INTERNAL_API_TOKEN|LITELLM_MASTER_KEY)=" /opt/ghcp-pool/.env'
```

- `<VM 登录用户>`：创建 VM 时指定的管理员用户名（Ubuntu 24.04 镜像常见为 `azureuser`）。
- `<VM 公网 IP>`：Azure 门户 VM 概览页的「公共 IP 地址」，也可以用 `az vm list-ip-addresses -g <资源组> -n <VM名> -o tsv`。

| 现象 | 处理 |
|---|---|
| `No such file or directory` | 部署目录不是 `/opt/ghcp-pool`。用 `ssh <用户>@<IP> "sudo find / -name '.env' -path '*ghcp*' 2>/dev/null"` 定位。注意仓库里的模板文件名是 `.env.pool`，部署时被复制/改名为 `.env`，现场以实际为准 |
| 只出来 2 行，缺 `LITELLM_MASTER_KEY` | LiteLLM 层还没部署，先做完第 05 章 |
| SSH 连不上（超时 / `Connection refused`） | 先按第 04 章的排查顺序：**网卡 NSG → 子网 NSG → VM 电源 → 数据库状态**。订阅策略会周期性清空 NSG 自定义规则、停 VM，也会**新建一个零规则的子网 NSG 挂到 VNet 上**——最后这种打标签也挡不住，最容易漏 |

**Windows 上传环境变量的写法差异**（本项目在 Windows 上开发过，这是踩过的坑）：

| Shell | 写法 |
|---|---|
| bash / Git Bash / WSL | `POOL_API_KEY='<值>' npx tsx tests/verify-cloud.mts` |
| PowerShell | `$env:POOL_API_KEY='<值>'; npx tsx tests/verify-cloud.mts` |

PowerShell 里内联 JSON 一律用单引号包外层，双引号里加 `\"` 转义会被 PowerShell 吃掉。另外在 Windows 上编辑 `.sh` / `.cjs` 时注意行尾要保持 LF，CRLF 会让 `bash` 报 `$'\r': command not found`。

### 2.3 三个脚本的服务器地址是硬编码的（重要，第一次上手必看）

| 脚本 | 地址来源（源码原文） | 接手时要做什么 |
|---|---|---|
| `verify-litellm.mts` | `const API = process.env.API_BASE \|\| 'https://api.20.78.139.35.nip.io'` | 传 `API_BASE` 即可，不用改代码 |
| `verify-cloud.mts` | `const API = 'https://api.20.78.139.35.nip.io'`（文件第 2 行） | **必须改这一行** |

而 `deploy/Caddyfile.pool` 里 `api.{$PUBLIC_HOST}` 是 `reverse_proxy litellm:4000`，`console.{$PUBLIC_HOST}` 是 `reverse_proxy console:7004`——**Caddy 里没有任何一条对外路由指向 Proxy:3000**（这是刻意的设计：Proxy 是内部服务，只由 LiteLLM 调用）。于是：

| 你所处的阶段 | 这三个脚本的 `API` 该填什么 |
|---|---|
| 只部署了基础栈，`api` 子域直连 Proxy | `https://api.<域名>`（本次验证就是在这个阶段跑通的） |
| 已按 `Caddyfile.pool` 把 `api` 子域切给 LiteLLM | **必须**改用 SSH 端口转发打内网 Proxy（见下） |

```bash
# 窗口 1：开一个到 VM 上 Proxy 的隧道，保持不关
ssh -N -L 3000:127.0.0.1:3000 <VM 登录用户>@<VM 公网 IP>
```

然后把三个脚本里的 `API` 常量改成 `const API = 'http://127.0.0.1:3000';`。

```bash
# 窗口 2：验证隧道通了
curl -s -o /dev/null -w '%{http_code}\n' http://127.0.0.1:3000/api/pools \
  -H 'X-Internal-Token: <INTERNAL_API_TOKEN>'
```

| 返回 | 含义 | 处理 |
|---|---|---|
| `200` | 通了，可以跑脚本 | — |
| `000` | 隧道没起来 | 看窗口 1 有没有报错；确认 VM 上 `docker compose ps` 里 `proxy` 是 `healthy` |
| `401` | token 填错 | `/api/*` 只认 `X-Internal-Token` 一个头（源码 `requireInternalToken`），值必须等于 `.env` 里的 `INTERNAL_API_TOKEN` |

> 改进建议（**不是当前仓库状态**）：把这三处常量统一改成 `process.env.API_BASE || '<默认值>'`，和 `verify-litellm.mts` 对齐，就不用每次改代码了。

### 2.4 顺手确认一次端口绑定

内部服务的宿主机绑定地址由 `.env` 的 `BIND_ADDR` 控制，默认 `127.0.0.1`。
在服务器上确认：

```bash
sudo ss -tlnp | grep -E ':(80|443|3000|4000|7001|7003|7004)\s' | awk '{print $4}' | sort -u
```

**期望**：只有 `0.0.0.0:80` 和 `0.0.0.0:443`，其余五个端口均为 `127.0.0.1:xxxx`。

再从外部机器确认一次：

```bash
curl -s -o /dev/null -w '%{http_code}\n' --max-time 8 http://<服务器地址>:3000/api/pools
```

| 返回 | 含义 |
|---|---|
| `000`（超时或拒绝） | ✅ 符合预期 |
| 其他 | 检查 `BIND_ADDR` 是否被改成了 `0.0.0.0`，以及网络层是否放行了多余端口 |

## 3. 逐个脚本

### 3.1 `tests/selector-check.cjs` —— 选择算法的四条性质

**验证什么**

用与 `src/proxy/src/pool/poolSelector.ts` **相同的算法**（sha256 → `readUIntBE(0, 6)` → 除以 `0x1000000000000` 归一 → `-w / ln(unit)` 加权 Rendezvous 打分）独立实现一遍，跑纯数学验证。不依赖数据库、不依赖网络、输入是固定种子（`session-0` … `session-9999` 的 sha256），因此结果是**确定性**的——同样的代码在任何机器上跑出的数字应当逐字相同。

四条性质对应四个业务问题：

| 性质 | 回答的业务问题 |
|---|---|
| 1 粘性 | 同一个会话会不会中途换账号（换了就丢审计链） |
| 2 分布均匀 | 100 个人摊到 N 个账号，会不会有人被压爆而别人闲着 |
| 3 移除成员的重映射范围 | 下线/冷却一个账号，会波及多少无关会话 |
| 4 权重 | 有的账号额度大，能不能按比例多分 |

> 脚本文件头的注释写的是「三个关键性质」，实际实现了四条。以代码为准。

**怎么跑**

```bash
cd <仓库根目录>
node tests/selector-check.cjs
```

不需要任何环境变量，也不依赖 `npm ci`（只用到 Node 内置 `crypto`）——这是接手第一天最先该跑通的一条。

**期望输出（本次复跑逐字一致）**

```
【性质1】粘性：同一 sessionKey 重复选择 20 次结果一致  → ✅ 通过
【性质2】分布：10000 会话 / 100 账号  均值=100.0 标准差=10.4 变异系数=10.4%  最少=64 最多=126  → ✅ 均匀
          覆盖账号数 100/100
【性质3】移除 1 个账号：重映射 101/10000 (1.0%)，其中「本不该动却动了」的 0  → ✅ 只影响被移除账号的会话
【性质4】权重 8:1:1 → big=80.4% (理论 80%)  small-1=9.4%  small-2=10.2%  → ✅ 符合

【对比】同一会话连发 20 个请求，落在几个不同账号上：
   Rendezvous 粘性 : 1 个账号   → 缓存命中率 ~95%（首次 write，其余 read）
   逐请求轮询(100) : 20 个账号  → 缓存命中率 0%（每次都是 cache_write）
```

**怎么读这些数字**

- 变异系数 10.4%：账号间负载差异约 10%。理论上独立随机分配的变异系数 ≈ 1/√100 = 10%，说明没有额外偏斜。
- 性质 3 的 `1.0%` 和 `0`：移除 1/100 个账号，只有 1.0% 的会话被重映射，且**其中 0 条是「本来绑在别的账号上却被殃及的」**。这是一致性哈希相对于取模的核心优势——换成 `hash % N`，移除一个账号会让绝大多数会话重新洗牌。
- 最后的【对比】块是**脚本里写死的说明性文字，不是本次运行测出来的**，里面的 `~95%` 是解释性估算。真实测量见 §3.9（实测 82.6%，口径不同，不要混用）。

**失败排查**

| 现象 | 含义 | 处理 |
|---|---|---|
| 性质 1 显示 ❌ | 打分函数引入了随机性或时间因素 | 检查 `poolSelector.ts` 里有没有混入 `Date.now()`、`Math.random()` |
| 性质 2 变异系数 > 20% | 哈希取位或归一化有问题 | 对照 `weightedScore` 的 `readUIntBE(0, 6)` 与 `0x1000000000000` 是否配对（6 字节 ↔ 2^48） |
| 性质 3 「本不该动却动了」> 0 | 已经不是 Rendezvous 语义了 | 检查是否被误改成了取模，或选择时引入了不稳定排序 |
| 数字与上面不同但都是 ✅ | 有人改了 `keys()` 的种子、账号数或 `mk()` 的命名规则 | 与本文的基线逐字比对；本脚本输入固定，不应出现浮动 |
| 报 `d.readUIntBE is not a function` | Node 版本过低或环境异常 | 换 v24 重试 |

### 3.2 `src/proxy/src/pool/pool.test.ts` —— 池核心逻辑单元测试（11 条）

**验证什么**

用内存 SQLite（`DB_PATH=:memory:`）建一个多成员的池，逐条验证 `poolResolver.ts` 与 `sessionKey.ts` 的行为。脚本内部自己设好了 `DB_PATH` / `INTERNAL_API_TOKEN` / `LOG_LEVEL`，**不需要外部环境变量**。

| # | 测试名（与源码逐字一致） | 保护的行为 |
|---|---|---|
| 1 | 1:1 身份不会被误判为池 | 普通账号身份传进来时不走池逻辑，1:1 模式零影响 |
| 2 | 禁用的池回落为普通身份 | `enabled=false` 后按普通身份走，不报错 |
| 3 | 会话粘性：同一 sessionKey 反复解析落在同一成员 | 同一 sessionKey 多次解析落在同一成员 |
| 4 | 不同会话会分散到多个成员 | 多个会话至少覆盖多个账号 |
| 5 | 429 立刻冷却该成员，会话自动改绑到别的成员 | `forceCooldown: true` 时**不必攒够失败次数**，成员立即进 `cooling` 且会话换绑 |
| 6 | 普通失败要攒够阈值才冷却 | 未到 `failureThreshold` 不冷却，到了才冷却 |
| 7 | 成功会清零失败计数并解除冷却 | 一次成功把 `state` 拉回 `active`、连续失败数归零、冷却时间清空 |
| 8 | 全员冷却时抛 PoolAllCoolingError 并给出 retryAfter | 且 `retryAfterSeconds > 0`，让客户端知道等多久 |
| 9 | 移除成员时该成员的会话绑定一并清理 | 不留悬空绑定，下次解析换到新成员 |
| 10 | 会话 key 推导优先级：header > metadata > prompt 前缀 | 四个分支（`header` / `metadata` / `prompt-prefix` / `fallback`）各断言一次 |
| 11 | 相同 prompt 前缀 → 相同会话 key（缓存亲和的基础） | 不同 system 提示词得到不同 key |

**关于默认策略——这是最容易随机失败的点**

`poolTypes.ts` 里 `POOL_DEFAULTS` 的实际值：

| 字段 | 默认值 |
|---|---|
| `strategy` | **`least-loaded`** |
| `sessionTtlSeconds` | 1800（30 分钟） |
| `cooldownSeconds` | 300（5 分钟） |
| `failureThreshold` | 3 |
| `weight` | 1 |

所以任何依赖「同会话固定同账号」的用例都必须在建池时**显式声明 `strategy: 'sticky-affinity'`**，`pool.test.ts` 里已经这么做了并留了注释。不这么做会间歇性失败。

**怎么跑**

```bash
cd <仓库根目录>
npx tsx --test src/proxy/src/pool/pool.test.ts
```

### 3.6 `tests/verify-cloud.mts` —— 从客户端侧验证云上池行为

**验证什么**

不进 VM、不看容器日志，纯粹以「客户端」的身份从外部验证已部署环境。四组：

| 组 | 脚本实际的断言 |
|---|---|
| 1 会话粘性 | 同一 `X-Session-Id: cloud-sticky-<毫秒时间戳>` 连发 5 次全部 200；`request-stats` 里 `poolId === 'team-pool'` 的条数 **≥ 5** |
| 2 多会话分散 | 再发 10 个不同会话后，`poolId === 'team-pool'` 的记录里出现的 `identity` **≥ 2 个** |
| 3 池状态 | `GET /api/pools/team-pool` 可读；**两个成员的 `lastUsedAt` 都非空**（都真承接过流量） |
| 4 1:1 回归 | 直接用 `demo01` 身份调用仍返回 200 |

> ⚠️ **必须知道的两个口径问题，否则会把「假通过」当成通过：**

### 3.7 `tests/verify-litellm.mts` —— 多租户隔离（**安全验收的核心**）

**验证什么**

这组用例验证多租户隔离是否成立：**使用方只能以自己 key 所绑定的身份访问，不能通过构造请求头切换到别的租户。**

身份由 LiteLLM 的 `trusted_identity_hook` 从虚拟 key 的 `metadata.trusted_user_id` 解析后注入下游，客户端自带的身份头会被丢弃。下面六组用例逐条确认这一行为。

六组：

| 组 | 脚本实际的断言 | 对应的安全属性 |
|---|---|---|
| 1 | `GET /health/liveliness`（不带任何 key）返回 200 | LiteLLM 活着 |
| 2 | 用 master key 建两把虚拟 key（`key_alias` 为 `tenant-a-<STAMP>` / `tenant-b-<STAMP>`），`metadata.trusted_user_id = 'team-pool'`，`rpm_limit=60 / tpm_limit=200000 / max_parallel_requests=5 / max_budget=50 / budget_duration=30d / duration=30d` | 每租户一把 key |
| 3 | 不带任何 key 调 `/v1/messages` → **必须正好是 401**；用 master key 直接推理 → **只断言 `!== 200`（实测 403）** | 无 key 不能用；master key 不是推理凭证 |
| 4 | 用虚拟 key **同时带伪造的 `X-User-Identity: demo01`** 调用 → **仍返回 200**；随后 `GET /spend/logs?limit=3` 返回 200 | 伪造头被 hook 剥掉，请求按 key 元数据的 `team-pool` 走池分配 |
| 5 | 两把 key 各自能正常调用（每次间隔 1 秒） | 租户之间不互相阻塞 |
| 6 | `GET /key/list?return_full_object=true&size=50` 里 `key_alias` 以 `tenant-` 开头的 key **≥ 2 把**，逐把打印 `spend` | per-key 计费独立 |

**这个脚本的三个能力边界（必须如实告诉客户，不要夸大）**

| 边界 | 说明 |
|---|---|
| 两把 key 指向的是**同一个池** `team-pool` | 脚本文件头注释写着「不同虚拟 key → 不同池 → 互不干扰」，但代码里两把 key 的 `trusted_user_id` 都是 `team-pool`。**「不同 key 走不同池」这条没有被自动验证**。要演示的话，需要手工再建一个池、再建一把 `trusted_user_id` 指向它的 key |
| 第 4 组的第二条断言不验证金额 | 「调用有记账」只检查 `GET /spend/logs?limit=3` 这个接口**返回 200**，不看返回内容、不比对 spend 是否增加 |
| 第 4 组不验证请求实际落到哪个账号 | 脚本无法从 LiteLLM 侧看到 GHCP 侧的归因。要真正确认伪造没穿透，必须手工做 A7（见 §6.1） |
| 第 6 组的「2 把」是下限，不是精确值 | 过滤条件是 `key_alias.startsWith('tenant-')`，会把**历次运行留下的所有测试 key** 都算进来。跑第 5 次时这里可能显示「10 把」，仍算 ✅ |
| 第 6 组在 `/key/list` 非 200 时**不会计失败** | 源码里 `ok(...)` 只在 `if (list.status === 200)` 分支内调用。接口挂了会静默略过，整体仍显示「全部通过」。看到第 6 组一行输出都没有，要当成失败处理 |

第 3、4 组的机制来自 `litellm/trusted_identity_hook.py`（逐条对照源码）：`async_pre_call_hook` 先无条件调用 `_remove_request_identity_headers(data)` 删掉 `data['headers']` / `data['extra_headers']` / `data['proxy_server_request']['headers']` / `data['metadata'].headers` / `data['litellm_metadata'].headers` 里所有大小写形式的 `X-User-Identity`；再要求 `user_api_key_dict.via_virtual_key is True`，否则 `HTTPException(401)`；再从 key 的 `metadata.trusted_user_id` 取身份，不是字符串抛 403，不匹配正则 `^[A-Za-z0-9][A-Za-z0-9._:@-]{0,127}$` 也抛 403；最后写进 `data['extra_headers']['X-User-Identity']`。配合 `config.yaml` 里的 `forward_client_headers_to_llm_api: false`，客户端无论如何都改不了自己的身份。

**怎么跑**

```bash
cd <仓库根目录>
API_BASE='https://api.<你的域名>' \
LITELLM_MASTER_KEY='<VM .env 里的 LITELLM_MASTER_KEY>' \

```

- `<你的域名>`：`.env` 里的 `PUBLIC_HOST`，形如 `20.78.139.35.nip.io` 或客户自有域名。整条 `API_BASE` 就是 `https://api.` + 这个值。

> ⚠️ **`STAMP` 每次必须给且必须不同。** 脚本用 `key_alias: \`${alias}-${Math.floor(Number(process.env.STAMP || '1'))}\``。不给就固定是 `tenant-a-1` / `tenant-b-1`；LiteLLM 的 `key_alias` 唯一，**第二次跑必然在第 2 组报错**。给了非数字会算出 `NaN`，alias 变成 `tenant-a-NaN`，同样只能用一次。`$(date +%s)` 是纯数字，符合要求。
> PowerShell 下：`$env:STAMP=[string][int][double]::Parse((Get-Date -UFormat %s))`

## 4. 已知失败项 —— 不要误判为改造引入的回归

### 4.1 事实（本次复跑确认）

`npm --workspace @ghcp/proxy run test` 的基线是 **50 tests / 48 pass / 1 fail / 1 skipped**。

那 1 条失败是：

| 项 | 值 |
|---|---|
| 测试名 | `persists JSON, SSE, plain-text, and bodyless upstream HTTP failures` |
| 文件 | `src/proxy/src/diagnostics/errorDiagnostics.test.ts`，声明在**第 279 行** |

### 4.2 它跟账号池改造有没有关系？—— 诚实说明

交付方的说法是：**这条测试在上游 GHCP API Console 的原始代码里就是失败的，改造前后基线完全一致。**

必须说清楚的是：这条断言打的是 `listRequestStats`，而池化改造**确实动过 `proxy_request_stats`（新增 `pool_id` 列）**。所以不能简单说「没有代码路径交集」——它跟池化改造在同一张表上。真正能自证的只有一件事：**跑一遍上游原始代码，看是不是同样失败**。

### 4.3 判定规则（写进验收标准）

| 结果 | 结论 |
|---|---|
| `fail 1`，且失败的**只有**上面这一条 | ✅ 回归通过（前提：§4.2 的上游对比已完成，或客户接受该项待确认） |

## 7. 写测试时的注意事项

这几条都是真踩过的坑，新写任何验证脚本前先读一遍。

### 7.1 Anthropic 会误判合成文本，导致 `stop_reason: "refusal"`

**现象**：请求返回 HTTP 200，但响应体里 `stop_reason` 是 `refusal`，`category` 是 `reasoning_extraction`，内容为空。看起来像「上游挂了」，其实是内容安全判定。

**触发条件（实测）**：

| 会触发 | 不会触发 |
|---|---|
| 大段重复的段落（为了凑 token 数把同一句复制 N 遍） | 内容各异的自然文本 |
| 形如 `Rule 1: ... cite internal reference document REF-0001` 的模板化规则列表 | 正常的科普 / 说明性段落 |
| 机械生成的编号 + 占位符组合 | 每段主题不同的真实内容 |

**为什么会这样**：这类文本在统计特征上很像「试图诱导模型泄露内部推理/系统提示」的攻击载荷，会被判为提取推理内容的尝试。

**正确做法**：用十几段**主题各不相同**的自然文本（科普、技术规范等）拼出足够长的系统提示词。每段内容真实、彼此无关、不重复。

**兜底做法**：脚本里加自动重试并跳过：

```ts
if (res.status === 200 && b?.stop_reason !== 'refusal') { /* 采纳 */ }
// 否则 sleep 1500ms 后重试
```

连续多次被拒时应把该轮排除出统计，而不是当成失败。若**经常**出现，说明测试文本需要重写。

⚠️ **`e2e-pool.mts` 和 `verify-cloud.mts` 没有 refusal 重试**——它们发的都是「回复OK」这类极短请求，很少被误判，但真被判了就是直接红。

## 7.3 对照实验要小心执行顺序造成的偏差

比较两种策略时，若两组用同一段系统提示词，先跑的那组会给后跑的那组留下热缓存，
导致后者的命中率被系统性高估。

**三条规则**：

| 规则 | 做法 |
|---|---|
| 每组用**各自独立**的 `RUN_ID` | A 组 `RUN_ID=<x>-A`，B 组 `RUN_ID=<x>-B`，让两组前缀不同，互不命中 |
| 交换顺序**再跑一遍** | 先 A 后 B 跑一次，先 B 后 A 再跑一次。两次结论一致才可信 |
| 只在**静默环境**里跑 | `GET /api/request-stats?limit=1` 读的是**全局**最后一条（不按 identity 过滤），有并发流量时账号列会串 |

另外注意**策略是池级别的全局状态**，不是请求级别的。两个人同时跑不同策略的实验会互相踩踏，
多人协作时给每个人建独立的池。

### 7.4 API 路由行为上的两个陷阱（写脚本前必读）

| 陷阱 | 事实 | 正确做法 |
|---|---|---|
| `GET /api/request-stats?identity=<x>` **不按 identity 过滤** | `adminApi.ts` 里实现是 `listRequestStats(undefined, readLimit(req.query.limit))`，`identity` 查询参数被丢弃，返回全局最近 N 条 | 要按账号过滤，用 `GET /api/accounts/<identity>/request-stats?limit=<N>` |
| `/api/*` 只认一个鉴权头 | `app.use('/api', requireInternalToken, ...)`，中间件只读 `X-Internal-Token` 并与 `config.internalApiToken` 全等比较，失败返回 401 `internal_auth_failed` | 不要额外带 `x-api-key`（无害但无用）；`x-api-key` 是 `/v1/*` 推理路径用的 |

### 7.5 其他零碎但会浪费时间的点

| 点 | 说明 |
|---|---|
| 默认策略是 `least-loaded` | 任何依赖「同会话同账号」的断言都必须显式 `strategy: 'sticky-affinity'`，否则会间歇性失败。`pool.test.ts` 里已经这么做了并留了注释；`e2e-pool.mts` 里**没有**（见 §3.5） |
| 新加的池测试记得进 glob | `src/proxy/package.json` 的 `test` 脚本不含 `src/pool/`，放在那里的测试**不会被 CI 跑到** |
| 账号 identity 大小写 | 导入接口会把用户名转小写。脚本里硬编码 `demo01` 还是 `Demo01`，要和 `GET /api/accounts` 的实际返回对齐，否则统计查不到、断言假失败 |
| 云上脚本的模型名写死为 `claude-opus-5` | 换环境要确认这个模型可用，否则所有推理断言都红 |
| Windows 行尾 | 编辑 `.sh` 保持 LF（CRLF 会让 bash 报 `$'\r': command not found`）；`.cjs` / `.mts` 影响小但也建议统一 LF |
| PowerShell 内联 JSON | 外层用单引号：`-d '{"strategy":"least-loaded"}'`。用双引号 + `\"` 转义会被 PowerShell 吃掉 |
| 批量 `az tag update` | 会被 ARM 限流，报错但**可能实际已生效**。别看返回码，去查真实状态 |
| 打不开网页先怀疑 NSG | 中国区 VPN 的 Fake-IP DNS 是**正常且必需**的（流量要走隧道），强制解析到真实 IP 反而连不上，**不要改 hosts**。排查顺序：网卡 NSG → **子网 NSG**（最容易漏，订阅策略会新建一个零规则的子网 NSG 挂上去，新建资源天生没标签，`CostControl=Ignore` / `SecurityControl=Ignore` 挡不住它）→ VM 电源 → 数据库状态。两层 NSG 都要放行，缺一不可 |
