### 0.2 全文占位符总表

后续所有文档共用这套占位符。**每个都写清了怎么取值**，不要凭感觉替换。

| 占位符 | 含义 | 怎么取值 | 存放位置 |
|---|---|---|---|

| `<INTERNAL_API_TOKEN>` | 服务间/管理接口令牌 | 同上，另生成一把 | `.env` 的 `INTERNAL_API_TOKEN` |

| `<LITELLM_MASTER_KEY>` | LiteLLM 管理密钥 | 必须以 `sk-` 开头：`echo "sk-$(node -e "console.log(require('crypto').randomBytes(30).toString('base64url'))")` | `.env` 的 `LITELLM_MASTER_KEY` |
| `<LITELLM_DB_PASSWORD>` | LiteLLM 的 PostgreSQL 密码 | 随机 24 字节，同上方法 | `.env` 的 `LITELLM_DB_PASSWORD` |
| `<池名>` | 对外暴露的池标识，例 `team-pool` | 自己起名。必须匹配 `^[A-Za-z0-9][A-Za-z0-9._:@-]{0,127}$`（这是 LiteLLM hook 的校验正则），且**不能与任何真实账号名重名** | `proxy_pools.pool_id` |
| `<租户名>` | 虚拟 key 的别名，例 `tenant-a` | 自己起名，仅用于对账辨识 | LiteLLM 的 `key_alias` |
| `<资源组>` / `<VM名>` | Azure 资源标识 | 建 VM 时你自己定的名字；忘了用 `az vm list -o table` 查 | — |

## 1. 一句话定位

**把一批 GitHub Copilot 订阅，聚合成一个带虚拟 key、能多租户隔离、能自动分摊负载的 Claude / GPT 兼容 API 服务。**

它建立在开源项目 [GHCP API Console](https://github.com/enjoyopenfuture/ghcp-api-console) 之上，新增了「账号池」与「LiteLLM 网关」两层能力。

### 解决的三个问题

| # | 问题 | 不用本方案会怎样 | 本方案怎么解 |
|---|---|---|---|
| 1 | **额度** | 单个 Copilot 账号的 AI Credits / Premium Request 额度有上限，一个重度用户几天就能打满，打满后整条链路不可用 | 一个对外的「池名」背后挂 N 个真实账号，额度是 N 份叠加；某个账号被冷却只影响它一个，其余继续服务 |
| 2 | **并发** | 单账号的上游并发受限，多个用户同时发请求会互相排队 / 触发 429 | 请求按策略分散到池内多个账号。**注意**：并发上限随成员数增长的说法未做压测验证，实际吞吐需现场确认（见 §9） |
| 3 | **多租户** | 只有一个共享凭据，无法区分谁是谁：额度算在一起、限额没法分开设、出了问题查不到是谁调的 | LiteLLM 前置：每个租户一把虚拟 key `sk-xxx`，身份由服务端从 key 元数据解析后注入下游，使用方无法自行指定；per-key 独立的 rpm / tpm / 预算 / 并发，消费与调用明细可按 key 查 |

### 关于端口暴露的重要提醒

三个 compose 文件加起来，**publish 到宿主机的端口比你想的多**：

| 宿主机端口 | 来源文件 | 服务 | 该不该对公网开 |
|---|---|---|---|
| 80 / 443 | `deploy/docker-compose.caddy.yml` | Caddy | **是**（80 是 ACME 签证书必需） |
| 3000 | `docker-compose.yml` | Proxy | 内部服务，绑 `127.0.0.1` |
| 4000 | `docker-compose.litellm.yml` | LiteLLM | 内部服务，绑 `127.0.0.1`（Caddy 走容器网络转发；`deploy/create-key.sh` 从本机访问） |
| 7001 / 7003 / 7004 | `docker-compose.yml` | SSO / Login / Console | 内部服务，绑 `127.0.0.1`（Console 通过 `console.<PUBLIC_HOST>` 走 Caddy） |
| 22 | 系统 | SSH | 是（建议限制来源 IP） |

内部服务的宿主机绑定地址由 `.env` 的 `BIND_ADDR` 统一控制，**默认 `127.0.0.1`**。
容器之间走 Docker 内网按服务名互访，不经过宿主机端口映射。

**已实测**：`ss -tlnp` 确认仅 80/443 监听在 `0.0.0.0`，其余五个端口均在回环地址；
从外部访问 3000 / 4000 / 7004 全部超时。网络层规则是第二道防线，不是唯一一道。

## 3. 组件职责表

| 组件 | 容器内端口 | 一行职责 | 是否本次新增 |
|---|---|---|---|
| **Caddy** | 80 / 443 | 自动 TLS + 按域名分流；`api.*` 走 LiteLLM，`console.*` 走 Console | 新增 |
| **LiteLLM** | 4000 | 虚拟 key 鉴权、身份强制注入、per-key 限流与计费；对外的唯一推理入口 | 新增 |
| **PostgreSQL** | 5432 | 存 LiteLLM 的虚拟 key 与消费记录 | 新增 |
| **Redis** | 6379 | LiteLLM 的路由协调与响应缓存 | 新增 |
| **GHCP Proxy** | 3000 | 兼容 API 网关；identity → 账号（或池 → 成员）映射、Copilot token 管理、请求转发与统计 | 上游已有，**本次加了池化** |
| **SSO** | 7001 | 自建 SAML IdP + SCIM 客户端；EMU 用户开通、Copilot seat、AI Credits 查询 | 上游已有 |
| **Login** | 7003 | 发起 GitHub Device Flow，用无头 Playwright 自动完成授权，把 Copilot OAuth token 回写 Proxy | 上游已有 |
| **Console** | 7004 | Web 运维台：账号、账号池、请求统计、上游错误诊断 | 上游已有，**本次加了池视图** |

管理类 API 挂在 Proxy 的 `/api` 前缀下，由 `X-Internal-Token` 保护
（`src/proxy/src/server.ts`：`app.use('/api', requireInternalToken, adminApiRouter)` 与 `app.use('/api', requireInternalToken, poolApiRouter)`）。
推理类路由走 `app.use(requireApiKey, requireIdentityHeader, compatibleRouter)`。

### 启动顺序是链式依赖（新手最容易在这里卡住）

`docker-compose.yml` 里的 `depends_on` 是 `service_healthy` 级别，链条是：

```
sso (healthy) ─┐
               ├─► proxy (healthy) ─► console
login (healthy)┘                  └─► litellm  (还额外要求 litellm-db / litellm-redis healthy)
```

**后果**：SSO 起不来 → Proxy 起不来 → LiteLLM 和 Console 全部卡在 `Created` 状态。
而 SSO 起不来最常见的原因是**缺 SAML 证书**：`docker-compose.yml` 把 `${SSO_CERT_DIR:-./certs}` 挂到容器的 `/certs`，缺 `idp-cert.pem` / `idp-key.pem` 会 CrashLoop。

第一次部署**必须先跑**（在仓库根目录）：

```bash
bash scripts/gen-certs.sh
```

期望输出：

```
Wrote:
  /opt/ghcp-pool/certs/idp-key.pem
  /opt/ghcp-pool/certs/idp-cert.pem
```

失败时：`openssl: command not found` → `sudo apt-get install -y openssl`；权限不足 → 确认当前用户对仓库目录可写（cloud-init 已把 `/opt/ghcp-pool` 属主设为 `azureuser`）。
导入 token 模式下用这个自签证书即可，它不参与任何对外信任链。

## 4. 一次请求的完整旅程

以 Claude Code 发一条 `POST /v1/messages` 为例，逐跳说明。

| 跳 | 在哪 | 谁做了什么 | 出错时表现 / 怎么办 |
|---|---|---|---|
| ① | 客户端 | 发 HTTPS 请求到 `https://api.<PUBLIC_HOST>/v1/messages`，带 `Authorization: Bearer sk-xxx`（或 `x-api-key: sk-xxx`，两者等效）；body 里含 `model` / `messages` / `metadata.user_id` / `cache_control` | — |
| ② | Caddy :443 | 终止 TLS（证书自动签发），按 Host 匹配到 `api.*` 这条，反代到 `litellm:4000`（内网 HTTP） | 证书签不下来 → 客户端 TLS 报错。**排查顺序**：(1) NSG 是否放行 **80**（ACME HTTP-01 必需）；(2) `docker compose logs caddy` 看 ACME 报错；(3) `deploy/Caddyfile.pool` 顶部的 `email admin@example.com` 是**占位邮箱，必须改成真实邮箱**，否则 CA 侧可能拒绝签发 |
| ③ | LiteLLM 鉴权 | 拿 `sk-xxx` 去 PostgreSQL 查虚拟 key，读出它的 `metadata`、`rpm_limit`、`max_budget` 等 | 无 key / key 不存在 → **401**（已实测）。数据库不可用时**也**拒绝请求，因为 `allow_requests_on_db_unavailable: false` |
| ④ | LiteLLM hook（前半） | `trusted_identity_hook` 的 `_remove_request_identity_headers` 把 `data.headers`、`data.extra_headers`、`data.proxy_server_request.headers`、`data.metadata.headers`、`data.litellm_metadata.headers` 里**任何大小写形式**的 `X-User-Identity` 全部删掉 | 客户端伪造的身份头在这一步无声消失（已实测） |
| ⑤ | LiteLLM hook（后半） | 校验 `via_virtual_key is True`；读 `metadata.trusted_user_id`；用正则 `^[A-Za-z0-9][A-Za-z0-9._:@-]{0,127}$` 校验；通过后写入 `data["extra_headers"]["X-User-Identity"]` | 代码里两条分支分别是：非虚拟 key → **401**（`"Inference requires a LiteLLM virtual key."`）；缺 `trusted_user_id` 或格式非法 → **403**。**实测用 master key 直接推理返回 403**；实测结果落在哪条分支未确认，排障时以「非 200 即被拦住」为准 |
| ⑥ | LiteLLM 路由 | 按 `litellm/config.yaml` 的 `model_list` 匹配：`claude-*` → `anthropic/claude-*`，其余 `*` → `openai/*`；两者的 `api_base` 都是 `GHCP_PROXY_BASE_URL`（`http://proxy:3000`），`api_key` 是 `GHCP_PROXY_API_KEY`（即 `.env` 的 `API_KEY`）。`forward_client_headers_to_llm_api: false` 保证不透传客户端头 | 模型名匹配不上 → LiteLLM 返回 4xx。**可用模型清单以 `GET /v1/models` 的实际返回为准**，不要照抄示例里的模型名 |
| ⑦ | Proxy 入口 | 校验 `x-api-key`，读 `X-User-Identity`（此时值是可信的池名，如 `team-pool`） | key 不对 → 401；无身份头 → 400（`IDENTITY_HEADER_REQUIRED=true` 时） |
| ⑧ | Proxy 池判定 | `findPool(identity)` 查 `proxy_pools`，命中且 `enabled` → 走池路径；否则回落到原 1:1 路径（查 `proxy_accounts`） | 这一步是**向后兼容的分岔口**：没建池的 identity 行为与上游完全一致。⚠️ 代码里特意把池判断放在 `getAccount` **之前**，否则池名会被当成未知账号，真的去 SSO 建一个叫池名的用户 |
| ⑨ | Proxy 会话 key | `deriveSessionKey(req, body)` 按优先级算出 sessionKey（见 §5.3） | 无 body 的请求（如 `/v1/models`）落到固定兜底 key |
| ⑩ | Proxy 选成员 | `resolvePoolMember`：`sticky-affinity` 且无 `exclude` 时先查 `proxy_session_affinity` 复用绑定；否则 `selectMember` 按策略挑一个 | 全员冷却 → 抛 `PoolAllCoolingError`；池里一个成员都没有 → `PoolEmptyError`。**这两个异常最终都会以 HTTP 502 返回客户端**（见 §5.5） |
| ⑪ | Proxy 取 token | 拿被选中成员的 identity，取它的 Copilot OAuth token | 账号不存在 → 202 `account_initializing`（触发冷启动开通）；token 未就绪 → 202 / 503 `oauth_not_ready`。Playwright 失败要看 `docker compose logs login` |
| ⑫ | 上游 | `HTTPS → api.githubcopilot.com`，`Authorization: Bearer <该成员的 token>`，SSE 流式透传回来 | 上游的 HTTP 状态码**原样透传**给客户端（含 429）；上游 401 会触发该账号的 token 失效重授权 |
| ⑬ | Proxy 回程记账 | 认证解析成功后即调 `reportMemberSuccess`（清零 `consecutive_failures`、解除冷却、刷新 `last_used_at`）。`recordRequestStat` 写 `proxy_request_stats`：**`identity` 记实际成员账号，`pool_id` 记对外池名** | 统计写失败只打日志，不影响响应。⚠️ `last_used_at` 由这里刷新，`least-loaded` 的轮转完全依赖它 |
| ⑭ | LiteLLM 记账 | 按 key 累加 spend，`proxy_batch_write_at: 60` 每 60 秒批量落 PostgreSQL | 超预算 → 后续请求被 LiteLLM 拒。注意最多有 60 秒的记账延迟 |
| ⑮ | Caddy → 客户端 | 流式响应原样回传 | — |

## 5. 账号池设计

这是本次改造的核心。选择算法、多租户隔离、缓存作用域均已实测；故障转移部分有一处**代码走查与直觉不符**，见 §5.5 的醒目提示。

### 5.1 数据模型

改造只做**加法**，不动既有表：

| 变更 | 内容 |
|---|---|
| 新表 `proxy_pools` | 池定义：`pool_id`（主键）、`strategy`、`session_ttl_seconds`、`cooldown_seconds`、`failure_threshold`、`enabled`、`created_at`、`updated_at` |
| 新表 `proxy_pool_members` | 成员：主键 `(pool_id, identity)`，含 `weight`、`state`、`cooling_until`、`consecutive_failures`、`last_used_at` |
| 新表 `proxy_session_affinity` | 会话绑定：主键 `(session_key, pool_id)`，含 `identity`、`expires_at`、`last_used_at` |
| 改列 | `proxy_request_stats` 增加 `pool_id` 列 |

> 新增的是 **3 张表 + 1 个列**。
> `proxy_accounts` 表**一个字段都没改**。这意味着：只要不建池，1:1 模式的行为与上游项目完全一致，随时可以回退。
> `proxy_pool_members.identity` 逻辑上指向 `proxy_accounts.identity`，但**没有外键约束** —— 加成员时账号不存在不会报错，要靠 `provision.sh` 第 3 步的账号状态输出自己核对。

**这些表存在哪**：默认 `STORAGE_DRIVER=sqlite`，库文件是容器内 `/data/proxy.sqlite`，落在 Docker 卷 `proxy-data` 上。仓库里另有 MySQL 驱动（`docker-compose.mysql.yml` + `upgrade/sqlite-to-mysql`），**本方案未使用、未验证**。

### 5.2 三种策略对比

| 策略 | 怎么选 | 会话绑定 | 负载分布 | 适用场景 |
|---|---|---|---|---|
| **`least-loaded`**（默认） | 每次挑 `last_used_at` 最久远的可用成员（从未用过的排最前） | **不写、不读**绑定 | 最均匀 | **多租户共用一个池的默认选择**。因为缓存跨账号共享（§6），均匀分摊不损失缓存 |
| `sticky-affinity` | 先查会话绑定；无绑定则用 Rendezvous 哈希确定性地选一个，并写入绑定（TTL 内每次访问续期） | 读 + 写 | 由哈希决定，离线仿真变异系数 10.4% | ① 需要按会话审计追溯到固定账号；② 客户端用了 `/responses` 的 `previous_response_id` 这类**有状态**接口 |
| `round-robin` | 对 sessionKey 做 sha256，取前 4 字节对可用成员数取模（成员先按 `identity` 排序） | 不写、不读 | 按会话哈希均分 | 需要确定性分配、又不想引入亲和表时 |

关键实现细节：**只有 `sticky-affinity` 会读写亲和表**（`poolResolver.ts`）。如果 `least-loaded` / `round-robin` 也无条件复用绑定，它们第一次分配后就退化成粘性了 —— 等于没分摊。

> ⚠️ **源码注释是过时的，读代码时不要被带偏。** 改造过程中默认策略从 `sticky-affinity` 改成了 `least-loaded`，但下面这几处注释没有同步更新：
>
> | 文件 | 过时的说法 | 实际情况 |
> |---|---|---|
> | `src/proxy/src/pool/poolTypes.ts` 顶部 | 「分散发生在会话粒度而非请求粒度」「逐请求轮询总成本不降反升」 | 前提（缓存按账号隔离）已被 §6 的实测推翻 |
> | `src/proxy/src/pool/poolTypes.ts` 策略注释 | `sticky-affinity`「默认」、`least-loaded`「缓存不友好，仅用于对照测试」 | 反了 |
> | `src/proxy/src/pool/poolSelector.ts` 顶部 | 「三级策略（sticky-affinity，默认）」 | 同上 |
> | `src/proxy/src/pool/sessionKey.ts` 顶部 | 「Anthropic 的 prompt 缓存是**按账号隔离**的」 | 实测是按**组织**隔离，跨 Copilot 账号共享 |
>
> **以同文件末尾的 `POOL_DEFAULTS.strategy = 'least-loaded'` 为准**，那才是运行时真正生效的默认值。

### 5.3 会话 key 怎么来

`deriveSessionKey()` 按优先级从强到弱（`src/proxy/src/pool/sessionKey.ts`）：

| 优先级 | 来源 | `origin` 标记 | 说明 |
|---|---|---|---|
| 1 | 请求头 `X-Session-Id` | `header` | 客户端主动控制，最强 |
| 2 | body 的 `metadata.user_id` | `metadata` | Anthropic Messages API 字段，Claude Code 会填 |
| 3 | `system` + 首条 `user` message 的**前 4096 字节**的 sha256 | `prompt-prefix` | 无需客户端任何配合。兼容 Anthropic 形状（顶层 `system` + `messages[]`）和 OpenAI Responses 形状（`instructions` / `input`） |
| 4 | 固定兜底值 | `fallback` | 无 body 的请求（如 `/v1/models`）稳定落到同一账号，避免无谓打散 |

为什么第 3 条只取**前缀**而不是全文：缓存本身就是前缀匹配的。对话越往后差异越大，但前缀（系统提示词 + 代码上下文）是稳定的。取太长会让无关的尾部变化打散分配，取太短会误合并不同会话。

补充一条实现细节：`/v1/messages/count_tokens` 与正式请求**共用同一个会话 key**，确保二者落到同一成员。

> 注意：默认策略 `least-loaded` **根本不读 sessionKey**。上面这套推导只在 `sticky-affinity` / `round-robin` 下才影响选择结果。

### 5.4 为什么用 Rendezvous（HRW）哈希

`sticky-affinity` 新会话的放置用 Rendezvous 哈希：对每个成员算 `score = -weight / ln(unit)`，其中 `unit` 来自 `sha256(sessionKey + " " + identity)` 前 6 字节归一化到 `[0,1)`，取 score 最大者。

选它而不是普通一致性哈希的理由，以及**实测数据**：

| 性质 | 实测结果 |
|---|---|
| **确定性/粘性** | 同一 sessionKey 重复选择 20 次结果完全一致 |
| **分布均匀** | 10000 会话 / 100 账号，变异系数 **10.4%** |
| **最小扰动**（最重要） | 移除 1 个账号只重映射 **1.0%** 的会话，且**不波及无关会话**（「本不该动却动了」的数量为 0） |
| **权重支持** | 权重 8:1:1 实测分配为 **80.4% / 9.4% / 10.2%**（理论 80/10/10） |

第三条是选它的决定性理由：加减一个账号，只有本来就属于那个账号的会话被重新分配，其余会话的绑定纹丝不动。一致性哈希要靠维护虚拟节点环才能接近这个效果，Rendezvous 天然具备，且权重是公式里的一个参数，不需要额外数据结构。

**数据来源与限制**：上述数字来自 `tests/selector-check.cjs` —— 它是与 `poolSelector.ts` 同算法的**独立离线实现**，跑的是仿真会话，不是真实流量。复现方式（任何装了 Node 的机器都能跑，不需要部署环境）：

```bash
node tests/selector-check.cjs
```

期望输出：四行 `【性质N】… → ✅` 的结论行，含上表中的数字。
失败时：`node: command not found` → 装 Node 20+；数字与上表有出入 → 说明算法被改过，**不要修改文档里的数字，去查 `poolSelector.ts` 的改动**。

### 5.5 故障转移怎么触发

设计意图（`poolResolver.ts` / `compatible.ts` 的 `notePoolFailure`）：

```
上游返回错误
     │
     ├─ CopilotApiError 且 status ∈ {429, 402}
     │        └─► reportMemberFailure(..., { forceCooldown: true })
     │            → 该成员**立刻**进入 cooling，cooling_until = now + cooldown_seconds
     │              （不必攒够 failureThreshold —— 限流信号本身就足够明确）
     │
     └─ 其余错误
              └─► consecutive_failures += 1
                  → 达到 failureThreshold 才进入 cooling

冷却恢复：无后台任务。isMemberAvailable() 在选择时实时比较
          cooling_until <= now，到期即自动视为可用。

成功一次：markMemberSuccess 清零 consecutive_failures、解除冷却、刷新 last_used_at。

全员冷却：selectMember 返回 { kind: 'all-cooling' }，
          resolver 抛 PoolAllCoolingError(poolId, retryAfterSeconds)。
```

> 🔴 **代码走查结论：实际生效范围比上面这张图窄，上线前必须现场确认。**
>
> | 走查发现 | 依据 | 影响 |
> |---|---|---|
> | `notePoolFailure` **只有一个调用点**，在 `assertModelSupportsPath` 的 catch 里（`src/proxy/src/routes/compatible.ts:287`） | 全仓库 grep 只此一处 | 只有「取模型清单」这一步失败才会回报给池 |
> | `CopilotApiError` **只在两处抛出**，都在 `listModels`（`src/proxy/src/copilot/copilotClient.ts:100/103`） | 同上 | 「429/402 立即冷却」实际只覆盖**模型清单调用**返回 429/402 的情况 |
> | 模型清单有**每账号 1 小时**的本地缓存（`MODELS_CACHE_TTL_MS = 60 * 60 * 1000`） | `copilotClient.ts` | 上面那条路径每小时最多触发一次 |
> | 推理请求本身的上游状态码是**原样透传**的（`pipeAndRecord` 里 `res.status(upstream.status)`），不抛异常 | `compatible.ts:312` | 上游推理返回 429 时，客户端收到 429，但**该成员不会被冷却** |
> | `reportMemberSuccess` 在**转发之前**就被调用（`compatible.ts:157/207`，位置在 `pipeAndRecord` 之前） | 同上 | 即使这次请求上游返回 429，失败计数也已被清零 |
> | `resolvePoolMember` 的 `exclude` 参数**没有任何调用方传值**（`copilotAuthManager.getAuth` 只传 `sessionKey`） | `compatible.ts:278` | **没有「同一次请求内换成员重试」**。转移发生在**下一次请求**，前提是该成员已被标记冷却 |
> | `PoolAllCoolingError` / `PoolEmptyError` 未被任何地方捕获转换 | `proxyErrorStatus()` 只特判 `CopilotModelPathError` 和 401/403，其余一律 **502** | 客户端看到的是 **HTTP 502**，消息体是 `All members of pool "<池名>" are cooling down.`；`retryAfterSeconds` 只存在于异常对象里，**没有写进 `Retry-After` 响应头** |
>
> **怎么现场确认**：把某个成员的 `state` 手动置为 `disabled`（`DELETE`/`PATCH` 成员接口，见《账号池运维》），观察后续请求是否全部落到其余成员；再把池里所有成员都停掉，发一个请求，看返回码是不是 502、消息体是不是上面那句。**确认结果与本表不符时，以现场为准并回来修订本节。**

`sticky-affinity` 下，如果绑定的成员已不可用（冷却或被移除），会先 `clearSessionAffinity` 丢弃旧绑定再重新选，并打一条 `affinity-rebind` 日志。

默认值（`POOL_DEFAULTS`）：`sessionTtlSeconds = 1800`（30 分钟，够覆盖一次连续的 Claude Code 会话）、`cooldownSeconds = 300`（5 分钟，与 Copilot 侧常见限流窗口相当）、`failureThreshold = 3`、`weight = 1`。`deploy/provision.sh` 建池时显式传的就是这几个值。

### 5.6 统计归因

`proxy_request_stats` 每行记：`identity` = **实际承接请求的成员账号**，`pool_id` = **对外的池名**。这样两个问题都能回答：

- 「`team-pool` 这个租户这个月用了多少？」 → 按 `pool_id` 聚合
- 「`demo01` 这个账号快到额度上限了吗？」 → 按 `identity` 聚合

记录的字段是路径、模型、成功与否、input token 数、失败原因 —— **不留存 prompt 正文**。需要全量内容审计的场景要另行建设。

> ⚠️ **保留条数默认极小，不改就没法对账。** `docker-compose.yml` 里 `REQUEST_STATS_PER_ACCOUNT_LIMIT` 的默认值是 **2**（`src/proxy/src/config.ts` 的兜底值也是 2），写入时会按 `identity` 分区、只保留最新的 N 条，其余直接删除。
> `.env.example` 里给的是 `REQUEST_STATS_PER_ACCOUNT_LIMIT=200` —— **一定要确保 `.env` 里有这一行**，否则每个账号只剩最近 2 条记录。
> 确认方法：`docker compose exec proxy printenv REQUEST_STATS_PER_ACCOUNT_LIMIT`，期望输出 `200`（或你设的值）。输出 `2` 或为空 → 改 `.env` 后 `docker compose up -d proxy` 重建容器。
> 需要长期留存请自行导出到外部存储，本方案未提供。

## 6. 反直觉结论：prompt 缓存跨 GHCP 账号共享

这是本方案最重要的技术发现，也是「默认用 `least-loaded`」这个决定的唯一依据。

### 6.1 直觉说什么

Anthropic 官方的 prompt 缓存是按组织隔离的。既然每个 Copilot 账号是不同的 GitHub 账号，很自然会认为：**换账号 = 缓存失效**。按这个假设，池化必须用粘性策略，否则每次换账号都要重新写一遍缓存（cache_write 比未命中的普通 input 还贵），成本不降反升。改造初期的代码注释就是按这个假设写的（§5.2 已列出这些过时注释）。

### 6.2 实测推翻了它

| 步骤 | 账号 | 观测值 |
|---|---|---|
| 1 | `demo01` | 发一个带 `cache_control: {"type":"ephemeral"}` 的长 prompt，写入缓存 **2000 token** |
| 2 | `demo02` | 发**完全相同**的请求 → `cache_read_input_tokens = 1716`，**直接命中** |

对应的测试脚本是 `tests/cache-scope.mts`（作用域实验）与 `tests/cache-final.mts`（命中实测）。这两个脚本需要 `POOL_API_KEY` / `POOL_INTERNAL` 环境变量，并直连一个已部署环境，**不是离线可跑的**，复现方式见《账号池运维》。

### 6.3 原因

从响应的 thinking 块签名里解出的 Anthropic 组织 ID 是：

```
ced1f98e-0b51-4610-8282-4e5d88384574
```

两个账号解出的是同一个值 —— **所有 GitHub Copilot 账号共用这同一个 Anthropic 组织**。缓存的作用域是「组织」，不是「GitHub 账号」。所以从 Anthropic 的视角看，`demo01` 和 `demo02` 根本就是同一个租户。

### 6.4 推论

> **按负载均匀分摊不会损失缓存。**

这直接决定了默认策略是 `least-loaded` 而不是 `sticky-affinity` —— 既然缓存不因换账号而失效，就应该选负载最均匀的那个策略。

### 6.5 前提条件与限制（必须说清楚）

| 条目 | 说明 |
|---|---|
| 触发条件 | 客户端必须显式声明 `cache_control: {"type":"ephemeral"}`，且内容超过约 **1024 token** 才会缓存。Claude Code 自带该字段 |
| 自研客户端 | 如果你的应用不发 `cache_control`，那就根本没有缓存可谈，本节结论对你不产生影响 |
| 样本量 | 结论来自 **2 个账号**的对照实验，不是大规模统计 |
| **这是 GitHub 侧的实现细节** | 不是 Anthropic 或 GitHub 的公开承诺。GitHub 完全可能在未来改成按账号隔离 |
| 怎么监控 | 观察响应里的 `cache_read_input_tokens`。如果哪天在跨账号场景下持续为 0，说明隔离策略变了 |
| 怎么应对 | 把池策略切回 `sticky-affinity` 即可（`PATCH /api/pools/<池名>`，body `{"strategy":"sticky-affinity"}`），无需改代码、无需重启 |

## 7. 安全边界

### 7.1 为什么 Proxy 绝不能直接暴露公网

**实测结论**：用同一个 `API_KEY`，分别把 `X-User-Identity` 设成 `team-pool` / `demo01` / `demo02` 三种身份发请求，**三次全部返回 200**。

Proxy 作为内部服务，接受来自 LiteLLM 的身份声明——这是分层架构里的常规分工，
认证在网关层完成，后端服务不重复做一遍。对应到部署上有三层保证：

- **凭据分离**：`API_KEY` 只配给 LiteLLM 使用，最终用户拿到的是虚拟 key。两者用途不同，不要混用。
- **路由隔离**：Caddy 只反代 `litellm:4000` 和 `console:7004`，`deploy/Caddyfile.pool` 里没有任何指向 3000 的路由。
- **绑定收敛**：Proxy 的 3000 端口绑在 `127.0.0.1`，只有服务器本机可达（已实测）。

网络层规则（只放行 22/80/443）是第四层，作为纵深防御，而非唯一依赖。

**自查命令**（在你自己的笔记本上跑，不是在 VM 上）：

```bash
curl -s -m 5 -o /dev/null -w '%{http_code}\n' http://<VM公网IP>:3000/healthz
```

| 输出 | 含义 | 怎么办 |
|---|---|---|
| 超时 / `000` | 端口没通，NSG 生效中 | 这是**期望结果** |
| `200` | **Proxy 已暴露公网** | 立刻检查 NSG：网卡 NSG → **子网 NSG** → 是否有新挂上来的零规则子网 NSG（见《已知的坑》） |

（在中国区通过代理软件访问时，超时也可能是代理造成的假象。判定「端口确实被挡住」应以 Azure 门户/CLI 上的 NSG 规则为准。）

### 7.2 LiteLLM 的 hook 做了什么

`litellm/trusted_identity_hook.py` 是 fail-closed 设计的 `async_pre_call_hook`，按顺序做四件事：

| 顺序 | 动作 | 失败时 |
|---|---|---|
| 1 | **先删后写**：把请求里所有位置（`headers` / `extra_headers` / `proxy_server_request.headers` / `metadata.headers` / `litellm_metadata.headers`）的 `X-User-Identity` 全部删掉，大小写不敏感 | 无声删除，不报错 |
| 2 | 断言 `user_api_key_dict.via_virtual_key is True` | 抛 **401** `"Inference requires a LiteLLM virtual key."` |
| 3 | 从 key 的 `metadata.trusted_user_id` 读身份 | 缺失或非字符串 → **403** `"Virtual key is missing trusted identity metadata."` |
| 4 | 正则校验 `^[A-Za-z0-9][A-Za-z0-9._:@-]{0,127}$`，通过后写入 `extra_headers["X-User-Identity"]` | 格式非法 → **403**；`extra_headers` 不是对象 → 400 |

配套的两条配置同样是安全边界的一部分：`general_settings.forward_client_headers_to_llm_api: false`（不透传客户端头）和 `general_settings.allow_requests_on_db_unavailable: false`（数据库不可用时拒绝请求，而不是放行）。

**实测验证结果**：

| 场景 | 结果 |
|---|---|
| 不带任何 key 调用 | **401** |
| 用 master key 直接推理 | **403**（hook 强制要求虚拟 key。落在上表第 2 步还是第 3 步未确认，不影响结论：被拦住了） |
| 带虚拟 key + 伪造的 `X-User-Identity: demo02` | 伪造的头被剥掉，**仍按 key 元数据里的身份**走池分配 |
| 端到端 | 虚拟 key → 注入 `team-pool` → 池分配 → `demo01`/`demo02` 轮流承接；`proxy_request_stats` 中 `identity` 为实际账号、`pool_id` 为 `team-pool` |

对应脚本 `tests/verify-litellm.mts`。⚠️ 它的 `API_BASE` **默认写死为演示环境的 `https://api.20.78.139.35.nip.io`**，在你自己的环境里跑之前必须覆盖：

```bash
API_BASE="https://api.<PUBLIC_HOST>" LITELLM_MASTER_KEY="<LITELLM_MASTER_KEY>" \
  npx tsx tests/verify-litellm.mts
```

失败时先确认这两个环境变量是否真的传进去了 —— 忘记设 `API_BASE` 会让脚本去打别人的环境，症状是全部超时或 4xx。

### 7.3 四层凭据不要搞混

| 凭据 | 谁持有 | 作用 | 放在哪 |
|---|---|---|---|
| `sk-xxx` 虚拟 key | **最终用户 / 租户** | 唯一发给外部的东西；由 `deploy/create-key.sh` 生成，**只在创建时显示一次** | 用户自己保管 |
| `<API_KEY>` | 只有 LiteLLM 容器（经 `GHCP_PROXY_API_KEY`） | LiteLLM → Proxy 的服务间凭据。**绝不能外发** | `.env` |
| `<INTERNAL_API_TOKEN>` | 运维人员 / Console / SSO / Login | Proxy 的 `/api` 管理接口（建池、加成员、导账号） | `.env` |
| `<LITELLM_MASTER_KEY>` | 运维人员 | 只能建 key / 查账，**不能直接推理**（被 hook 挡住，实测 403） | `.env` |

### 7.4 建 key 时的护栏

`litellm/config.yaml` 的 `upperbound_key_generate_params` 给虚拟 key 的参数设了上限；`deploy/create-key.sh` 的默认值远低于上限：

| 参数 | `create-key.sh` 默认值 | 配置允许的上限 |
|---|---|---|
| `duration` | 90d | 90d |
| `max_budget`（美元） | 100 | 500 |
| `budget_duration` | 30d | 30d |
| `rpm_limit` | 60 | 600 |
| `tpm_limit` | 200000 | 1000000 |
| `max_parallel_requests` | 5 | 20 |

> 超过上限建 key 会被 LiteLLM 拒绝。要放宽得改 `config.yaml` 并重启 LiteLLM 容器。
> `create-key.sh` 传的 `"models": []` 表示不限制模型（LiteLLM 语义），**是否等价于「全部放行」需现场确认**。

## 8. 与上游开源项目的差异清单

上游 [GHCP API Console](https://github.com/enjoyopenfuture/ghcp-api-console) 解决的是「批量拿到并自动维护 N 个 GitHub 账号」的问题，身份到账号是 **1:1** 的，且假定调用方是可信内网。本方案的差异：

| # | 维度 | 上游 | 本方案 |
|---|---|---|---|
| 1 | 身份 → 账号 | 1:1 固定映射 | 1:1 **或** 1:N（池），按 identity 是否命中 `proxy_pools` 分岔 |
| 2 | 数据库 | `proxy_accounts` / `proxy_request_stats` 等 | **新增** `proxy_pools`、`proxy_pool_members`、`proxy_session_affinity`；`proxy_request_stats` 加 `pool_id` 列。`proxy_accounts` 未改动 |
| 3 | 选择算法 | 无（只有一个账号） | **新增** `src/proxy/src/pool/`：Rendezvous 哈希 + 三种策略 |
| 4 | 会话概念 | 无 | **新增** `sessionKey.ts` 四级推导 |
| 5 | 故障处理 | 单账号失败即失败 | **新增** 冷却 / 失败计数 / 自动恢复（实际触发范围见 §5.5 的走查提示） |
| 6 | 对外入口 | Proxy 直出，身份靠可信内网假设 | **新增** LiteLLM 层：虚拟 key + `trusted_identity_hook` + per-key 限流计费 |
| 7 | TLS / 域名 | 自行处理 | **新增** Caddy 自动 TLS + 双域名分流（`api.*` / `console.*`） |
| 8 | 管理 API | 账号 CRUD | **新增** `GET/POST /api/pools`、`GET/PATCH/DELETE /api/pools/:poolId`、`GET/POST /api/pools/:poolId/members`、`DELETE /api/pools/:poolId/members/:identity`、`POST /api/pools/:poolId/members/:identity/resume`、`POST /api/pools/maintenance/prune-sessions` |
| 9 | 部署产物 | 通用 compose | **新增** `deploy/`（cloud-init、Caddyfile.pool、compose 叠加层、provision.sh、create-key.sh、pool-bridge.mjs） |
| 10 | 测试 | — | **新增** `tests/`：选择算法性质、本地 E2E、云上验证、LiteLLM 隔离、缓存作用域实验 |
| 11 | 兼容性 | — | 不建池时行为与上游**完全一致**，可整体回退 |

## 9. 本方案**不适用**的场景

按诚实优先的原则列出。这些不是「待办事项」，是当前的真实边界。

| 场景 | 为什么不适用 |
|---|---|
| **需要合同级 SLA 的生产系统** | GitHub Copilot 不提供面向第三方服务端集成的公开裸 API。本方案依赖内部接口，上游随时可能变更或封禁。上游项目 README 本身就写明「用于生产前必须自行评估合规、稳定性和运维风险」 |
| **需要「一个最终用户 = 一个 GitHub 账号」的合规姿态** | 池化的本质就是把 N 个用户映射到 M 个账号，与上游项目「不应共享账号」的合规主张**方向相反**。如果客户的合规要求是 1:1，那就别建池 —— 系统支持不建池 |
| **合规 / 法务判断** | 本文档不构成任何合规意见。账号聚合、额度合池是否符合 GitHub Copilot 服务条款，**必须由客户自己的法务判断**。技术上跑得通不等于允许这么用 |
| **需要 Anthropic 原生全部能力** | 只能用 Copilot 后端暴露的模型和参数。Batch API、Files API、原生 PDF 输入、citations 等能力**未验证**，大概率不支持（代码里 `/v1/files` 是直接返回 404 + 不支持说明的） |
| **有状态接口 + 默认策略** | `/responses` 的 `previous_response_id` 依赖同一账号。默认的 `least-loaded` 每次重新分配，会打断状态。用这类接口**必须**把池策略切成 `sticky-affinity` |
| **依赖「上游 429 自动切号」** | 见 §5.5 的走查提示：推理请求本身返回 429 时，当前代码不会冷却该成员。**部署后必须现场确认**，确认前不要把「自动容错」写进给客户的承诺里 |
| **高可用** | 单台 VM + docker-compose，无冗余。VM 挂了整条链路全挂。PostgreSQL / Redis / SQLite 均无内置备份策略（数据在 Docker 卷里，删卷即丢） |
| **高吞吐 / 大规模** | 部署规格是 Standard_D2s_v5（2 vCPU）。实测规模是 **2 个账号**，选择算法的 100 账号数据来自离线仿真而非真实流量。**未做压测**，实际吞吐上限需现场确认 |
| **跨区域 / 低延迟** | 单区域单实例，无就近接入 |
| **拿 LiteLLM 的金额去对 GitHub 账单** | LiteLLM 的 spend 是按它自己的模型价格表估算的美元金额，与 GitHub 侧的 AI Credits / Premium Request 计量是**两套完全不同的口径**。对账口径需现场确认 |
| **需要全量内容审计** | `proxy_request_stats` 只记路径、模型、成败、token 数、失败原因，**不留存 prompt 正文**，而且默认只保留每账号最近 N 条（见 §5.6）。要留存需另行建设，并同步评估数据合规 |
| **中国大陆长期稳定运行** | 从大陆访问 Azure 与 `api.githubcopilot.com` 的长期稳定性**未做长时间验证**。且中国区常见代理软件的 Fake-IP DNS 会带来额外排障复杂度（详见《已知的坑》） |

### 10.2 启动命令（三层 compose 是叠加关系）

**前置检查**（缺一不可，全部在仓库根目录执行）：

```bash
cd /opt/ghcp-pool
test -f .env && echo "OK: .env 存在" || echo "缺 .env：cp .env.example .env 后填写"
test -f certs/idp-cert.pem && echo "OK: 证书存在" || echo "缺证书：bash scripts/gen-certs.sh"
```

**启动**：

```bash
cd /opt/ghcp-pool
docker compose -f docker-compose.yml \
               -f docker-compose.litellm.yml \
               -f deploy/docker-compose.caddy.yml up -d --build
```

> ⚠️ **注意第三个 `-f` 的路径带 `deploy/` 前缀** —— `docker-compose.caddy.yml` 在 `deploy/` 目录下，不在仓库根目录。文件内注释里写的是三个同级文件的用法，那是按「把它们放在同一目录」的假设写的，直接照抄会报 `no such file`。

> 🔴 **由此引出的一个真实陷阱（部署前必须处理）**：Docker Compose 用**第一个 `-f` 文件所在的目录**作为项目目录，`deploy/docker-compose.caddy.yml` 里的 `./Caddyfile.pool` 会被解析成 **`/opt/ghcp-pool/Caddyfile.pool`**（根目录），而这个文件实际在 `deploy/` 下。挂载源不存在时 Docker 会**创建一个同名目录**并挂进去，Caddy 随即起不来。
>
> **先验证再启动**：
>
> ```bash
> docker compose -f docker-compose.yml -f docker-compose.litellm.yml \
>                -f deploy/docker-compose.caddy.yml config | grep -A2 'Caddyfile'
> ```
>
> 看解析出来的 `source:` 绝对路径。如果它指向 `/opt/ghcp-pool/Caddyfile.pool`（根目录）而该文件不存在，二选一：
>
> ```bash
> # 方案 A（改动最小）：把 Caddyfile 复制到根目录
> cp deploy/Caddyfile.pool ./Caddyfile.pool
>
> # 方案 B：改 deploy/docker-compose.caddy.yml，把 ./Caddyfile.pool 改成 ./deploy/Caddyfile.pool
> ```
>
> 无论选哪种，**改完 `Caddyfile.pool` 里的 `email` 之后要改的是你实际挂载的那一份**，别改错文件。选定后请在《部署手册》里固化，避免两份文件长期不同步。

**期望输出**：一串 `Container ghcp-pool-xxx-1  Started`，无 `error` 字样。

**失败时对照**：

| 报错片段 | 原因 | 怎么办 |
|---|---|---|
| `set PUBLIC_HOST` / `set API_KEY` / `set LITELLM_MASTER_KEY` 等 | `.env` 缺项或没在项目目录 | 确认在 `/opt/ghcp-pool` 下执行，且 `.env` 里该变量已填 |
| `no such file or directory ... docker-compose.caddy.yml` | 少写了 `deploy/` 前缀 | 用上面的完整命令 |
| `dependency failed to start: container ... is unhealthy`（sso） | 缺 SAML 证书 | `bash scripts/gen-certs.sh` 后重跑 |
| `permission denied while trying to connect to the Docker daemon` | 当前用户不在 docker 组 | `sudo usermod -aG docker $USER` 后**重新登录 SSH**（cloud-init 已加过 azureuser，但需要重新登录才生效） |

**启动后自检**：

```bash
# 1. 所有容器都在跑
docker compose -f docker-compose.yml -f docker-compose.litellm.yml \
               -f deploy/docker-compose.caddy.yml ps
# 期望：sso/login/proxy/console/litellm/litellm-db/litellm-redis/caddy 均为 running 或 healthy

# 2. Proxy 活着（VM 本机）
curl -s -o /dev/null -w '%{http_code}\n' http://127.0.0.1:3000/healthz     # 期望 200

# 3. LiteLLM 活着（VM 本机）
curl -s -o /dev/null -w '%{http_code}\n' http://127.0.0.1:4000/health/liveliness   # 期望 200

# 4. TLS + 路由 + 鉴权全链路（可以在任意能上网的机器跑）
curl -s -o /dev/null -w '%{http_code}\n' -X POST https://api.<PUBLIC_HOST>/v1/messages \
  -H 'content-type: application/json' \
  -d '{"model":"x","max_tokens":16,"messages":[{"role":"user","content":"hi"}]}'
# 期望 401 —— 401 才是对的：说明证书签下来了、Caddy 路由对了、LiteLLM 在拦无 key 请求。
# 这一步在鉴权阶段就返回，所以 model 填什么都无所谓。
```

第 4 步返回 000/超时时的排查顺序（细节见《已知的坑》）：
**网卡 NSG → 子网 NSG → VM 电源状态 → 数据库/容器状态**。
子网 NSG 这层最容易漏 —— 订阅策略会**新建一个零规则的子网 NSG 挂到 VNet 上**，而新建资源天生没有 `CostControl=Ignore` / `SecurityControl=Ignore` 标签，打标签挡不住这一种。
另外：中国区代理软件的 Fake-IP DNS 是**必需**的（流量要走隧道），**不要改 hosts 文件**去强解真实 IP，那样反而连不上；浏览器打不开时先怀疑 NSG 被清了。
