# 账号批量接入指南

> 适用范围：本文只讲「怎么把 GitHub Copilot 账号弄进池子」。VM 创建、docker-compose 起栈、Caddy/LiteLLM 配置见 `docs-pool/` 里的部署篇。
>
> 本文的前置条件：`docker compose ps` 里 sso / login / proxy / console 四个容器都是 `healthy`（下面 §1.1 有确认命令）。
>
> 本文所有接口字段、错误码、默认值都对着仓库源码核对过，源码位置在表格里给出；凡是**只做过源码走查、没在真机上触发过**的结论，都单独标了「未实测」。

## 0. 两条路线怎么选

| | 路线 A：导入已有 OAuth token | 路线 B：完整自动化（SSO + SCIM + Device Flow） |
|---|---|---|
| 前提 | 已经拿到 `gho_` 开头的 Copilot OAuth token | 客户有 GitHub EMU 企业 + SCIM token + SAML 配置 + 空余席位 |
| 谁来建账号 | 你手工准备账号清单 | 系统自动建号、推 SCIM、分席位、跑授权 |
| 单账号耗时 | 秒级（只做一次 `/models` 校验） | 约 1 分钟（Playwright 无头浏览器跑完整登录授权） |
| 本环境验证情况 | **已实测通过**（demo01 / demo02 两个账号，端到端 200） | **未在本环境验证**——顾问侧没有 EMU 企业。本文只写原理和客户需要做什么 |
| 典型场景 | POC、演示、从别的环境迁移账号 | 客户正式环境、需要长期自动续期 |
| 主要局限 | token 有有效期，过期要重新授权（本方案未测出具体有效期，见 §3.8） | 依赖客户企业侧配置，链路长、失败点多 |

**建议**：先用路线 A 把池子跑通、把演示做完；等客户愿意开 EMU 权限时再上路线 B。两条路线产出的账号在池子里没有任何区别——池只认 `proxy_accounts.identity`。

## 1. 开始之前：约定与准备

### 1.1 在哪台机器上执行

本文所有管理类命令都在**服务器本机、通过 `127.0.0.1` 执行**。

原因很简单：Proxy 和 LiteLLM 的端口默认绑定在 `127.0.0.1`（由 `.env` 的 `BIND_ADDR` 控制），本来就只有本机能连。对外只有 Caddy 的 `api.<域名>`（→ LiteLLM）和 `console.<域名>`（→ Console）。

账号导入、建池这类管理接口属于内部管理面，在本机调用即可，无需对外开放。

```bash
ssh -i <你的私钥路径> azureuser@<VM 公网 IP>
```

| 占位符 | 怎么取值 |
|---|---|
| `<你的私钥路径>` | 创建 VM 时保存的私钥。本次联调用的是仓库根目录的 `pool_vm_key`（**这是联调残留物，正式环境请自己生成密钥，不要复用、不要进 git**） |
| `<VM 公网 IP>` | Azure 门户该 VM 的「公共 IP 地址」，或 `az vm list-ip-addresses -g <资源组> -n <VM名> -o tsv` |

登上去先确认栈是好的：

```bash
cd /opt/ghcp-pool && docker compose ps
```

期望输出：`sso` / `login` / `proxy` / `console` 四行，`STATUS` 列都是 `Up ... (healthy)`。

- 某个容器是 `Restarting` → 看 `docker compose logs --tail=80 <服务名>`。`sso` 反复重启多半是缺 SAML 证书，见 §3.7 末尾。
- 提示 `no configuration file provided` → 你不在 `/opt/ghcp-pool`，或这台机器上的部署目录不是这个路径，需现场确认。

**SSH 连不上 / 浏览器打不开时**，按这个顺序排查（顺序不能乱，子网 NSG 这层最容易漏）：

| 顺序 | 检查项 | 说明 |
|---|---|---|
| 1 | 网卡 NSG | 自定义规则可能被订阅策略清空 |
| 2 | **子网 NSG** | 策略可能**新建**一个零规则的 NSG 挂到 VNet 上。新建资源天生没有 `SecurityControl=Ignore` 标签，标签挡不住这一种 |
| 3 | VM 电源状态 | 策略会停 VM / 数据库实例 |
| 4 | 数据库状态 | 同上 |

两层 NSG 是独立的，**缺一不可**，都要放行。另外：中国区代理软件的 Fake-IP DNS（把域名解析成 `6.6.4.243` 这类假 IP）是**必需的**，流量要走隧道；**不要改 hosts 文件强制解析到真实 IP，改了反而连不上**。浏览器打不开先怀疑 NSG，不要怀疑 DNS。

### 1.2 会话准备（后面每个命令都依赖这一步）

```bash
cd /opt/ghcp-pool
set -a; . ./.env; set +a
echo "INTERNAL_API_TOKEN 长度=${#INTERNAL_API_TOKEN}  API_KEY 长度=${#API_KEY}"
```

期望输出：两个长度都 **大于 0**。

失败时：

| 现象 | 原因 / 怎么办 |
|---|---|
| `bash: ./.env: No such file or directory` | 仓库里的模板叫 `.env.pool`，VM 上那份叫什么**需现场确认**（`ls -a /opt/ghcp-pool` 看一眼）。`deploy/provision.sh` 读的是 `./.env`，建议 `cp .env.pool .env` 统一成 `.env`，省得后面每条命令都要改 |
| 长度为 0 | 环境文件里没有这两行。`API_KEY` 和 `INTERNAL_API_TOKEN` 在 `docker-compose.yml` 里写成 `${API_KEY:?...}` 的必填形式，栈能起来就说明文件里一定有，多半是你 `cd` 错目录了 |
| 长度比你贴进去的值多 1 | 环境文件是 CRLF 换行，值尾部带了 `\r`，后面所有请求都会 401。`sed -i 's/\r$//' /opt/ghcp-pool/.env` 后重跑本节 |

### 1.3 端口、接口归属与认证头

| 服务 | VM 内地址 | 认证头 | 本文用到的接口 |
|---|---|---|---|
| SSO | `http://127.0.0.1:7001` | `X-Internal-Token` | `POST /api/users`、`POST /api/users/import`、`GET /api/users/:ssoUser`、`GET /api/users/capacity` |
| Proxy 管理面 | `http://127.0.0.1:3000/api/*`、`/internal/*` | **只要 `X-Internal-Token`** | `POST /api/accounts/copilot-oauth-token/import`、`GET /api/accounts`、`GET /api/request-stats`、`POST /api/pools*` |
| Proxy 推理面 | `http://127.0.0.1:3000/v1/*`、`/chat/completions`、`/responses` | `x-api-key`（或 `Authorization: Bearer`）+ `X-User-Identity` | `POST /v1/messages`、`GET /v1/models` |
| Login | `http://127.0.0.1:7003` | `X-Internal-Token` | `GET /api/tasks`（路线 B 才用到） |
| Console | `http://127.0.0.1:7004` | 浏览器登录态 | 图形界面，见 §6 |

认证边界来自 `src/proxy/src/server.ts`：`/api` 与 `/internal` 挂 `requireInternalToken`，其余路径才挂 `requireApiKey` + `requireIdentityHeader`。**记住这条，§3.5 那个反直觉的 401 就是它造成的。**

VM 上可用的工具：`jq`（`deploy/cloud-init.yaml` 的 `packages` 里装了）、`python3`（Ubuntu 24.04 自带）、`curl`。**VM 上没有装 node**（cloud-init 只装了 Docker），需要 node 时用容器里的：`docker compose exec -T proxy node -e '...'`。下文统一用 `python3` 做 JSON 格式化和 JSON 生成，你也可以换成 `jq`。

### 1.4 一个必须知道的部署事实：四个端口都发布在 0.0.0.0

`docker-compose.yml` 里的端口映射是这样写的：

```yaml
- "${SSO_PORT:-7001}:7001"
- "${LOGIN_PORT:-7003}:7003"
- "${PROXY_PORT:-3000}:3000"
- "${CONSOLE_PORT:-7004}:7004"
```

不带 IP 前缀的映射会绑到 **0.0.0.0**，也就是说 3000 / 7001 / 7003 / 7004 在 VM 的公网网卡上是**监听着的**，唯一的屏障就是 NSG——而 §1.1 已经说了 NSG 会被订阅策略周期性清掉。

建议（**本环境未实测改过，改完请自己复验**）：在环境文件里把这几个变量写成带回环地址的形式，让 Docker 只发布到本机：

```bash
PROXY_PORT=127.0.0.1:3000
SSO_PORT=127.0.0.1:7001
LOGIN_PORT=127.0.0.1:7003
CONSOLE_PORT=127.0.0.1:7004
```

然后 `docker compose up -d` 重建。这四个变量在仓库里**只**被端口映射用到（源码走查：`grep -rn 'PROXY_PORT' docker-compose*.yml src/*/src/config.ts` 只命中映射那一行），Caddy 走 Docker 内网的服务名访问 `litellm:4000` / `console:7004`，不受影响。改完确认：`curl -s http://127.0.0.1:3000/healthz` 仍返回 `{"status":"ok","service":"proxy"}`，且 `https://console.<域名>` 仍能打开。

## 2. 名字规则：先看这一节，否则后面必踩坑

这是路线 A 最常见的失败原因，值得单独一节。

系统里有三个名字，**它们的大小写规则不一样**：

| 名字 | 存在哪 | 大小写处理 | 代码位置 |
|---|---|---|---|
| SSO 用户名 `ssoUser` | SSO 的 `sso_users` 表 | 创建时被 `sanitizeSsoUser()` 强制处理：**转小写** → 截掉 `@` 及其后面 → 非 `[a-z0-9._-]` 的连续字符换成一个 `-` → 去掉首尾的 `-` → 截断到 32 字符 | `src/sso/src/users/service.ts` |
| Proxy 账号 `identity` | Proxy 的 `proxy_accounts` 表 | **原样保留 CSV 里 `name` 列的大小写**，只做 `trim()`，不做任何转换 | `src/proxy/src/accounts/copilotOauthTokenImport.ts` |
| 池成员 `identity` | `proxy_pool_members` 表 | 加成员时用 `getAccount(identity)` 精确匹配。`proxy_accounts.identity` 是 `TEXT PRIMARY KEY`、没有 `COLLATE NOCASE`，SQLite 的 `=` 因此**区分大小写** | `src/proxy/src/db/sqliteStorage.ts` |

导入时 Proxy 会拿 CSV 的 `name` 去 SSO 查用户（`GET /api/users/:ssoUser`），而 SSO 侧的查询是 `WHERE lower(sso_user) = lower(?)`，**不区分大小写**，所以 CSV 里写 `Demo01` 也能找到 SSO 用户 `demo01`——**导入会成功**。但导入进去的账号 identity 就是 `Demo01`，之后你用 `demo01` 加池成员会拿到 `404 account_not_found`，而且报错信息完全不会提大小写，非常难查。

> 这不是假设。仓库里的 `provision.sh` 第 4 步循环的是 `Demo01` / `Demo02`，而同目录 `import-payload.json` 导入的是 `demo01` / `demo02`——照着那份脚本直接跑，加成员必然 404。

**规则：从头到尾全部用小写。** SSO 用户名、CSV 的 `name` 列、加池成员的 `identity`、`X-User-Identity` 头、LiteLLM 虚拟 key 的 `metadata.trusted_user_id`，全部统一成同一个小写字符串。

命名建议：

| 项 | 建议 | 约束来源 |
|---|---|---|
| 账号名 | `<租户短名>-<两位序号>`，如 `acme-01`、`acme-02` | SSO 只保留 `[a-z0-9._-]`，长度 ≤ 32 |
| 池名 | `<租户短名>-pool`，如 `acme-pool` | 建池接口要求匹配 `^[A-Za-z0-9][A-Za-z0-9._:@-]{0,127}$`；LiteLLM 的 `trusted_identity_hook.py` 对 `trusted_user_id` 用的是**同一个正则**，两边一致 |
| 池名 vs 账号名 | **必须不同**。池名和已有账号 identity 撞车会被拒 | 建池返回 `409 pool_id_conflicts_with_account` |

为什么池名不能和账号名撞：Proxy 收到一个 identity 时，**先查池、再查账号**（`src/proxy/src/copilot/copilotAuthManager.ts` 的 `getAuth()`，源码里有专门的注释警告）。如果一个名字既是池又是账号，路由就有二义性，所以建池接口直接拒绝。

> 说明：`proxy_accounts.identity` 的大小写敏感性是 **SQLite** 的行为，本环境 `.env.pool` 里 `STORAGE_DRIVER=sqlite`。如果换成 `STORAGE_DRIVER=mysql`，MySQL 默认排序规则通常不区分大小写，行为会不一样——**未验证，改驱动前需现场确认**。不管哪种驱动，「全小写」这条规则都是安全的。

## 3. 路线 A：导入已有 OAuth token（已验证）

### 3.1 全流程一览

```
准备账号清单（name + gho_token）
   ↓
① 在 SSO 里创建同名用户            POST  http://127.0.0.1:7001/api/users
   ↓                                （必须先做，否则导入报 SSO user not found）
② 拼 CSV，调导入接口               POST  http://127.0.0.1:3000/api/accounts/copilot-oauth-token/import
   ↓                                （服务端逐个拿 token 调 Copilot /models 验证后才写库）
③ 验证账号状态 = valid             GET   http://127.0.0.1:3000/api/accounts?pageSize=100
   ↓
④ 单账号发一次真实推理             POST  http://127.0.0.1:3000/v1/messages
   ↓
⑤ 建池 + 加成员                    见 §5
```

### 3.2 token 从哪来

本文不负责教你怎么搞到 `gho_` token，只列出已知的几种来源：

| 来源 | 说明 |
|---|---|
| 从别的环境迁移 | 直接读原环境 `proxy_accounts` 表的 `copilot_oauth_token` 列 |
| 仓库自带的单账号调试命令 | `npm run login:token -- --gh-login <github登录名> --sso-user <sso用户名> --sso-password <密码> --sso-type custom`（可选 `--sso-url <url>`；也可用 `LOGIN_GH_LOGIN` / `LOGIN_SSO_USER` / `LOGIN_SSO_PASSWORD` 环境变量代替，见 `src/login/src/debugToken.ts`）。成功后把 token 打到 stdout。**需要能跑 Playwright 的机器和可达的 SSO，VM 上没装 node，这条命令不能在 VM 上直接跑** |
| 客户/同事直接给 | 最常见 |

本环境样本里 token 的形状是 `gho_` + 36 个字符（总长 40）；**别的来源不一定是这个长度，不要拿长度当校验条件**。

**不要把 token 写进 git 仓库**——仓库根目录的 `seed-accounts.json` / `import-payload.json` / `imp.json` 是本次联调留下的样例文件，**里面有明文 token**，正式环境不要照抄这种做法，交付前先清掉。

### 3.3 第 ① 步：创建 SSO 用户

导入接口会先调 `GET /api/users/<name>` 确认 SSO 用户存在，**不存在就整行失败**，报错原文是：

```
SSO user "xxx" was not found. Create it manually in SSO Users before importing this token.
```

**单个创建：**

```bash
curl -s -X POST http://127.0.0.1:7001/api/users \
  -H "X-Internal-Token: ${INTERNAL_API_TOKEN}" \
  -H "Content-Type: application/json" \
  -d '{"ssoUser":"<账号名>"}' | python3 -m json.tool
```

`<账号名>`：你规划的小写账号名，如 `acme-01`。见 §2 的命名规则。

期望输出（HTTP 201，`SsoUserDto`）：

```json
{
    "ssoUser": "acme-01",
    "email": "acme-01@<SSO 运行时设置里的邮箱域名>",
    "role": "user",
    "emuStatus": "not_synced",
    "copilotSeatStatus": "unknown",
    "createdAt": "...",
    "updatedAt": "..."
}
```

`emuStatus": "not_synced"` 和 `copilotSeatStatus": "unknown"` 在路线 A 下是**正常值**——本路线不推 SCIM、不分席位，这两个字段永远停在初始态，不影响导入和用池。

**批量创建（推荐，一次调用建完所有用户）：** SSO 有一个批量导入接口 `POST /api/users/import`，`csvText` 支持单列 `ssoUser` 或双列 `ssoUser,password`，表头可写可不写（`src/sso/src/users/bulkImport.ts`）：

```bash
curl -s -X POST http://127.0.0.1:7001/api/users/import \
  -H "X-Internal-Token: ${INTERNAL_API_TOKEN}" \
  -H "Content-Type: application/json" \
  -d '{"csvText":"ssoUser\nacme-01\nacme-02"}' | python3 -m json.tool
```

每行返回一个 `status`：`created`（新建）/ `unchanged`（已存在、密码没动）/ `updated`（已存在且你给了密码，**密码被覆盖了**）/ `failed`。只有 `failed` 计入 `summary.failed`，所以重跑是安全的、幂等的。**路线 A 不需要密码，用单列格式，别带 password 列**，免得误改已有用户的密码。

关于密码：单个创建时请求体里可以带 `"password":"<密码>"`。**导入 token 模式下用不到 SSO 密码**（不跑登录授权），不传即可；不传时服务端把密码设成与用户名相同（`resolveInitialPassword()`：`config.defaultUserPassword ?? ssoUser`，即环境变量 `SSO_DEFAULT_USER_PASSWORD` 为空时回落到用户名——本环境即如此）。

失败处理：

| 现象 | 原因 | 怎么办 |
|---|---|---|
| `401 {"error":{"code":"internal_auth_failed"}}` | `X-Internal-Token` 不对 | 重跑 §1.2，确认 `INTERNAL_API_TOKEN` 非空、没带 `\r` |
| `400 {"error":{"code":"create_user_failed","message":"SSO user \"xxx\" already exists."}}` | 用户已存在（单个创建接口的行为） | **正常情况，忽略即可**，继续下一步。用批量接口则表现为 `status: "unchanged"` |
| `409 {"error":{"code":"sso_user_limit_reached"}}` | SSO 用户数达到上限 | 先看 `GET /api/users/capacity`（返回 `{current, limit, remaining, reached}`，`limit` 为 `null` 表示不限），再去 Console 的 Settings 调 `maxSsoUsers` |
| `Connection refused` | SSO 容器没起来 | `docker compose ps sso`；SSO 缺 SAML 证书会 CrashLoop，见 §3.7 末尾 |

### 3.4 第 ② 步：CSV 格式

CSV 是拼在 JSON 请求体的 `csvText` 字段里的一个**字符串**，不是上传文件。

**表头必须精确是 `name,copilotOauthToken`**——两列、逗号分隔、不能改大小写、不能加第三列（前后空格会被 `trim()` 吃掉，所以 `name , copilotOauthToken` 也能过，但别赌这个）。表头不对，整个文件直接作废。

```
name,copilotOauthToken
acme-01,gho_xxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxx
acme-02,gho_yyyyyyyyyyyyyyyyyyyyyyyyyyyyyyyyyy
```

解析规则（都会产出一条 `status: "failed"` 的行和具体 `detail`）：

| 规则 | 违反时的 detail |
|---|---|
| 第一行必须是合法表头 | `CSV header must be exactly: name,copilotOauthToken`——**注意：表头行不合法时，后面所有数据行都被静默跳过，不会再报别的错** |
| 内容不能整个为空 | `CSV header is required: name,copilotOauthToken` |
| 数据行必须正好两列 | `Expected two columns: name,copilotOauthToken` |
| `name` 不能为空 | `name is required.` |
| token 不能为空 | `copilotOauthToken is required.` |
| 同一个 CSV 里 `name` 不能重复（**判重不区分大小写**，`Demo01` 和 `demo01` 算重复） | `Duplicate name "xxx" in import CSV.` |
| 双引号必须闭合 | `Unclosed quoted value` |
| 空行会被跳过，BOM 会被剥掉，支持双引号包裹和 `""` 转义 | — |

### 3.5 第 ③ 步：调导入接口

```bash
curl -s -X POST http://127.0.0.1:3000/api/accounts/copilot-oauth-token/import \
  -H "X-Internal-Token: ${INTERNAL_API_TOKEN}" \
  -H "Content-Type: application/json" \
  -d '{"csvText":"name,copilotOauthToken\n<账号名>,<gho_token>"}' | python3 -m json.tool
```

`<账号名>` / `<gho_token>`：§3.3 建好的 SSO 用户名，和 §3.2 拿到的 token。注意 `\n` 是 JSON 字符串里的换行转义，**在单引号里原样写 `\n` 两个字符，不要按回车**。

**只需要 `X-Internal-Token` 一个头**。`/api/*` 挂的是 `requireInternalToken`，`x-api-key` 在这里不参与鉴权（`src/proxy/src/server.ts`）。本次联调时习惯性地两个头都带，也能通——多带一个 `x-api-key` 无害，但**它会改变你写错路径时看到的报错**，见下面失败表。

服务端行为（`importCopilotOauthTokens()`）：对每一行，先查 SSO 用户 → 再拿 token 调 Copilot `/models` 做真实校验 → **校验通过才写库**，写库是 upsert（`ON CONFLICT(identity) DO UPDATE`，同名直接覆盖 token 并把状态置 `valid`）。所以导入成功就意味着这个 token 当下是能用的，不需要额外验活。

期望输出（HTTP 200，`BatchResult` 结构）：

```json
{
    "batchId": "...",
    "startedAt": "...",
    "finishedAt": "...",
    "summary": { "total": 2, "success": 2, "failed": 0 },
    "rows": [
        {
            "line": 2,
            "name": "acme-01",
            "status": "success",
            "detail": "Copilot OAuth token was validated and imported with name as GH login fallback; sync SSO to GH to confirm ghLogin.",
            "account": { "identity": "acme-01", "ssoUser": "acme-01", "ghLogin": "acme-01", "copilotOauthStatus": "valid", "...": "..." }
        }
    ]
}
```

**关于 `detail` 的两种文案**，别被吓到：

| detail | 什么时候出现 |
|---|---|
| `Copilot OAuth token was validated and imported.` | SSO 用户已经有 `ghLogin`（走过 SCIM 同步） |
| `Copilot OAuth token was validated and imported with name as GH login fallback; sync SSO to GH to confirm ghLogin.` | SSO 用户没有 `ghLogin`——**路线 A 手工建的用户就是这种**，服务端拿 CSV 的 `name` 当 `ghLogin` 兜底。**这是 success，不是警告**，池化只用 `identity`，不用 `ghLogin` |

**注意：整体 HTTP 200 不代表每一行都成功。** 一定要看 `summary.failed` 和每行的 `status`。

失败处理：

| 现象 | 原因 | 怎么办 |
|---|---|---|
| 行 detail = `SSO user "xxx" was not found...` | 没建 SSO 用户，或名字对不上 | 回 §3.3；注意 §2 的大小写规则 |
| 行 detail = `Copilot OAuth token validation failed: token is invalid or expired.` | token 无效/过期（上游返回 401） | 重新获取 token |
| 行 detail = `Copilot OAuth token validation failed: account has no Copilot access or is blocked by organization policy.` | 上游返回 403，账号没有 Copilot 权限或被组织策略拦截 | 找客户确认该 GitHub 账号的 Copilot 订阅与企业策略 |
| 行 detail = `Copilot OAuth token validation failed: List models failed with HTTP <code>.` | 其他上游状态码（含 429、5xx、网络问题） | 看具体 code；429 就等一会儿重试 |
| 行 detail 含 `CSV header must be exactly` | 表头写错 | 见 §3.4，逐字符核对 |
| `401 {"error":{"code":"internal_auth_failed"}}` | `X-Internal-Token` 不对 | 重跑 §1.2 |
| `401 {"error":{"code":"missing_api_key"}}` | **优先怀疑路径写错**。`/api/` 下没有匹配到的路径会一路掉到推理路由，而推理路由才要 `x-api-key`，于是报出一个和「导入」毫不相干的错 | 逐字符核对路径是否为 `/api/accounts/copilot-oauth-token/import`。**仓库里的 `deploy/provision.sh` 写的是 `/api/accounts/import-copilot-oauth-tokens`，那个路径不存在**，会以这个 401 的形式表现出来 |
| `400 {"error":{"code":"missing_identity_header"}}` 或 `404 Unsupported Copilot API path: ...` | 同上，路径写错了，但因为你**额外带了 `x-api-key`**，请求闯过了 API key 那一关，卡在了下一关 | 同上，核对路径 |
| `400 {"error":{"code":"invalid_import","message":"csvText is required."}}` | 请求体没带 `csvText`，或是空串 | 检查 JSON 是否被 shell 吃掉了引号 |
| `400 {"error":{"code":"copilot_oauth_import_failed"}}` | 整个导入过程抛异常（例如 SSO 服务不可达） | `docker compose ps sso` / `docker compose logs --tail=50 proxy` |

### 3.6 批量脚本

仓库里**没有**这个脚本，下面的内容需要你自己新建。它做三件事：规范化清单（转小写、去 CRLF）→ 一次性批量建 SSO 用户 → 一次性导入 token。

先准备清单文件 `/opt/ghcp-pool/accounts.list`，每行 `<账号名> <gho_token>`（空格分隔），`#` 开头的行忽略：

```
# 租户 acme 的账号
acme-01 gho_xxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxx
acme-02 gho_yyyyyyyyyyyyyyyyyyyyyyyyyyyyyyyyyy
```

保存为 `/opt/ghcp-pool/import-accounts.sh`：

```bash
#!/usr/bin/env bash
# 批量创建 SSO 用户并导入 Copilot OAuth token
# 用法: ./import-accounts.sh <清单文件>
set -euo pipefail

cd /opt/ghcp-pool
set -a; . ./.env; set +a          # 环境文件叫 .env.pool 的话改这一行

LIST="${1:?用法: $0 <清单文件>}"
SSO="http://127.0.0.1:7001"
PROXY="http://127.0.0.1:3000"
NORM="$(mktemp)"; SSO_BODY="$(mktemp)"; IMP_BODY="$(mktemp)"
trap 'rm -f "$NORM" "$SSO_BODY" "$IMP_BODY"' EXIT

# ---- 0. 规范化：去 CRLF、丢空行和注释、账号名一律转小写 ----
tr -d '\r' < "$LIST" | awk 'NF && $1 !~ /^#/ { print tolower($1), $2 }' > "$NORM"
awk 'NF != 2 { printf("第 %d 行不是「账号名 token」两列: %s\n", NR, $0); bad=1 } END { exit bad }' "$NORM"
echo "== 待处理 $(wc -l < "$NORM") 个账号 =="

# ---- 1. 批量创建 SSO 用户（已存在会返回 unchanged，可重复跑）----
echo "== 1. 创建 SSO 用户 =="
python3 - "$NORM" > "$SSO_BODY" <<'PY'
import json, sys
names = [line.split()[0] for line in open(sys.argv[1], encoding="utf-8") if line.split()]
print(json.dumps({"csvText": "ssoUser\n" + "\n".join(names)}))
PY
curl -sS -X POST "$SSO/api/users/import" \
  -H "X-Internal-Token: ${INTERNAL_API_TOKEN}" \
  -H "Content-Type: application/json" \
  -d @"$SSO_BODY" | python3 -c '
import json, sys
r = json.load(sys.stdin)
if "error" in r:
    print("  接口返回错误:", json.dumps(r["error"], ensure_ascii=False)); sys.exit(1)
s = r.get("summary", {})
print("  总计 %s  成功 %s  失败 %s" % (s.get("total"), s.get("success"), s.get("failed")))
for row in r.get("rows", []):
    print("  %-9s %-20s %s" % (row.get("status",""), row.get("ssoUser",""), row.get("detail","")))
sys.exit(0 if s.get("failed") == 0 else 1)
'

# ---- 2. 拼 CSV 并导入（用 python 生成 JSON，避免引号转义问题）----
echo "== 2. 导入 Copilot OAuth token =="
python3 - "$NORM" > "$IMP_BODY" <<'PY'
import json, sys
lines = ["name,copilotOauthToken"]
for raw in open(sys.argv[1], encoding="utf-8"):
    parts = raw.split()
    if len(parts) == 2:
        lines.append("%s,%s" % (parts[0], parts[1]))
print(json.dumps({"csvText": "\n".join(lines)}))
PY
curl -sS -X POST "$PROXY/api/accounts/copilot-oauth-token/import" \
  -H "X-Internal-Token: ${INTERNAL_API_TOKEN}" \
  -H "Content-Type: application/json" \
  -d @"$IMP_BODY" | python3 -c '
import json, sys
r = json.load(sys.stdin)
if "error" in r:
    print("  接口返回错误:", json.dumps(r["error"], ensure_ascii=False)); sys.exit(1)
s = r.get("summary", {})
print("  总计 %s  成功 %s  失败 %s" % (s.get("total"), s.get("success"), s.get("failed")))
for row in r.get("rows", []):
    ok = row.get("status") == "success"
    print("  %s %-20s %s" % ("OK  " if ok else "FAIL", row.get("name",""), row.get("detail","")))
sys.exit(0 if s.get("failed") == 0 else 1)
'
```

运行：

```bash

/opt/ghcp-pool/import-accounts.sh /opt/ghcp-pool/accounts.list
```

期望输出：

```
== 待处理 2 个账号 ==
== 1. 创建 SSO 用户 ==
  总计 2  成功 2  失败 0
  created   acme-01              Created SSO user
  created   acme-02              Created SSO user
== 2. 导入 Copilot OAuth token ==
  总计 2  成功 2  失败 0

```

重跑时第 1 步会变成 `unchanged  acme-01  Existing SSO user password was left unchanged`，这是正常的。

失败处理：

| 现象 | 怎么办 |
|---|---|
| `$'\r': command not found` / `syntax error near unexpected token` | 脚本文件是 CRLF 换行（在 Windows 上编辑过）。`sed -i 's/\r$//' /opt/ghcp-pool/import-accounts.sh` 后重跑。（清单文件的 CRLF 脚本内部已经用 `tr -d '\r'` 处理了） |
| `第 N 行不是「账号名 token」两列` | 清单文件里那一行多了/少了字段，或者用了逗号而不是空格 |
| 脚本退出码非 0 且有 `FAIL` 行 | 按 §3.5 的失败表逐行处理；修完直接重跑，全流程幂等（建用户是 unchanged，导入是 upsert） |
| `python3: command not found` | `sudo apt-get install -y python3`。也可以把两段 JSON 生成改成手写字符串，但转义很容易出错，不推荐 |
| 卡住不动 | 第 2 步会对**每个** token 真的去调一次 `api.githubcopilot.com/models`，账号多时会慢；出网不通时会一直等到超时。先 `curl -sS -o /dev/null -w '%{http_code}\n' https://api.githubcopilot.com/models` 确认 VM 能出网 |

### 3.8 路线 A 的局限

| 局限 | 说明 |
|---|---|
| **token 会过期** | `gho_` token 有有效期。过期后该账号的请求会失败，需要重新拿 token 再导入一次（导入是 upsert，同名直接覆盖并把状态置回 `valid`）。**本方案未测出具体有效期，需现场确认** |
| 没有自动续期 | 路线 A 不建立 SSO 密码 → Login 任务 → 自动重授权的链路。`POST /api/accounts/<identity>/copilot-oauth/reauthorize` 这个接口要求账号有 `ssoUser` + `ghLogin` 且必须传 `ssoPassword`，本质上还是要走路线 B 那套 Playwright 授权，**路线 A 环境下用不了**。过期只能人工换 token |
| 过期发现滞后 | 目前没有主动的 token 有效性巡检。半自动的替代做法：`GET /api/request-stats?limit=200`（不带 identity 就是全量）里 `success:false` + `failureReason` 能看出哪个账号在持续失败；或者定期对每个账号发一次最小推理请求（如 §3.7 那条 `max_tokens:24` 的命令）。**这个巡检脚本本方案没有写、没有验证过** |
| 自动失效标记只覆盖 401 | 上游返回 **401** 时 Proxy 会自动把该账号的 token 置为 `expired`（`invalidateUnauthorizedAuth()`）；403、429 等不会改状态 |
| 池的故障隔离能力有边界 | 见 §5.1 末尾的「关于冷却触发范围」——不要假设「坏账号一定会被池自动摘掉」 |

## 4. 路线 B：完整自动化（SSO + SCIM + Device Flow）

> ⚠️ **本节未在本环境验证。** 顾问侧没有 GitHub EMU 企业，无法实际跑通这条链路。以下内容全部来自源码（`src/proxy/src/copilot/copilotAuthManager.ts`、`src/proxy/src/routes/internalApi.ts`、`src/login/`、`src/sso/`）的阅读结论，写的是**原理和客户需要做什么**，不是「我实测过的操作步骤」。到客户现场时，请把本节当作设计说明和配置清单，实际操作步骤要在客户环境里重新验证一遍。

### 4.1 这条链路解决什么问题

路线 A 的账号是「死的」——token 过期就得人工换。路线 B 让系统自己完成：建 SSO 用户 → 通过 SCIM 推到客户的 GitHub EMU 企业 → 分配 Copilot 席位 → 用无头浏览器跑完 GitHub Device Flow 授权 → 拿到 `gho_` token 写库。整条链路可以在 token 过期时重跑，实现自动续期。

### 4.2 完整时序（8 步）

假设客户端第一次用一个 Proxy 从没见过的 identity 发请求。

| 步 | 发起方 | 动作 | 接口 / 代码 | 结果 |
|---|---|---|---|---|
| 1 | 客户端 | 带 `X-User-Identity: <新identity>` 发推理请求 | `POST /v1/messages`（Proxy:3000） | 通过 `x-api-key` 与身份头校验，进入 `copilotAuthManager.getAuth()` |
| 2 | Proxy | 先查池、再查账号，都没有 → 抢**数据库租约** | `claimIdentityInitialization(identity, claimId, IDENTITY_INIT_LEASE_SECONDS)`，写 `proxy_identity_initializations` 表 | 抢到 → 继续；没抢到（别的请求/实例正在做）→ 直接返回，不重复开通 |
| 3 | Proxy → SSO | 确保 SSO 用户存在 | `POST http://sso:7001/api/users/ensure`，body `{ identity, preferredSsoUser }` | 返回 `{ user, passwordForLogin, created }`。`passwordForLogin` 是后面 Playwright 登录要用的明文密码；用户已存在且密码不是已知默认值时，这个字段会是空的 |
| 4 | Proxy → 客户端 | **立刻返回 202，不阻塞** | `202 {"error":{"code":"account_initializing","message":"Account initialization has started."}}` | 客户端需要重试 |
| 5 | Proxy → SSO（后台） | 把用户推到 GitHub EMU 并分配 Copilot 席位 | `POST /api/users/batch`，body `{ operation: "sync_emu", ssoUsers: [...], assignCopilotSeat: true }` | SSO 通过 SCIM 在客户企业创建/更新用户，回填 `ghLogin`（形如 `<handle>_<企业shortcode>`），再调 GitHub API 分配席位 |
| 6 | Proxy（后台） | 建本地账号记录，生成本次**授权代次** | `createAccount({ identity, ssoUser, ghLogin, copilotOauthStatus: 'refreshing', copilotOauthAttemptId: <UUID> })` | 此后请求该 identity 返回 202（因为状态是 `refreshing`） |
| 7 | Proxy → Login（后台） | 创建登录任务 | `POST http://login:7003/api/tasks`，body `{ identity, ssoUser, ssoPassword, ghLogin, oauthAttemptId, ssoType }` | Login 排队执行：GitHub Device Flow 拿设备码 → Playwright（`playwright-extra` + stealth）打开验证页 → GitHub 登录 → 企业 SSO 跳转到自建 IdP 的 `/login` → 用 `ssoUser`/`ssoPassword` 登录 → SAML 断言回 GitHub → 授权 OpenCode OAuth client → 轮询拿到 `gho_` token。**单次约 1 分钟**，是整条链路最重的部分 |
| 8 | Login → Proxy | 回写 token | `PUT /internal/accounts/<identity>/copilot-oauth-token`，body `{ oauthAttemptId, copilotOauthToken, ghLogin }` | 代次匹配 → 写库并置 `valid`，客户端下次重试即 200。代次不匹配 → `409 stale_oauth_attempt`。失败路径走 `POST /internal/accounts/<identity>/mark-copilot-oauth-failed` |

### 4.3 三个关键设计

**① 数据库租约去重（`proxy_identity_initializations`）**

同一个新 identity 的并发首请求，只能有一个真的去开通，否则会在客户企业里建出一堆重复用户、白白消耗席位。

- 表结构：`identity` 主键 + `claim_id` + `lease_expires_at`。抢租约是原子的 DB 操作，抢不到的请求直接返回（然后照样收到 202）。
- 租约时长由环境变量 `IDENTITY_INIT_LEASE_SECONDS` 控制，代码默认 **900** 秒（`src/proxy/src/config.ts`）。设成 15 分钟是因为第 7 步可能要跑 1 分钟以上、还可能排队。
- 进程内另有一层 `Map` 做同进程去重。**为什么光有内存 Map 不够**：多个 Proxy 实例时内存互不可见，必须落到数据库这一层才是真去重。
- 开通结束（成功或失败）后释放租约；崩溃没释放的靠 `lease_expires_at` 到期兜底。

**② `oauthAttemptId` 防陈旧回调**

Login 任务是异步的、可能超时、可能被重试。如果一个跑了很久的老任务姗姗来迟地回写 token，会把新任务刚写好的有效 token 覆盖成旧的。

- 每次发起授权都生成一个新 UUID，写进 `proxy_accounts.copilot_oauth_attempt_id`。
- 回写的 SQL 带 `WHERE identity = ? AND copilot_oauth_attempt_id = ?`。代次已经变了 → 更新 0 行 → 接口返回 `409 stale_oauth_attempt`，token 不会被覆盖。
- 标记失败的接口 `mark-copilot-oauth-failed` 用同样的机制：陈旧的失败上报会被静默忽略（日志里是 `ignore-stale-copilot-oauth-failure`），不会把一个已经成功的账号误标成失败。
- 顺带一提：路线 A 的导入接口会把 `copilot_oauth_attempt_id` 置为 `NULL`——手工导入的 token 天然「赢」过任何在途的授权任务。

**③ 非阻塞状态机（202 让客户端重试）**

开通要 1 分钟以上，HTTP 请求不能挂那么久。所以 Proxy 把「开通」和「响应」彻底分开：

| 账号状态 | Proxy 返回 | code |
|---|---|---|
| 账号不存在（刚触发开通） | `202` | `account_initializing` |
| 账号存在，`copilotOauthStatus = 'refreshing'` | `202` | `account_initializing` |
| 账号存在，但既不是 `valid` 也不是 `refreshing` | `503` | `oauth_not_ready` |
| SSO 用户数达上限 | `409` | `account_limit_reached` |
| 账号 `valid` | 正常转发 | — |

### 4.4 客户端会看到什么

```json
HTTP/1.1 202 Accepted
{"error":{"code":"account_initializing","message":"Account initialization has started."}}
```

**客户端必须自己重试。** 202 不带 `Retry-After`，也不会自动升级成 200。给客户的接入说明里要写清楚：

- 首次使用一个新身份时，可能连续收到若干个 202。
- 建议重试策略：间隔 10~15 秒轮询，总时长至少覆盖 2 分钟（Device Flow 单次约 1 分钟，还可能排队）。**具体的重试次数/间隔本方案未做实测调优，需现场确认。**
- 超过预期时间仍是 202 → 去 Login 看任务状态（`GET http://127.0.0.1:7003/api/tasks`，带 `X-Internal-Token`；单个任务 `GET /api/tasks/<id>`，可以 `POST /api/tasks/<id>/retry` 重试），失败任务有独立的账号级日志文件。
- 变成 `503 oauth_not_ready` → 授权失败了，不是还在进行中，要去查 Login 任务的报错。

⚠️ **Claude Code 等标准客户端不会处理 202**，会直接报错。所以**池化场景下绝对不要依赖冷启动开通**——见 §4.6。

### 4.5 客户必须提供什么

| 项 | 对应环境变量 | 说明 |
|---|---|---|
| GitHub EMU 企业 | `ENTERPRISE_SLUG`、`ENTERPRISE_SHORTCODE` | 必须是 Enterprise Managed Users 形态。`shortcode` 决定生成的 GitHub 登录名后缀 `<handle>_<shortcode>` |
| SCIM 配置 | `SCIM_BASE_URL`（形如 `https://api.github.com/scim/v2/enterprises/<slug>`）、`SCIM_TOKEN` | SCIM token 需要企业管理员生成，权限足以创建/更新/停用企业用户 |
| SAML 配置 | `SP_ENTITY_ID`、`SP_ACS_URL`、`SSO_PUBLIC_BASE_URL` | 在客户 GitHub 企业里把 IdP 指向自建 SSO 的 `/metadata`。**`SSO_PUBLIC_BASE_URL` 必须是 GitHub 侧可达的公网地址**，因为浏览器会被 GitHub 重定向过来 |
| SAML 证书 | 挂载到 SSO 容器的 `/certs/idp-cert.pem`、`/certs/idp-key.pem` | 缺失会 CrashLoop。**路线 B 下必须是与 GitHub 企业里登记的 IdP 证书一致的那一对**，不能用自签凑数（这一点与路线 A 不同） |
| Copilot 席位 | 用于调 GitHub API 分配/回收席位的 PAT | 变量名**需现场确认**（`.env.example` 里对应的那一行），本环境没配过这个值 |
| 席位数量 | — | 每个池成员账号占一个 Copilot 席位。池子多大就要多少席位 |
| 出网能力 | — | Login 容器要能访问 `github.com` 和 `api.github.com` 跑 Device Flow 和 Playwright。**中国区网络下这一条需现场确认** |

### 4.6 池化场景下怎么用（与上游设计的区别）

这是本次改造在使用方式上最重要的一个转变，必须给客户讲清楚。

| | 上游原生设计 | 本方案（池化） |
|---|---|---|
| 心智模型 | **一人一号**。每个终端用户对应一个 identity，第一次用的时候现场开通 | **账号是基础设施**。账号池是运维预先建好的一批账号，和「有多少用户」解耦 |
| 触发时机 | 用户请求触发（冷启动） | 运维提前批量建好，**不由用户请求触发** |
| 客户端要不要处理 202 | 要 | **不要**——正常情况下客户端永远见不到 202 |
| 身份含义 | identity = 某个具体的人 | 对外 identity = **池名**（一个租户一个池），池内成员才是真账号 |
| 统计归因 | identity 就是人 | `proxy_request_stats` 里 `identity` 记**实际成员账号**，`pool_id` 记对外池名。两者都留痕 |

**所以路线 B 在池化场景下的正确用法是：把它当成一个「批量造账号」的工具，而不是一个「用户自助开通」的机制。**

具体做法（**未验证，供客户现场参考**）：

1. 运维先规划好账号名（如 `acme-01` … `acme-NN`）。
2. **在把池交付给客户端之前**，逐个用这些名字发一次一次性的推理请求，触发 §4.2 的开通链路，然后轮询直到 `GET /api/accounts/<账号名>` 返回 `copilotOauthStatus: "valid"`。这一步是运维行为，慢一点没关系。
3. 全部 `valid` 之后，再建池、加成员（§5）。
4. 客户端只拿到 LiteLLM 虚拟 key，虚拟 key 的 `metadata.trusted_user_id` 填**池名**。客户端从头到尾只看到 200。

**一个必须避开的坑**（`copilotAuthManager.getAuth()` 上方有专门的注释警告）：Proxy 的身份解析是**先查池、再查账号**。如果顺序反了，池名会被当成一个未知 identity，触发冷启动开通——真的去 SSO 里建一个叫池名的用户。所以：**池名和账号名必须完全区分开**（见 §2），并且不要把池名喂给任何会触发开通的路径。

## 5. 通用部分：账号进池

两条路线产出的账号在这一层完全一样。

### 5.1 怎么规划池子大小

**本方案没有测出「单账号在什么负载下会被限流」的阈值，所以这里不给推荐数字。** 给的是推算方法。

> prompt 缓存由客户端的 `cache_control` 标记驱动，网关侧不需要配置。Claude Code 自带该字段。

**这意味着：把负载在账号之间均匀分摊，不会损失缓存命中。** 所以池子大小可以**纯粹按额度和限流来定**，不需要为了「保住缓存」而刻意把会话钉在少数几个账号上。这也是 `least-loaded` 成为默认策略的原因。

（补充两条缓存前提：缓存需要客户端显式声明 `cache_control: {"type":"ephemeral"}`，且内容超过约 1024 token 才会被缓存。Claude Code 自带这个字段，自研客户端要自己加。）

> 读代码时会遇到的一个矛盾：`src/proxy/src/pool/poolTypes.ts` 和 `poolSelector.ts` 的注释里写着「sticky-affinity 是默认、缓存友好」「least-loaded 缓存不友好，仅用于对照测试」。**那些注释是缓存实验之前写的，已经过时**——真正的默认值是代码里的 `POOL_DEFAULTS.strategy = 'least-loaded'`。以本文和 `POOL_DEFAULTS` 为准。

推算步骤：

| 步 | 做什么 | 用什么观察 |
|---|---|---|
| 1 | 摸清客户的真实负载形态：并发会话数、每会话请求频率、平均上下文大小 | 和客户一起估，或先小规模跑一段时间看 `GET /api/request-stats?limit=200`（全量）/ `GET /api/accounts/<账号名>/request-stats?limit=200`（单账号，**按实际成员账号过滤，不是按池名**） |
| 2 | 用**单个账号**在客户的真实负载下压一段时间，记录多久出现第一次 429 | `GET /api/error-diagnostics`（带 `X-Internal-Token`）能看到完整的上游请求/响应留痕，429 在这里最清楚 |
| 3 | 按「单账号可承载的并发/频率」× 池大小 ≥ 目标负载，反推需要几个账号 | — |
| 4 | 留冷却余量：一个成员被冷却后要等 `cooldownSeconds`（默认 300 秒）。池子必须大到「冷却掉若干个成员后剩下的仍能扛住」 | `GET /api/pools/<池名>` 看 `activeMembers` / `totalMembers` |
| 5 | 校验上限：SSO 用户数有上限；席位数也是硬约束 | `GET http://127.0.0.1:7001/api/users/capacity`（返回 `{current, limit, remaining, reached}`，`limit: null` 表示不限） |

运行期的健康信号：

| 信号 | 含义 | 动作 |
|---|---|---|
| `activeMembers` 长期等于 `totalMembers` | 池子有余量 | 不用动 |
| 经常有成员 `state` 为 `cooling` | 接近限流边界 | 考虑扩池 |
| 客户端收到 `502` + `All members of pool "<池名>" are cooling down.` | 全员冷却 | 立刻扩池，或用 §5.5 的 `resume` 手工解冻 |
| 客户端收到 `502` + `Pool "<池名>" has no usable members.` | 池里没成员，或成员全被 `disabled` | 检查是不是忘了加成员 |
| `GET /api/request-stats` 里某个 `identity` 的 `success:false` 持续增长 | 大概率是这个账号本身有问题（token 过期 / 没席位 / 被策略拦） | 单独查这个账号，见 §3.7 |

> **关于「全员冷却」返回什么**（源码走查，**未实测触发**）：`PoolAllCoolingError` 内部带一个 `retryAfterSeconds` 字段，但它**没有被写进 HTTP 响应**，也没有 `Retry-After` 头——`sendCompatibleError()` 把这类未知错误统一按 502 + `api_error` 返回，客户端只能看到那句英文 message。要知道还要冷却多久，只能在 VM 上查 `GET /api/pools/<池名>` 里每个成员的 `coolingUntil`。

> **关于冷却的触发范围（重要，源码走查结论，未实测）：** 冷却计数只在 `notePoolFailure()` 被调用时才累加，而当前代码里它**只挂在「转发前的模型可用性预检」那条异常路径上**（`forwardAuthenticated()` 里 `assertModelSupportsPath` 抛 `CopilotApiError` 时）。真正转发出去的那个推理请求，如果上游返回 429/402/5xx，是**作为 HTTP 响应原样透传**给客户端的，不会走异常路径；并且成员会在拿到上游响应后被立即记一次 `reportMemberSuccess`（不看状态码）。
>
> 结论：**不要假设「上游一限流，池就会自动把这个账号摘掉」**。设计上是这么写的（429/402 立即冷却、其余错误累计到 `failureThreshold`），但实际推理路径上这套机制能不能被触发，**本方案没有实测验证过，需现场确认**。在确认之前，运维上要靠 `GET /api/request-stats` 里的 `success:false` / `failureReason` 主动发现坏账号，必要时用 §5.5 的 `state:"disabled"` 手工摘除。

### 5.2 建池

```bash
curl -s -X POST http://127.0.0.1:3000/api/pools \
  -H "X-Internal-Token: ${INTERNAL_API_TOKEN}" \
  -H "Content-Type: application/json" \
  -d '{"poolId":"<池名>","strategy":"least-loaded","sessionTtlSeconds":1800,"cooldownSeconds":300,"failureThreshold":3}' \
  | python3 -m json.tool
```

`<池名>`：见 §2 的命名建议，如 `acme-pool`。必须匹配 `^[A-Za-z0-9][A-Za-z0-9._:@-]{0,127}$`。

参数说明（不传就用 `POOL_DEFAULTS` 的默认值）：

| 字段 | 默认值 | 含义 | 什么时候要改 |
|---|---|---|---|
| `strategy` | `least-loaded` | 见 §5.3 | 见 §5.3 |
| `sessionTtlSeconds` | `1800` | 会话绑定存活时间（秒）。**只有 `sticky-affinity` 策略会写和读这个绑定** | 客户的单次会话明显长于 30 分钟时调大 |
| `cooldownSeconds` | `300` | 成员冷却时长（秒），与 Copilot 侧常见限流窗口相当 | 观察到实际限流窗口更长时调大 |
| `failureThreshold` | `3` | 连续失败多少次进冷却。设计上 429/402 不受这个阈值约束（立即冷却），但触发范围见 §5.1 末尾的提醒 | 上游偶发抖动多时调大 |
| `enabled` | `true` | 池是否启用。**置为 `false` 后 `findPool()` 会当作「不是池」**，于是池名会被当成未知账号 → 触发冷启动开通（202） | 临时停用整个租户时慎用，最好改在 LiteLLM 侧禁用虚拟 key |

⚠️ 只有**正整数**才会被接受。`sessionTtlSeconds: 0` 或负数、小数、字符串都会被 `readPositiveInt()` 判成 `undefined`，然后**静默回落到默认值**，不会报错。传完记得看返回值里的实际生效值。

期望输出：HTTP 201 + 池详情（含 `poolId` / `strategy` / `sessionTtlSeconds` / `cooldownSeconds` / `failureThreshold` / `enabled` / `members: []` / `activeMembers: 0` / `totalMembers: 0`）。

⚠️ **`POST /api/pools` 是 upsert**：对已存在的池再发一次 POST，**没传的字段会被重置成默认值**（SQL 是 `ON CONFLICT DO UPDATE SET ... = excluded....`，而 `excluded` 里没传的字段已经被填成了默认值）。要改配置请用 `PATCH`（§5.5），不要重发 POST。成员不受影响，只有池配置会被重置。

失败处理：

| 现象 | 原因 | 怎么办 |
|---|---|---|
| `400 pool_id_required` | `poolId` 为空或不是字符串 | 检查 JSON |
| `400 pool_id_invalid` | 池名含不支持的字符 | 只用 `[A-Za-z0-9._:@-]`，且首字符是字母或数字，总长 ≤ 128 |
| `409 pool_id_conflicts_with_account` | 池名和已有账号 identity 撞车 | 换个池名。见 §2 |
| `400 pool_strategy_invalid` | 策略拼错 | 只能是 `least-loaded` / `sticky-affinity` / `round-robin` |

### 5.3 选哪个策略

| 策略 | 行为 | 什么时候用 |
|---|---|---|
| **`least-loaded`（默认）** | 每次都在可用成员里挑 **`lastUsedAt` 最早**的那个（成功一次就把 `lastUsedAt` 刷新为当前时间），负载最均匀。**不读也不写会话绑定表，`sessionTtlSeconds` 对它无效** | **多租户共用一个池时的默认选择**，绝大多数场景就用它 |
| `sticky-affinity` | 同一会话固定同一账号，绑定关系落 `proxy_session_affinity` 表并在每次命中时续期，`sessionTtlSeconds` 后过期；绑定的成员不可用时丢弃绑定重新选 | ① 需要按会话审计追溯「这次对话用的是哪个账号」；② 客户端用了 `/responses` 的 `previous_response_id` 这类**有状态**接口，换账号会破坏状态 |
| `round-robin` | 按会话 key 的哈希对可用成员（按 identity 排序后）取模。**同一会话结果稳定，但完全不看负载** | 对照测试用；一般不选 |

⚠️ **权重（`weight`）只对 `sticky-affinity` 生效。** Rendezvous（HRW）哈希是 `sticky-affinity` 的选择算法，权重在它的打分公式里起作用；`least-loaded` 只看 `lastUsedAt`、`round-robin` 只看哈希取模，**两者都完全忽略 `weight` 字段**（`src/proxy/src/pool/poolSelector.ts` 的 `selectMember()` switch 分支）。默认策略下给成员设权重不会有任何效果——这一点很容易踩。

Rendezvous 哈希的实测性质（对应 `tests/selector-check.cjs` 的四条性质）：

| 性质 | 实测结果 |
|---|---|
| 确定性 | 同 `sessionKey` 必落同一账号 |
| 均匀性 | 10000 会话 / 100 账号，变异系数 **10.4%** |
| 最小扰动 | 移除 1 个账号只重映射 **1.0%** 的会话，且不波及无关会话 |
| 权重生效 | 权重 8:1:1 实测分配 **80.4% / 9.4% / 10.2%** |

会话 key 的推导优先级（`src/proxy/src/pool/sessionKey.ts`，决定「什么算同一个会话」；**默认的 least-loaded 策略下这个值只用于日志，不影响选谁**）：

1. `X-Session-Id` 请求头
2. 请求体 `metadata.user_id`（Claude Code 会传）
3. `system` + 消息数组里到第一条 `user` 为止的文本，取前 4096 字节做 sha256（也兼容 `/responses` 的 `instructions` / `input`）
4. 固定兜底值（都没有时，例如 `GET /v1/models` 这种无 body 的请求，这类请求会稳定落在同一个成员上，避免无谓打散）

### 5.4 加成员

```bash
curl -s -X POST http://127.0.0.1:3000/api/pools/<池名>/members \
  -H "X-Internal-Token: ${INTERNAL_API_TOKEN}" \
  -H "Content-Type: application/json" \
  -d '{"identity":"<账号名>","weight":1}' | python3 -m json.tool
```

期望输出：HTTP **201** +

```json
{
    "poolId": "acme-pool",
    "identity": "acme-01",
    "weight": 1,
    "state": "active",
    "consecutiveFailures": 0,
    "createdAt": "...",
    "updatedAt": "...",
    "accountStatus": "valid",
    "ghLogin": "acme-01"
}
```

`accountStatus` 直接来自 `proxy_accounts`——加成员时顺手确认它是 `valid`，能省掉后面一次排查。

批量加（承接 §3.6 的清单文件）：

```bash
cd /opt/ghcp-pool
set -a; . ./.env; set +a
POOL=<池名>
tr -d '\r' < accounts.list | awk 'NF && $1 !~ /^#/ { print tolower($1) }' | while read -r NAME; do
  CODE=$(curl -s -o /tmp/member.$$.json -w '%{http_code}' -X POST "http://127.0.0.1:3000/api/pools/${POOL}/members" \
    -H "X-Internal-Token: ${INTERNAL_API_TOKEN}" \
    -H "Content-Type: application/json" \
    -d "{\"identity\":\"${NAME}\",\"weight\":1}")
  python3 -c '
import json,sys
code, name = sys.argv[1], sys.argv[2]
d = json.load(open("/tmp/member.'"$$"'.json"))
if code == "201":
    print("  + %-20s %s (%s)" % (d.get("identity"), d.get("state"), d.get("accountStatus")))
else:
    print("  ! %-20s HTTP %s %s" % (name, code, json.dumps(d.get("error", d), ensure_ascii=False)))
' "$CODE" "$NAME"
done
rm -f /tmp/member.$$.json
```

期望输出：每行 `+ acme-01 active (valid)`。

失败处理：

| 现象 | 原因 | 怎么办 |
|---|---|---|
| `404 {"error":{"code":"pool_not_found"}}` | 池不存在 | 先建池（§5.2），核对池名 |
| `404 {"error":{"code":"account_not_found","message":"Account \"xxx\" does not exist. Onboard it first."}}` | 账号没导入，或**大小写不一致** | 用 `GET /api/accounts?pageSize=100` 看确切名字。这是最常见的原因，见 §2 |
| `400 {"error":{"code":"identity_required"}}` | body 里没有 `identity`，或是空串 | 检查 JSON |
| `400 {"error":{"code":"member_cannot_be_pool"}}` | 把池自己加成了成员 | 换名字。（正常流程下先撞到的是 `account_not_found`，因为建池时已经挡掉了同名账号） |

⚠️ **加成员也是 upsert，而且有副作用**：对已有成员重发 POST 时，
- 不传 `weight` → 权重**被重置成 1**；
- 不传 `state` → 状态**被重置成 `active`**（会把你手动 `disabled` 的成员重新启用）。

`consecutiveFailures` 和 `coolingUntil` 不会被这次 upsert 改动（它们不在 `DO UPDATE SET` 列表里）。所以改权重时要把其他字段一起带上。

### 5.5 常用运维操作

先设一次变量，下面几条都用得上：

```bash
cd /opt/ghcp-pool && set -a; . ./.env; set +a
P=http://127.0.0.1:3000
H=(-H "X-Internal-Token: ${INTERNAL_API_TOKEN}" -H "Content-Type: application/json")
```

> 这里的 `H=(...)` 是 **bash 数组**，展开时必须写成 `"${H[@]}"`。用 `sh`/`dash` 跑会报 `Syntax error: "(" unexpected`——本节命令请在 bash 下执行。

| 操作 | 命令 | 期望输出 / 说明 |
|---|---|---|
| 看池详情 | `curl -s "$P/api/pools/<池名>" "${H[@]}" \| python3 -m json.tool` | 含 `strategy` / `members[]`（每个成员的 `state`、`weight`、`coolingUntil`、`consecutiveFailures`、`lastUsedAt`、`available`）/ `activeMembers` / `totalMembers`。`available` 是算出来的：`state=active`，或 `state=cooling` 但 `coolingUntil` 已过期 |
| 只看成员列表 | `curl -s "$P/api/pools/<池名>/members" "${H[@]}" \| python3 -m json.tool` | `{items:[...]}`，不带 `available` 字段 |
| 列出所有池 | `curl -s "$P/api/pools" "${H[@]}" \| python3 -m json.tool` | `{items:[...], total:N}`，每个 item 是完整池详情 |
| 改策略 / 参数 | `curl -s -X PATCH "$P/api/pools/<池名>" "${H[@]}" -d '{"strategy":"sticky-affinity"}'` | 只改传了的字段（没传的用现有值）。**改配置一律用 PATCH，不要重发 POST** |
| 设权重（仅 `sticky-affinity` 有效） | `curl -s -X POST "$P/api/pools/<池名>/members" "${H[@]}" -d '{"identity":"<账号名>","weight":8}'` | 权重影响 HRW 哈希的分配比例。实测 8:1:1 → 80.4%/9.4%/10.2%。**默认的 least-loaded 策略下设了也没用**，见 §5.3 |
| 临时停用某成员 | `curl -s -X POST "$P/api/pools/<池名>/members" "${H[@]}" -d '{"identity":"<账号名>","weight":1,"state":"disabled"}'` | `disabled` 不参与选择。**`weight` 要带上，否则被重置成 1** |
| 手动解除冷却 | `curl -s -X POST "$P/api/pools/<池名>/members/<账号名>/resume" "${H[@]}"` | 排障用：把成员置回 `active`、清空 `coolingUntil`、连续失败计数清零，返回池详情。⚠️ **这个接口内部走的也是 upsert 且不传 weight，会把该成员的权重重置成 1**——用了 `sticky-affinity` + 非默认权重的话，resume 之后记得把权重补回去 |
| 移除成员 | `curl -s -X DELETE "$P/api/pools/<池名>/members/<账号名>" "${H[@]}"` | `{"removed":true,...}`。同时清掉该成员的会话绑定。成员不存在 → `404 member_not_found` |
| 删除池 | `curl -s -X DELETE "$P/api/pools/<池名>" "${H[@]}"` | `{"deleted":true,...}`。会连带删掉该池的全部成员行和会话绑定，**但不会删账号**，账号还在 `proxy_accounts` 里 |
| 清理过期会话绑定 | `curl -s -X POST "$P/api/pools/maintenance/prune-sessions" "${H[@]}"` | `{"removed":N}`。只对 `sticky-affinity` 有意义 |
| 看某账号的请求统计 | `curl -s "$P/api/accounts/<账号名>/request-stats?limit=50" "${H[@]}" \| python3 -m json.tool` | **按实际成员账号过滤，传池名会得到空数组**。每条含 `identity`（实际成员账号）、`poolId`（对外池名）、`path`、`model`、`success`、`failureReason`、各类 token 数 |
| 看全量请求统计 | `curl -s "$P/api/request-stats?limit=200" "${H[@]}" \| python3 -m json.tool` | 不按账号过滤，排查「池里到底谁在承接」最方便。`limit` 不传默认 100 |
| 看上游失败留痕 | `curl -s "$P/api/error-diagnostics" "${H[@]}" \| python3 -m json.tool` | 分页列表；`GET /api/error-diagnostics/<id>` 看完整请求/响应。**含明文凭据，外发前先脱敏**，见 §3.7 |

关于统计的保留条数：由 `REQUEST_STATS_PER_ACCOUNT_LIMIT` 控制**每个账号**保留多少条，超出的旧记录会被裁掉。本环境 `.env.pool` 设的是 `200`，`.env.example` 默认是 `2`（够小，改栈时注意别用默认值，否则统计几乎看不到东西）。

### 5.6 多租户隔离：一个租户一个池

架构上的隔离靠**两层**共同保证，缺一不可：

```
租户 A 的客户端 ──[LiteLLM 虚拟 key A]──┐
                                        ├─ LiteLLM 强制注入 X-User-Identity = key 的 metadata.trusted_user_id
租户 B 的客户端 ──[LiteLLM 虚拟 key B]──┘
                                        ↓
                            Proxy 按 identity 找到对应的池
                                        ↓
                        acme-pool: acme-01 acme-02 ...
                        beta-pool: beta-01 beta-02 ...
```

- **第一层（LiteLLM）**：`litellm/trusted_identity_hook.py` 是多租户隔离的**认证边界**。实测行为：无 key → 401；用 master key 直接推理 → 403（hook 强制要求虚拟 key）；**客户端自己带的 `X-User-Identity` 头会被剥掉**（hook 里的 `_remove_request_identity_headers`），仍按虚拟 key 的元数据走池分配。hook 还会校验 `trusted_user_id` 匹配 `^[A-Za-z0-9][A-Za-z0-9._:@-]{0,127}$`，不匹配直接 403——和建池的正则一致，所以只要池名建得出来，就一定能写进虚拟 key。
- **第二层（Proxy 的池）**：一个池的成员只服务这个池。跨池账号不会被串用。

操作上就是：**给每个租户建一个独立的池，池成员账号不共用**，然后为每个租户签发一把虚拟 key，key 的 `metadata.trusted_user_id` 填该租户的池名。虚拟 key 的签发和限流/计费配置见 LiteLLM 篇。

端到端实测已确认：LiteLLM 虚拟 key → 注入 `team-pool` → 池分配 → `demo01`/`demo02` 轮流承接，`proxy_request_stats` 中 `identity` 为实际账号、`pool_id` 为 `team-pool`。

**如果多个租户共用一个池**（额度紧张时的折中），要跟客户讲清楚：额度和限流会互相影响，一个租户压满会导致另一个租户遇到冷却；但**计费和审计仍然分得开**（LiteLLM 按虚拟 key 记账，Proxy 按 `identity` + `pool_id` 记账）。这种情况策略用默认的 `least-loaded`。

## 7. 故障速查

| 现象 | 最可能的原因 | 先查什么 |
|---|---|---|
| 导入返回 `401 missing_api_key` | **路径写错**（`/api/` 下未匹配的路径会掉到推理路由） | 逐字符核对 `/api/accounts/copilot-oauth-token/import`（`deploy/provision.sh` 里那个 `import-copilot-oauth-tokens` 是错的） |
| 导入返回 `400 missing_identity_header` / `404 Unsupported Copilot API path` | 同上，路径写错，只是你多带了 `x-api-key` | 核对路径 |
| 导入返回 `401 internal_auth_failed` | `X-Internal-Token` 不对，或值尾部带了 `\r` | 重跑 §1.2 |
| 导入某行 `SSO user "xxx" was not found` | 没建 SSO 用户 | §3.3 |
| 导入 detail 里出现 `...with name as GH login fallback...` | **不是错误**，是路线 A 的正常成功文案 | 不用管，看 `status` 是不是 `success` |
| 加成员 `404 account_not_found` | **大小写不一致**，或账号根本没导入 | `GET /api/accounts?pageSize=100` 看确切名字（§2） |
| 建池 `409 pool_id_conflicts_with_account` | 池名和账号名撞车 | 换池名（§2） |
| 账号列表比预期少 | 默认 `pageSize=25` | 加 `?pageSize=100`，看 `total`，必要时翻页（§3.7） |
| 推理返回 `202 account_initializing` | identity 拼错触发了冷启动开通；或池被 `enabled:false` 了 | 核对 identity；`GET /api/pools/<池名>` 看 `enabled`。本环境（路线 A）走不通冷启动链路 |
| 推理返回 `503 oauth_not_ready` | 账号状态不是 `valid` | `GET /api/accounts/<账号名>` 看 `copilotOauthStatus` |
| 推理返回 `400 missing_identity_header` | 忘带 `X-User-Identity` | 补上（`IDENTITY_HEADER_REQUIRED=true`） |
| 客户端收到 `502 All members of pool "..." are cooling down.` | 全员冷却 | `GET /api/pools/<池名>` 看谁在 `cooling`、`coolingUntil` 是多久；扩池、排查坏账号，或 `resume` |
| 客户端收到 `502 Pool "..." has no usable members.` | 池里没成员，或全被 `disabled` | `GET /api/pools/<池名>/members` |
| 给成员设了权重但完全没效果 | 策略是 `least-loaded` 或 `round-robin`，**它们不看权重** | 见 §5.3；要按权重分配得先 `PATCH` 成 `sticky-affinity` |
| 停用的成员莫名其妙又活了 / 权重变回 1 | 对成员重发了 POST（或调了 `resume`），未传字段被重置 | §5.4、§5.5 的两个 ⚠️ |
| 池配置改完又变回默认值 | 用 POST 改配置了 | 改配置用 PATCH（§5.5） |
| SSO 容器 CrashLoop | 缺 `/certs/idp-cert.pem` / `idp-key.pem` | 补证书（路线 A 用自签即可；路线 B 必须用与 GitHub 企业登记一致的真证书） |
| 浏览器打不开 console/api | NSG 被订阅策略清了 | 网卡 NSG → **子网 NSG** → VM 电源 → 数据库（顺序不能乱）。**不要改 hosts** |
| 脚本报 `$'\r': command not found` | Windows 上编辑过，CRLF 换行 | `sed -i 's/\r$//' <脚本路径>`；`.env` 也可能中招 |
| `${H[@]}` 报 `Syntax error: "(" unexpected` | 用 sh/dash 跑了 bash 数组 | 用 `bash` 执行 |
| `az tag update` 批量执行报错 | ARM 限流；**报错但可能实际已生效** | 去查资源的真实标签状态，不要看返回码 |

写测试用例时的一个额外注意：**Anthropic 会误判某些合成文本**——重复段落、形如 `Rule N: ... cite internal reference document REF-XXXX` 的模板文本会触发 `stop_reason=refusal`、`category=reasoning_extraction`。造测试数据要用内容各异的自然文本。

另外，Windows 上准备命令时：PowerShell 内联 JSON 要用单引号包裹，双引号里用 `\"` 转义会被吃掉；能在 VM 上用 bash + 单引号写就别在 PowerShell 里拼。
