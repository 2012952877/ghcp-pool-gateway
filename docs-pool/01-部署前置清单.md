> **命令执行环境**：本文所有命令默认在 **Git Bash / WSL / macOS / Linux** 下执行。如果你在 Windows PowerShell 里跑，把 `| grep xxx` 换成 `| Select-String xxx`，并注意 PowerShell 内联 JSON 要用单引号（双引号加 `\"` 转义会被吃掉）。

## 0. 先做一个决定：走哪条路线

在往下看之前，先和客户确认这次要达成什么，因为**两条路线的前置条件差了 2–6 周**。

| | **路线 A：导入已有 token** | **路线 B：完整自动化** |
| --- | --- | --- |
| 一句话 | 手里已有几个能用 Copilot 的 GitHub 账号，把它们的 token 导进来组成池 | 从企业 SAML 登录开始，自动开通 EMU 用户、分配 Copilot 席位、自动拿 token |
| 需要 GitHub Enterprise + EMU | **不需要** | **必须** |
| 需要 SCIM Token | 不需要（但 `.env` 里**必须填占位值**，见 §4.2） | 必须（真实值） |
| 需要配置企业 SAML SSO | 不需要（用自签证书让 SSO 容器起来即可） | 必须（要把企业 SAML 指向本方案的 SSO 服务） |
| 需要 Copilot 席位 | 需要，但可以是已有的个人/企业席位 | 需要，且要能由脚本分配 |
| 前置周期 | **当天到 1 天**（不含 Azure 审批） | **2–6 周**（采购 + 企业配置） |
| 本项目验证状态 | **已在 Azure 上端到端实测通过** | 本次云上部署**未走**这条链路，SSO/SCIM 相关环境变量是占位值 |

**建议**：第一次见面一律走路线 A 把系统跑起来、把账号池讲清楚；路线 B 作为后续阶段，让客户在这期间并行走采购和企业配置。

### 0.1 路线 A 能演示什么 / 不能演示什么

| | 内容 |
| --- | --- |
| **能演示** | 账号池三种选择策略（`least-loaded` / `sticky-affinity` / `round-robin`）；HRW 哈希的分配均匀性与移除账号时的低重映射；上游 429/402 触发的即时冷却与自动恢复；LiteLLM 虚拟 key 的多租户隔离（无 key → 401、master key 直推 → 403、伪造 `X-User-Identity` 头被剥掉）；**prompt 缓存跨 GHCP 账号共享**（实测 demo01 写入 2000 token 缓存，demo02 发相同请求 `cache_read=1716` 命中）；Caddy 自动 TLS 与按域名分流；Console 上看账号状态、请求统计（`identity` 记实际成员账号、`pool_id` 记对外池名）、上游错误诊断 |
| **不能演示** | 用户用企业 SAML 登录后自动开通 EMU 账号；SCIM 自动建号 / 停用 / 删除；Copilot 席位自动分配与 AI Credits 用量看板；Login 服务的 Device Flow + 无头 Playwright 自动授权链路（**在本次云上环境未验证**）；token 失效后的自动续期——路线 A 下 token 失效必须**人工重新导入** |

### 0.2 ⚠️ 路线 A 的 token 从哪来（初稿在这里有误，已更正）

| 问题 | 回答 |
| --- | --- |
| token 是什么 | 通过 GitHub Device Flow 拿到的 Copilot OAuth token。Proxy 拿它去访问 `api.githubcopilot.com`（**已核对代码**：`src/proxy/src/config.ts` 里 `COPILOT_API_BASE_URL` 默认 `https://api.githubcopilot.com`，Proxy 运行时**不**访问 `api.github.com`） |
| 仓库里那个调试命令能不能直接用来取 token | **能，但有前提，别被命令名骗了。** 仓库脚本是 `src/login` 下的 `login:copilot-oauth`（根目录暴露的等价脚本名是 `login:token`，两者都指向 `src/login/src/debugToken.ts`）。**已核对代码**：它必填 `--gh-login`、`--sso-user`、`--sso-password`，会拉起**无头 Playwright 浏览器**去走 SSO 登录页并替你点掉 GitHub 的设备授权页，成功后把原始 token 打到 stdout（提示信息走 stderr）。<br>**也就是说：它假设已经有一个 SSO IdP 能用账号密码登录这个 GitHub 账号。** 对「同事自己的个人 GitHub 账号 + 2FA」这种场景，这条命令**不适用** |
| 那路线 A 实际怎么拿 | **需现场确认。** 三种可能：① 客户/工程师本机已有的 Copilot 客户端授权文件里就有 token；② 手工走一次 GitHub Device Flow（`https://github.com/login/device/code` → `https://github.com/login/oauth/access_token`，**已核对代码**：`src/login/src/config.ts` 里就是这两个端点；`docker-compose.yml` 里 `GITHUB_OAUTH_CLIENT_ID` 默认 `Ov23li8tweQw6odWQebz`、`GITHUB_OAUTH_SCOPE` 默认 `read:user`）——**纯手工 device flow 本项目未验证**；③ 客户自己提供。**动手前一定要先确认这一条落地方式，否则演示当天会卡在「拿不到 token」上** |
| 谁能拿 | token 对应的 GitHub 账号必须**当前拥有可用的 Copilot 访问权限**。导入接口会先调 Copilot API 校验（**已核对代码**，`src/proxy/src/accounts/copilotOauthTokenImport.ts`）：401 → `token is invalid or expired`；403 → `account has no Copilot access or is blocked by organization policy` |
| 组织策略 | 如果账号属于某个 GitHub 组织，且该组织开了 **OAuth App 访问限制**，上面那个 client id 可能被拦，表现为授权失败或导入报 403。**请提前让客户确认**，这一条最容易在现场才发现 |
| 有效期多久 | **未验证**。本项目没有测过 token 的自然过期时间。已确认的行为是：上游返回 401 时 Proxy 会清除该 identity 的 token 并标记为 `expired`（**已核对代码**：`src/proxy/src/copilot/copilotAuthManager.ts`），此时必须人工重新导入；403 会原样透传且**不**清除 token |
| 要几个 | 演示账号池至少 **2 个**（本项目实测用的是 demo01 / demo02）。3 个以上更容易讲清楚负载分摊 |
| 导入前提 | **对应的 SSO 用户必须已经在 SSO 服务里存在**，否则导入返回 `SSO user "<name>" was not found. Create it manually in SSO Users before importing this token.`（`deploy/provision.sh` 会替你先建好 SSO 用户） |
| 导入格式 | CSV，表头必须**精确**为 `name,copilotOauthToken`。**已核对代码**：列名前后的空格会被 `trim` 掉可以容忍，但**拼写和大小写必须完全一致、必须正好两列**；表头不合格时后续所有行会被整批跳过。CSV 内同名（忽略大小写）会被判重复 |
| 大小写 | 账号名统一按**小写**处理（`provision.sh` 会先转小写，SSO 侧比对也忽略大小写）。**直接全用小写，别给自己找麻烦** |
| 安全 | token 等价于该账号的 Copilot 使用权。请客户用一次性/演示账号，不要用生产管理员账号；演示结束后主动吊销 |

## 2. Azure 侧

### 2.1 订阅类型

| 要求 | 说明 |
| --- | --- |
| 必须是 **Azure 全球版**（portal.azure.com） | 中国世纪互联版（portal.azure.cn）是独立云，**本方案未在其上验证** |
| 计费类型 | 按需付费（Pay-As-You-Go）、EA、MCA、CSP 均可 |
| 不推荐 | **免费试用（Free Trial）**：vCPU 配额上限低，且通常无法提额；**Visual Studio / MSDN 订阅**：通常挂着严格的治理策略，正是 §6 那些坑的高发环境 |
| 订阅状态 | 必须是 `Enabled`。用 `az account show` 确认 |

### 2.2 需要的 RBAC 角色

| 要做的事 | 建议角色 | 授予范围 |
| --- | --- | --- |
| 创建资源组、VM、磁盘、VNet、子网、NSG、公网 IP | **Contributor** | 目标资源组（若资源组还没建，则临时给订阅级，建完后收回到资源组级） |
| 拆细的替代方案 | **Virtual Machine Contributor** + **Network Contributor** | 目标资源组。注意 VM Contributor 单独不能建 VNet/NSG，两个都要 |
| 给资源打 `CostControl=Ignore` / `SecurityControl=Ignore` 标签 | Contributor 已包含 | — |
| 查看订阅上挂了哪些策略（排障必需） | **Reader** 即可 | 订阅 |
| **申请 / 创建策略豁免** | 通常需要订阅级的策略管理权限或直接由 Owner 代办 | 订阅或管理组 |

> 最后一行的具体角色名各租户治理模型不同，**请让客户的订阅 Owner 确认**——不要自己去猜角色名然后申请错。多数情况下更快的做法是：不申请权限，直接请 Owner 帮你把豁免建好。

### 2.3 区域选择建议

| 区域 | 建议 | 理由 |
| --- | --- | --- |
| East Asia（香港） | **首选** | 从中国大陆访问延迟最低 |
| Southeast Asia（新加坡） | 次选 | 延迟略高，容量通常更充裕 |
| Japan East | 备选 | 延迟可接受，成本略高 |
| 美国 / 欧洲区域 | 不建议 | 交互式对话场景延迟体感明显变差 |

补充说明：

- 上游 `api.githubcopilot.com` 从哪个 Azure 区域访问都可以，**区域选择只影响工程师和演示客户端到 VM 这一段的延迟**。
- 区域一旦定下，公网 IP 也跟着定；用 nip.io 的话域名里就带着这个 IP，**IP 变了域名和证书都要重来**。所以务必创建**静态（Static）**公网 IP，不要用动态。
- 先确认目标区域有 Dsv5 系列容量和配额，再动手（命令见 §5）。

### 2.4 预估月成本

## 3. 网络（入站 / 出站 / 域名 / 中国区）

### 3.1 必须放行的入站端口

| 端口 | 协议 | 来源 | 用途 | 能不能不开 |
| --- | --- | --- | --- | --- |
| **443** | TCP | 演示客户端所在网段（能收窄就收窄，收不窄就 Internet） | `api.<域名>`（推理入口）和 `console.<域名>`（运维控制台） | 不能 |
| **80** | TCP | **Internet** | Caddy 的 ACME 证书签发挑战 + HTTP→HTTPS 跳转 | 不能，除非改用 DNS-01 |
| **22** | TCP | **只放行工程师的出口 IP**，或走堡垒机 | SSH 部署运维 | 不能 |

**关于 443 的来源收窄**：如果演示客户端走 VPN / 代理出去，它的源 IP 是**代理出口 IP**，而且可能随时变。收窄成一个固定网段的做法在这种环境里经常反而把自己挡在外面。**实操建议**：443 开到 Internet，安全性靠 LiteLLM 虚拟 key 保证；把「收窄」的精力放在 22 上。

**关于 80 端口**：Caddy 的自动 TLS 会尝试 ACME 挑战。**本项目实测环境是 80 和 443 都对 Internet 开放的状态下签发成功的；只开 443（TLS-ALPN-01）能否成功本项目未单独验证**。如果客户的安全策略绝对不允许把 80 开到 Internet，替代方案是 DNS-01（需要对应 DNS 厂商的 Caddy 插件）或直接提供已有证书文件——**这两种做法本项目都未实现、未验证**，属于需要额外工作量的变更，请提前和客户谈清楚。

**证书签发频率**：反复销毁重建环境时，注意 Let's Encrypt 对同一组域名有「重复证书」的周频率上限。本项目**没有触发过**，属于提醒而非实测结论。真要反复重建，可先用 ACME staging 环境调通再切正式（**本项目未验证该切换方式**）。

### 3.2 端口模型

只有 Caddy 对外，其余服务都是内部服务：

| 端口 | 服务 | 绑定地址 | 谁访问 |
| --- | --- | --- | --- |
| 80 / 443 | Caddy | `0.0.0.0` | 对外，唯一入口 |
| 3000 | GHCP Proxy | `127.0.0.1` | LiteLLM（走 Docker 网络）、本机管理脚本 |
| 4000 | LiteLLM | `127.0.0.1` | Caddy（走 Docker 网络）、本机管理脚本 |
| 7001 / 7003 / 7004 | SSO / Login / Console | `127.0.0.1` | Proxy 与 Console（走 Docker 网络）、本机管理脚本 |

绑定地址由 `.env` 的 `BIND_ADDR` 统一控制，**默认 `127.0.0.1`**：

```bash
BIND_ADDR=127.0.0.1
```

compose 展开后形如 `127.0.0.1:3000:3000`，只有服务器本机能连。
容器之间走 Docker 内部网络按服务名互访（如 `http://proxy:3000`），不经过这些映射，
因此收敛绑定不影响任何服务间调用。

保留这些本机映射是为了方便在服务器上直接跑 `provision.sh`、`create-key.sh`
和健康检查——它们都用 `127.0.0.1` 访问。

> **网络层规则是第二道防线。** 由于默认已绑回环地址，即使防火墙规则被误删或被策略重置，
> 内部服务也不会随之暴露。放行 80 / 443 即可，无需为 3000 / 4000 等端口单独配置。

> 若确有需要让其他主机直连内部服务（例如把 Console 放到内网负载均衡后面），
> 可将 `BIND_ADDR` 改为内网网卡地址，**不要设为 `0.0.0.0`**。

### 3.3 出站目标

默认情况下，绑了公网 IP 的 Azure VM 出站不受限。**只有当客户订阅挂了 Azure Firewall、强制隧道（UDR）或出站 NSG 白名单时**，才需要把下面的清单提交给网络团队。

| 目标 | 端口 | 谁用 | 什么时候需要 |
| --- | --- | --- | --- |
| `api.githubcopilot.com` | 443 | Proxy → Copilot 推理上游 | **运行时，永久必需** |
| ACME 目录：Let's Encrypt / ZeroSSL | 443 | Caddy 签发和续期证书 | **运行时，永久必需**（证书要续期） |
| `api.github.com` | 443 | **仅 SSO 服务**（Copilot 席位、AI Credits、SCIM）。**已核对代码**：Proxy 运行时不访问它 | 路线 B 运行时 |
| `github.com`（`/login/device/code`、`/login/oauth/access_token`） | 443 | Login 服务 Device Flow | 路线 B 运行时；路线 A 若在 VM 上现取 token 也需要 |
| Docker Hub（`registry-1.docker.io`、`auth.docker.io` 等） | 443 | 拉 `caddy:2.10.2-alpine` / `postgres:16-alpine` / `redis:7-alpine` 镜像 | **构建/部署时** |
| `ghcr.io` | 443 | 拉 LiteLLM 官方基础镜像 `ghcr.io/berriai/litellm:main-stable` | **构建/部署时** |
| `download.docker.com`、Ubuntu apt 源 | 443 / 80 | cloud-init 装 Docker | **首次开机时** |
| npm registry（`registry.npmjs.org`） | 443 | 构建 proxy / sso / login / console 四个镜像 | **构建时** |
| Playwright 浏览器下载源 | 443 | Login 镜像构建时安装 Chromium | **构建时**（这一步耗时最长、占空间最大，网络差时最容易失败） |

补充两条：

- **Docker Hub 匿名拉取有速率限制**。同一出口 IP 反复重建时可能被限，表现为 `toomanyrequests`。解决办法是在 VM 上 `docker login` 一个 Docker Hub 账号。**本项目未触发过，属于提醒。**
- 如果客户出站管控很严，最省事的做法是**在网络通畅的环境先把镜像构建好推到客户的 ACR**，VM 上只拉私有镜像。这样只剩下运行时的两三个出站目标要放行。**此路径本项目未验证。**

### 3.4 域名与证书方案

| 方案 | 前置准备 | 优点 | 缺点 |
| --- | --- | --- | --- |
| **nip.io**（推荐首次演示用） | **零准备**。域名直接是 `<公网IP>.nip.io`，例如 `20.78.139.35.nip.io` | 不用等 DNS 审批；本项目**已实测通过** | 依赖第三方免费 DNS 服务，无 SLA；IP 一变域名就变、证书要重签；正式对客户交付时观感一般 |
| **客户自有域名** | 提前加两条 A 记录：`api.<域名>` 和 `console.<域名>` 都指向 VM 的静态公网 IP。TTL 建议先设 300 秒 | 观感专业，IP 可以换 | 要走客户 DNS 审批，1–3 工作日 |

两种方案都需要：

- 静态公网 IP（不要动态）。
- 80 端口从 Internet 可达（ACME 挑战）。
- 把 `deploy/Caddyfile.pool` 第 2 行的 `email admin@example.com` 换成真实邮箱。
- 域名值最终写进 `.env` 的 `PUBLIC_HOST`，**不带 `api.` / `console.` 前缀**——Caddy 用 `api.{$PUBLIC_HOST}` / `console.{$PUBLIC_HOST}` 自己拼（**已核对代码**：`deploy/Caddyfile.pool`）。

### 3.5 ⚠️ 中国区网络：Fake-IP DNS

**这是实测踩过的坑，写在这里避免对方工程师走弯路。**

中国区常见的代理软件会把域名解析成假 IP（实测见过 `6.6.4.243` 这种）。看起来像 DNS 坏了，但：

- **Fake-IP 是必需的**——流量必须走隧道才能通，强制解析到真实 IP 反而连不上。
- **所以不要改 hosts 文件**，改了只会更糟。
- **同理，`nslookup` / `ping` 在这种环境下的结果没有诊断价值**，别拿它们判断「域名解析对不对」。用 `curl -v https://console.<域名>` 看能不能建立 TLS 才是有效判据。
- 浏览器打不开 `console.<域名>` 时，**第一反应不应该是查 DNS，而是查 NSG 规则是不是又被策略清空了**（见 §6）。
- 仓库里的 `deploy/pool-bridge.mjs` 是本地桥接脚本，专门用来绕开 Fake-IP DNS 做调试。**仅调试用，不是部署组件。**

## 4. 代码与配置的前置条件

这一节是初稿漏掉但**当天一定会卡住**的部分。

### 4.1 代码怎么送上 VM

`docker compose build` 要在 VM 上读源码，而仓库不在公网。三条路，**动手前先定好走哪条**：

| 方式 | 说明 | 额外前置 |
| --- | --- | --- |
| VM 上 `git clone` | 最顺，但要 VM 能访问客户内部 Git，且要有凭据 | Git 服务器地址 + 只读凭据；出站放行 |
| 本机打包 `scp` 上去 | 最稳，不依赖 VM 的 Git 访问 | 22 端口已放行；注意排除 `node_modules`、`.git` |
| 先构建镜像推 ACR，VM 只拉镜像 | 出站管控严时最省事 | 一个 ACR + 拉取凭据。**本项目未验证** |

目标目录固定是 **`/opt/ghcp-pool`**（`deploy/cloud-init.yaml` 会创建并把属主设成 `azureuser`）。`provision.sh` 和 `create-key.sh` 的注释也都假设在这个目录下执行。

### 4.2 `.env`：路线 A 也必须填的字段

`cp .env.example .env` 之后要填的东西，按「必须真实」和「可以是占位值」分开：

| 字段 | 路线 A 要求 | 怎么取值 |
| --- | --- | --- |
| `PUBLIC_HOST` | **真实** | `<VM公网IP>.nip.io` 或客户域名，**不带 api./console. 前缀** |
| `API_KEY` | **真实随机** | 见下方生成命令。⚠️ 只给 LiteLLM 用，绝不下发给最终用户 |
| `INTERNAL_API_TOKEN` | **真实随机** | 同上。服务间内部调用令牌 |
| `SESSION_SECRET` | **真实随机** | 同上。Console 会话签名 |
| `LITELLM_MASTER_KEY` | **真实随机**，**必须 `sk-` 开头** | `sk-` + 随机串 |
| `LITELLM_DB_PASSWORD` | **真实随机** | 同上 |
| `SP_ENTITY_ID` / `SP_ACS_URL` / `ENTERPRISE_SLUG` / `SCIM_BASE_URL` / `SCIM_TOKEN` | **占位值即可，但不能留空** | **已核对代码**：`docker-compose.yml` 里这几项写成 `${X:?set X}`，为空时 `docker compose` 会直接报错拒绝启动。路线 A 下它们不会被真正用到 |
| `SSO_PUBLIC_BASE_URL` | 保持 `http://sso:7001` | 同上，不能留空 |

**生成随机密钥**（`.env.example` 里给的两条，任选其一，在本机或 VM 上执行）：

```bash
node -e "console.log(require('crypto').randomBytes(32).toString('base64url'))"
```

```bash
openssl rand -base64 32 | tr -d '/+=' | cut -c1-43
```

> **期望输出**：一行 40 多个字符的随机串。
> **失败时**：`node` 不存在就用 `openssl` 那条；两个都没有，在本机生成好再贴进 VM 的 `.env`。

> ⚠️ **Windows 上编辑 `.env` 或脚本注意 CRLF**。用 CRLF 保存的 `.env` 会让变量值末尾多一个 `\r`，症状是密钥"看起来对但就是认证失败"。用 `dos2unix` 或在 VM 上直接 `nano` 编辑。

### 4.3 SAML 自签证书（不做会 CrashLoop）

```bash
bash scripts/gen-certs.sh
```

> **期望输出**：两行 `Wrote:` 后面跟 `<仓库根>/certs/idp-key.pem` 和 `idp-cert.pem`。
> **它做了什么**（**已核对代码**）：`openssl req -x509 -newkey rsa:2048 -nodes -days 3650 -subj "/CN=local-emu-idp"`，并把私钥 `chmod 600`。
> **默认输出目录**：仓库根下的 `certs/`，可用环境变量 `CERT_DIR` 覆盖；compose 侧挂载路径由 `SSO_CERT_DIR`（默认 `./certs`）控制，两者要对上。
> **失败时**：`openssl: command not found` → `sudo apt-get install -y openssl`。不生成就直接起服务的话，SSO 容器会 CrashLoop，进而 proxy / console 因为 `depends_on: service_healthy` 一直起不来。

### 4.4 VM 上还需要的运行时依赖

`deploy/cloud-init.yaml` 只装了 `ca-certificates` / `curl` / `gnupg` / `jq` 和 Docker。但：

| 依赖 | 谁用 | 说明 |
| --- | --- | --- |
| `python3` | `deploy/provision.sh` 和 `deploy/create-key.sh` 全程用 `python3` 解析 JSON 输出 | Ubuntu 24.04 通常自带，但**开机后要确认**：`python3 --version`。没有就 `sudo apt-get install -y python3` |
| `node`（可选） | `provision.sh` 生成 SSO 初始密码时优先用 `node`，取不到会自动回退到 `openssl` | **不装也行**（**已核对代码**：有 `|| openssl` 兜底） |
| `docker compose` v2 | 全部编排 | cloud-init 装的是 `docker-compose-plugin`，用法是 `docker compose`（中间空格），不是 `docker-compose` |

**开机后第一件事**是确认 cloud-init 跑完了：

```bash
ls -l /opt/ghcp-pool/.cloud-init-done && docker --version && python3 --version
```

> **期望输出**：三行，分别是那个标记文件、Docker 版本、Python 版本。
> **失败时**：标记文件不存在说明 cloud-init 还没跑完或失败了，看 `sudo cat /var/log/cloud-init-output.log` 的末尾。`docker: permission denied` 说明当前用户不在 `docker` 组——**先确认 VM 的管理员用户名是不是 `azureuser`**（见 §1 #12），是的话重新登录一次让组生效。

## 6. ⚠️ 订阅策略会周期性破坏环境

**这一节是整份清单里最重要的部分。** 本项目在真实 Azure 环境上被订阅策略破坏过至少三次，每次都花了大量时间排查。请务必在见面前就把这件事和客户的云治理团队讲清楚。

### 6.1 三种已实测的破坏方式

| # | 破坏方式 | 症状长什么样 | 隐蔽程度 |
| --- | --- | --- | --- |
| **a** | **清空资源组下全部 NSG 的自定义规则** | 突然所有端口不通，443 直接超时。查 NSG 规则列表发现自定义规则一条不剩 | 中——一查 NSG 就能看出来 |
| **b** | **停止计算与数据库资源**（实测被停过 AKS 集群和 MySQL / PostgreSQL 实例；单 VM 部署下对应就是 VM 被 deallocate） | 服务全挂，SSH 也连不上 | 低——VM 状态一看就知道 |
| **c** | **新建一个子网 NSG 挂到 VNet 子网上，里面零规则** | **最隐蔽**。网卡 NSG 的规则全都在、VM 在正常运行、日志也没异常，但公网就是不通 | **高——最容易漏，务必记住这一层** |

### 6.2 标签能挡住什么、挡不住什么

给资源打 `CostControl=Ignore` + `SecurityControl=Ignore` 标签**有帮助，但不是万能的**：

| 破坏方式 | `CostControl=Ignore` | `SecurityControl=Ignore` | 结论 |
| --- | --- | --- | --- |
| a. 清空 NSG 规则 | — | 有帮助 | **部分挡住** |
| b. 停止 VM / 数据库 | 有帮助 | — | **部分挡住** |
| c. 新建零规则子网 NSG | 挡不住 | 挡不住 | **完全挡不住**——策略新建出来的资源天生就没有标签，标签机制在这里根本不生效 |

打标签时的实操坑：**`az tag update` 批量执行会被 ARM 限流**，命令报错但实际可能已经生效。**不要看返回码，要去复查资源的真实标签状态。**

### 6.3 出问题时的固定排查顺序

**照这个顺序查，一步都别跳。** 尤其是第 2 步，最容易漏。

1. **网卡（NIC）NSG** —— 规则还在吗？
2. **子网 NSG** —— 是不是多出来一个新 NSG，或者原来那个的规则被清了？**这一层最容易漏。**
3. **VM 电源状态** —— 是不是被 deallocate 了？
4. **数据库 / 容器状态** —— PostgreSQL、Redis、各服务容器是不是还在跑？

补充两条实测结论：

- **两层 NSG 都要放行**。网卡 NSG 和子网 NSG 是彼此独立的两层，缺一不可。只配一层等于没配。
- **（仅 AKS 部署相关，单 VM 部署可跳过）** AKS 的 LoadBalancer 开启了 `enableFloatingIP`（DSR），包到达节点时目标 IP 仍然是公网 IP。因此 NSG 规则的 destination **必须写公网 IP**，写子网网段不生效。

### 6.4 建议客户提前申请的豁免

**这是全清单里周期最长的一项（3–10 工作日），请第一时间发起。**

请客户的云治理 / 策略团队针对**目标资源组**建立策略豁免（Policy Exemption），申请时说清楚：

| 说明项 | 建议写法 |
| --- | --- |
| 范围 | 只针对这一个资源组，不扩大到订阅 |
| 有效期 | 明确写截止日期（例如「PoC 演示环境，有效期 6 周，到期自动失效」）——有明确到期时间的申请通过率更高 |
| **必须覆盖的策略类型** | ① 强制修改 / 清空 NSG 规则的策略；② 自动停止闲置计算和数据库资源的成本策略；③ **自动为子网创建并附加 NSG 的策略**（第三条最关键，也最容易被漏掉，因为它是「创建」而非「修改」） |
| 补充要求 | 请对方明确回复「豁免是否包含自动新建资源的那一类策略」，不要只拿到一句「已豁免」 |

**如果拿不到豁免怎么办**（诚实说，这在治理严格的订阅里很常见）：

- 接受「环境会被反复破坏」这个前提，把它变成日常运维动作。
- 提前把**重建 NSG 规则的命令**写成脚本存在 VM 上（以及一份存在本机——VM 连不上时才需要它），被清了就重跑一遍。
- **每天开工前、每次演示前 15 分钟，按 §6.3 的顺序跑一遍自检**，别在客户面前才发现不通。
- 演示当天准备好一个降级方案（例如本地端到端环境，见 `tests/e2e-pool.mts`），万一云上被破坏还能继续讲。
