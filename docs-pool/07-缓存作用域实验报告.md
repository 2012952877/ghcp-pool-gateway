# GHCP 账号池：prompt 缓存作用域实验报告

**日期**：2026-09-08
**环境**：`ghcp-pool-rg` / `20.78.139.35`（单 VM + docker-compose 全栈）
**代码**：`tests/cache-cross-account.mjs`（仓库 `2012952877/ghcp-pool-gateway`）

---

## 一、一句话结论

**Anthropic 的 prompt 缓存在多个 GitHub Copilot 账号之间共享，换账号不会丢缓存。**
因此账号池用 `least-loaded` 按负载均匀分摊是安全的，不会付出额外的缓存写入成本。

实验同时发现并修复了一个生产配置问题：LiteLLM 的响应缓存被打开，导致相同请求跨租户返回同一份旧响应，且掩盖了真实的缓存指标。

---

## 二、为什么要做这个实验

账号池的默认策略是 `least-loaded`——每次挑最久未使用的账号，同一个会话的连续请求会落在不同账号上。

这个设计成立的前提是：**换账号不丢 prompt 缓存**。

如果缓存按 GHCP 账号隔离，那么：

| | 单价（相对基础输入价） |
|---|---|
| 缓存写入 | **1.25×** |
| 缓存读取 | **0.1×** |
| 无缓存 | 1× |

每次换号都会 miss 并重新写入，等于每次都付 1.25× ——**池化就成了净亏**。所以这个问题必须用实验回答，不能靠推测。

---

## 三、实验设计

### 3.1 如何控制"请求落在哪个账号"

账号池默认策略会自动选号，无法指定。解决办法是**给每个账号签发一把 1:1 的虚拟 key**：

```bash
B="https://api.20.78.139.35.nip.io"
M="<LITELLM_MASTER_KEY>"

for acct in demo01 demo02; do
  curl -s -X POST "$B/key/generate" \
    -H "Authorization: Bearer $M" \
    -H "Content-Type: application/json" \
    -d "{\"key_alias\":\"cache-exp-$acct\",
         \"metadata\":{\"trusted_user_id\":\"$acct\"},
         \"max_budget\":5,\"duration\":\"1d\"}"
done
```

`metadata.trusted_user_id` 填**账号名**而不是池名，Proxy 查不到同名的池，就回落到 1:1 模式直接使用该账号。这样每把 key 就精确对应一个 GHCP 账号。

### 3.2 对照组：这个实验最关键的部分

只做"demo01 写入 → demo02 读取"是**不够的**。如果观察到 miss，无法区分两种情况：

- 缓存按账号隔离
- 这条链路上缓存**根本没生效**

所以必须加一个**同账号基线**：

| 用例 | 账号 | 目的 |
|---|---|---|
| S1 | demo01 | 冷启动，建立缓存 |
| **S2** | demo01 | **同账号重复请求 —— 基线** |
| **S3** | demo02 | **跨账号，同一前缀 —— 待测项** |
| S4 | demo02 | demo02 自己重复一次 |

判定逻辑：

```
S2 不命中  →  链路上缓存没生效，S3 的结果无法解读，先排查
S2 命中 且 S3 命中  →  缓存跨账号共享
S2 命中 但 S3 不命中  →  缓存按账号隔离
```

再加三个反向对照，排除"测到的其实不是缓存"：

| 用例 | 内容 | 预期 |
|---|---|---|
| C1 | 换一段**不同**的前缀 | 不命中（否则说明是"总是命中"，前面的结论无意义） |
| C2 | 相同前缀但**不打** `cache_control` | 既不写也不读 |
| C3 | 前缀**过短** | 不建缓存 |

### 3.3 载荷构造的三个坑

**① 前缀必须够长。** 最小可缓存长度是模型相关的：

| 模型 | 最小 token 数 |
|---|---:|
| Claude Opus 5、Fable 5/5.1 | 512 |
| **Claude Sonnet 5**、Opus 4.8、Sonnet 4.6/4.5 | **1024** |
| Opus 4.7 | 2048 |
| Opus 4.6/4.5、Haiku 4.5 | 4096 |

低于门槛**不会报错**，只是静默地不缓存。

**② 每轮要用唯一标识。** 否则会命中上一轮跑剩的缓存，得到假阳性。本实验在前缀里嵌入一个随机 `RUN_ID`。

**③ 不要用机械重复的合成文本。** 早期版本用了 `Rule 1 / Rule 2 / Rule 3...` 这种结构，触发了模型的 `stop_reason: refusal`，实验数据全废。改用自然的技术文档语料后正常。

## 四、完整代码

完整脚本见仓库 `tests/cache-cross-account.mjs`。核心部分：

### 4.1 构造前缀

```js
/** 每次运行用一个唯一 ID，保证前缀是全新的 */
const RUN_ID = Math.random().toString(36).slice(2, 10).toUpperCase();

const SECTIONS = [
  ['服务分层', '网关层负责鉴权与配额，业务层只处理领域逻辑…'],
  ['数据一致性', '账户余额的变更走单一写入路径，所有读取从只读副本获取…'],
  // …共 12 条自然技术文档语料
];

function buildPrefix(variant) {
  const head = `内部工程规范手册（编号 ${RUN_ID}-${variant}）\n\n`;
  const body = SECTIONS.map(([t, x], i) => `${i + 1}. ${t}\n${x}\n`).join('\n');
  const tail = `\n变体标识 ${variant} 用于构造互不相同的缓存键。\n`;
  return head + body + tail;
}
```

### 4.2 发送请求

```js
async function ask(key, variant, opts = {}) {
  const { cache = true, short = false } = opts;

  const text = short
    ? `短前缀 ${RUN_ID}-${variant}，仅用于验证最小长度门槛。`
    : buildPrefix(variant);

  const systemBlock = { type: 'text', text };
  // 缓存断点打在 system 块末尾：渲染顺序是 tools → system → messages，
  // 断点之后的 messages 每次不同也不影响命中
  if (cache) systemBlock.cache_control = { type: 'ephemeral' };

  const res = await fetch(`${API_BASE}/v1/messages`, {
    method: 'POST',
    headers: {
      'Content-Type': 'application/json',
      'x-api-key': key,               // 这把 key 决定落到哪个 GHCP 账号
      'anthropic-version': '2023-06-01',
    },
    body: JSON.stringify({
      model: MODEL,
      max_tokens: MAX_TOKENS,
      system: [systemBlock],
      messages: [{ role: 'user', content: '收到请回复"OK"，不要解释。' }],
    }),
  });

  const body = await res.json();
  const u = body.usage ?? {};
  return {
    input: u.input_tokens ?? 0,
    write: u.cache_creation_input_tokens ?? 0,   // 写入缓存的 token（付 1.25×）
    read:  u.cache_read_input_tokens ?? 0,       // 从缓存读的 token（付 0.1×）
  };
}
```

### 4.3 主流程

```js
// 先证明后续几次发的前缀逐字节相同 —— 否则 miss 可能只是内容不同
const digestA = createHash('sha256').update(buildPrefix('A')).digest('hex').slice(0, 16);
console.log(`前缀 A 的 sha256 = ${digestA}`);

const s1 = await ask(KEY_A, 'A');          // demo01 冷启动
await sleep(2000);
const s2 = await ask(KEY_A, 'A');          // demo01 重复 —— 基线
await sleep(2000);
const s3 = await ask(KEY_B, 'A');          // demo02 同一前缀 —— 待测
await sleep(2000);
const s4 = await ask(KEY_B, 'A');          // demo02 重复

const c1 = await ask(KEY_B, 'C');                    // 不同前缀
const c2 = await ask(KEY_A, 'A', { cache: false });  // 不打标记
const c3 = await ask(KEY_A, 'D', { short: true });   // 过短

const SAME_ACCOUNT_HITS  = s2.read > 0;
const CROSS_ACCOUNT_HITS = s3.read > 0;

if (!SAME_ACCOUNT_HITS) {
  console.log('⚠️ 同账号基线都没命中 —— 链路上缓存没生效，S3 无法解读');
} else if (CROSS_ACCOUNT_HITS) {
  console.log('结论：缓存在 GHCP 账号之间【共享】');
} else {
  console.log('结论：缓存按 GHCP 账号【隔离】');
}
```

### 4.4 运行

```bash
export KEY_A="<绑 demo01 的虚拟 key>"
export KEY_B="<绑 demo02 的虚拟 key>"
export MODEL="claude-sonnet-5"

```

## 五、实验过程：三次失败与定位

这部分比结论本身更有参考价值。

### 第 1 轮：跨账号不命中

```
E1  demo01 冷启动    write=1071  read=0
E2  demo02 同一前缀  write=1071  read=0    ← 不命中
```

看上去像"缓存按账号隔离"。但当时**没有同账号基线**，无法排除"缓存根本没生效"。

### 第 2 轮：补上基线，发现基线也不命中

```
S1  demo01 冷启动    write=1071  read=0
S2  demo01 重复      write=1071  read=0    ← 连自己都不命中
```

同一个账号、逐字节相同的前缀、间隔 2 秒，仍然重新写入。说明**问题不在账号维度**。

### 第 3 轮：逐层隔离

| 测试 | 结果 |
|---|---|
| 直连 `api.anthropic.com`，`claude-opus-5` | ❌ 不命中 |
| 直连 `api.anthropic.com`，`claude-sonnet-5` | ✅ **命中** |
| 加长前缀到 4869 token（opus-5） | ❌ 仍不命中 |
| 关闭 thinking / 调 effort（opus-5） | ❌ 仍不命中 |

→ 说明**方法本身是对的**（sonnet-5 直连能命中），opus-5 在这个账号上的缓存行为另有原因，先换用 sonnet-5 继续。

继续隔离 GHCP 链路：

| 路径 | 结果 |
|---|---|
| 容器内 → Proxy:3000（绕过 LiteLLM） | ✅ **命中，且跨账号命中** |
| 容器内 → LiteLLM:4000 | ✅ 命中 |
| 外网 → Caddy → LiteLLM | ❌ 不命中 |
| 外网 → SSH 隧道 → LiteLLM（绕过 Caddy） | ❌ 不命中 |

Proxy 直连那一次已经给出了答案：

```
第1次[demo01]: write=1741  read=0      ← 冷启动
第2次[demo01]: write=0     read=1741   ← 同账号命中
第3次[demo02]: write=0     read=1741   ← 跨账号命中 ✅
```

**缓存确实跨账号共享。** 剩下的问题是：为什么从外部走完整链路就测不出来。

## 六、定位到的生产问题：LiteLLM 响应缓存

连发 4 次相同请求，检查响应的 `id`：

```
LiteLLM #1  id=msg_011CeqiDBpZrzxzW5K4UXzfU  回复="47"  w=1223 r=0
LiteLLM #2  id=msg_011CeqiDBpZrzxzW5K4UXzfU  回复="47"  w=1223 r=0
LiteLLM #3  id=msg_011CeqiDBpZrzxzW5K4UXzfU  回复="47"  w=1223 r=0
LiteLLM #4  id=msg_011CeqiDBpZrzxzW5K4UXzfU  回复="47"  w=1223 r=0
```

**message id 完全相同** —— LiteLLM 在从 Redis 重放旧响应，请求根本没到上游。看到的 `usage` 是第一次那组陈旧数字。

根因是配置里打开了 LiteLLM 自己的响应缓存：

```yaml
litellm_settings:
  cache: true                    # ← 问题在这
  cache_params:
    type: redis
```

### 影响

跨租户测试（两把不同的虚拟 key 发相同请求）：

```
租户A #1  id=msg_011CeqiFJcey5rNNhNrFhnNA   ← A 的请求
租户B #1  id=msg_011CeqiFJcey5rNNhNrFhnNA   ← B 拿到了 A 的响应
租户B #2  id=msg_011CeqiFJcey5rNNhNrFhnNA
```

三个问题：

1. **跨租户共享响应** —— 租户 B 发出与 A 相同的请求，会拿到 A 那次的结果，请求不到上游
2. **计费失真** —— 重放的 `usage` 是第一次的数字，per-key 消费统计不准
3. **掩盖真实缓存** —— 看到的 `cache_read` / `cache_write` 全是陈旧值，无法判断 Anthropic 侧是否真的命中

> 需要说明的是，这**不是内容泄漏**：缓存键由请求内容决定，租户 B 必须发出逐字节相同的请求才会命中，读不到 A 的私有数据。但它破坏了按租户计费和用量观测。

> ⚠️ 这段配置是从生产 AKS 环境抄过来的，**生产环境同样存在**，需要一并处理。

### 修复

```yaml
litellm_settings:
  # 不要打开 LiteLLM 自己的响应缓存。
  # 我们要的是 Anthropic 的 prompt 缓存（由客户端 cache_control 驱动、
  # 在上游生效），不是网关层的响应缓存。两者是不同的东西。
  cache: false
```

修复后复验：

```
租户A #1  id=msg_011CeqiSoFQ8xhttv8FXbath   w=1224  r=0
租户B #1  id=msg_011CeqiT3txWRxCG5XAK9PWW   w=0     r=1224
租户B #2  id=msg_011CeqiTKRbuWDMbxhPgGepF   w=0     r=1224
```

id 各不相同（真实推理），且 B 命中了 Anthropic 侧的 prompt 缓存。

## 七、最终结果

修复后跑完整链路，7 项全过：

```
── 第一组：同账号基线（关键对照）────────────────────────
  ✅ S1  冷启动，建立缓存      [demo01]  input=18  write=1073  read=   0
  ✅ S2  ★同账号重复请求      [demo01]  input=18  write=   0  read=1073

── 第二组：跨账号（本实验要回答的问题）──────────────────
  ✅ S3  ★跨账号，同一前缀     [demo02]  input=18  write=   0  read=1073
  ✅ S4  demo02 自己重复一次   [demo02]  input=18  write=   0  read=1073

── 第三组：对照实验 ────────────────────────────────────
  ✅ C1  不同前缀不应命中      [demo02]  input=18  write=1073  read=   0
  ✅ C2  不打标记则不缓存      [demo01]  input=1091 write=  0  read=   0
  ✅ C3  过短则不建缓存        [demo01]  input=53  write=   0  read=   0

  同账号重复请求命中缓存 : 是  (S2 read=1073)
  跨账号同一前缀命中缓存 : 是  (S3 read=1073, write=0)

  结论：缓存在 GHCP 账号之间【共享】
```

关键读法：**S3 的 `write=0, read=1073`** —— demo02 没有重新写入，而是直接读到了 demo01 建的那份缓存。

C1 用不同前缀得到 `write=1073, read=0`，证明系统不是"总是命中"，S2/S3 的命中是真实的。

## 八、对方案的影响

### 8.1 默认策略保持 `least-loaded`

缓存跨账号共享，所以按负载均匀分摊**不损失缓存收益**。原设计成立。

三种策略的选择依据回到各自本来的理由，与缓存无关：

| 策略 | 何时用 |
|---|---|
| `least-loaded`（默认） | 多人共用一个池，负载最均匀 |
| `sticky-affinity` | 需要按会话审计追溯；或客户端用了有状态接口 |
| `round-robin` | 需要同一会话结果稳定，但不看负载 |

### 8.2 缓存要生效，客户端得配合

不是自动的，三个条件缺一不可：

| 条件 | 说明 |
|---|---|
| 显式标记 | 请求里要带 `cache_control: {"type":"ephemeral"}` |
| 够长 | 见 §3.3 的门槛表，模型相关 |
| 前缀逐字节相同 | 是前缀精确匹配，不是语义相似 |

Claude Code 自带这些标记，客户直接用不需要做什么。自研应用要自己加。

### 8.3 断点位置

渲染顺序是 `tools` → `system` → `messages`。把稳定内容放前面、断点打在稳定部分末尾：

```json
"system": [{"type": "text", "text": "<大段共享前缀>",
            "cache_control": {"type": "ephemeral"}}],
"messages": [{"role": "user", "content": "<每次都不同的问题>"}]
```

**不要**把断点打在整个请求末尾——那样每次都写一份新缓存，永远读不回来，纯付 1.25× 的写入费。

常见的静默失效原因：system prompt 里插了时间戳、请求 ID、用户名；JSON 序列化不确定（key 顺序变）；工具列表按用户动态生成。

### 8.4 经济性

| | 相对基础输入价 |
|---|---|
| 缓存写入（5 分钟 TTL） | 1.25× |
| 缓存读取 | 0.1× |

5 分钟 TTL 下**两次请求即回本**（1.25 + 0.1 = 1.35 vs 不缓存 2.0）。每次命中会刷新计时，所以连续流量能一直保持热。

## 九、遗留问题

**`claude-opus-5` 在测试用的 Anthropic key 上缓存不命中**，而 `claude-sonnet-5` 用完全相同的载荷正常命中。已排除：前缀长度（试到 4869 token）、thinking 配置、effort 等级。原因未定位，需要进一步确认是账号/workspace 相关还是模型相关。

**这一条影响面较大** —— 当前方案默认用 `claude-opus-5`。建议：

1. 在客户环境上用 `tests/cache-cross-account.mjs` 跑一次 `MODEL=claude-opus-5`，确认该环境下的实际行为
2. 若同样不命中，短期可对缓存敏感的场景改用 `claude-sonnet-5`
