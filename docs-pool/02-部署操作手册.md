# GHCP 账号池网关 —— 部署操作手册

> 本手册面向**照着做的人**。每一步都给出：做什么 → 可直接复制的命令 → 期望输出 → 失败了怎么办。
> 全程约 **60–90 分钟**（其中镜像构建 15–25 分钟），主要卡点在 Azure 订阅策略和 Copilot token 准备。

## 0. 读前必看

### 0.1 你将搭出什么

```
客户端（Claude Code / 自研应用）
  ↓ LiteLLM 虚拟 key（sk-xxx，一租户一把）
Caddy            自动 TLS + 按域名分流
  ├─ api.<PUBLIC_HOST>     → LiteLLM:4000
  └─ console.<PUBLIC_HOST> → Console:7004
LiteLLM:4000     虚拟 key、身份注入、per-key 限流与计费
  + PostgreSQL / Redis
  ↓ 强制注入 X-User-Identity = 虚拟 key 的 metadata.trusted_user_id
GHCP Proxy:3000  【账号池在这一层】identity → 池 → 选成员 → 该成员的 Copilot OAuth token
  ├─ SSO:7001    自建 SAML IdP + SCIM 客户端
  └─ Login:7003  GitHub Device Flow + 无头 Playwright
  ↓
api.githubcopilot.com
```

### 0.2 端口模型

只有 Caddy 对外，其余都是内部服务：

| 端口 | 服务 | 宿主机绑定 | 谁访问 |
|---|---|---|---|
| 80 / 443 | Caddy | `0.0.0.0` | 对外，唯一入口 |
| 4000 | LiteLLM | `127.0.0.1` | Caddy（走 Docker 网络）、本机管理脚本 |
| 3000 | Proxy | `127.0.0.1` | LiteLLM（走 Docker 网络）、本机管理脚本 |
| 7001 / 7003 / 7004 | SSO / Login / Console | `127.0.0.1` | 内部调用、本机管理脚本；Console 经 Caddy 对外 |

绑定地址由 `.env` 的 `BIND_ADDR` 统一控制，**默认 `127.0.0.1`**，通常不需要修改。
容器之间走 Docker 内部网络按服务名互访，不经过宿主机端口映射。

因此 NSG 只需放行 **22 / 80 / 443**。即使规则被订阅策略清空重置（见 §6），
内部服务也不会随之暴露——网络层规则是第二道防线，不是唯一一道。

## 第 1 步：环境准备（az login、选订阅、确认权限）

### 1.1 登录

```bash
az login --use-device-code
```

**期望输出**：终端给出 `https://microsoft.com/devicelogin` 和一段 code；浏览器完成后，终端打印订阅 JSON 数组。

**失败处理**

| 现象 | 处理 |
|---|---|
| 浏览器一直转圈 / 打不开 devicelogin | VPN 的 Fake-IP 正常，等；仍不行换网络 |
| `AADSTS50076` 需要 MFA | 加 `--tenant <租户ID>` 重试 |
| `az: command not found` | 装 Azure CLI，Windows 用 MSI 安装包 |

### 1.2 选订阅

```bash
az account list --query "[].{名称:name, 订阅ID:id, 状态:state}" -o table
az account set --subscription "<订阅ID>"
az account show --query "{订阅:name, 订阅ID:id, 租户:tenantId}" -o table
```

**期望输出**：最后一条打印出的订阅名 = 工程师要用的那个。**核对无误再往下走**，后面所有资源都建在这里。

### 1.3 确认权限

```bash
ME=$(az ad signed-in-user show --query id -o tsv)
az role assignment list --assignee "$ME" --include-inherited \
  --query "[].{角色:roleDefinitionName, 范围:scope}" -o table
```

**期望输出**：至少有一行 `Contributor` 或 `Owner`，范围是 `/subscriptions/<订阅ID>`（或后面要用的资源组）。

**失败处理**

| 现象 | 处理 |
|---|---|
| 输出为空 | 权限可能通过组继承，`--include-inherited` 已加；仍为空就直接做 1.4 + 第 2 步，用实际建资源来验证 |
| `az ad signed-in-user` 403 | 租户禁止读目录。跳过本步 |

### 1.4 注册资源提供程序（新订阅常漏）

```bash
for ns in Microsoft.Compute Microsoft.Network Microsoft.Storage; do
  az provider register --namespace "$ns"
done
sleep 30
for ns in Microsoft.Compute Microsoft.Network Microsoft.Storage; do
  echo "$ns = $(az provider show -n "$ns" --query registrationState -o tsv)"
done
```

**期望输出**：三行都是 `Registered`。

**失败处理**：显示 `Registering` 就再等 1–2 分钟重查。显示 `NotRegistered` 且报权限错 → 权限不足，找订阅 Owner。

## 第 2 步：建资源组与 VM（建的时候就打标签）

> **为什么强调标签**：这套环境实测被订阅策略周期性破坏过三种方式。`CostControl=Ignore` + `SecurityControl=Ignore` 能挡住其中两种，**挡不住第三种**。详见附录 B。

### 2.1 定义变量（本节后续都用它们）

```bash
RG=<资源组>
LOC=<区域>
VM=<虚拟机名>
TAGS="CostControl=Ignore SecurityControl=Ignore"
```

> 这些是**当前 shell 的变量**，关掉终端就没了。后面每一节开头如果发现 `$RG` 是空的，回来重设一遍。

### 2.2 生成 SSH 密钥

```bash
ssh-keygen -t ed25519 -f ~/.ssh/ghcp_pool_key -N "" -C "ghcp-pool"
ls -l ~/.ssh/ghcp_pool_key ~/.ssh/ghcp_pool_key.pub
```

**期望输出**：两个文件都存在，私钥权限 `-rw-------`。

> 已经有同名文件时 `ssh-keygen` 会问是否覆盖——**不要覆盖**已经在用的密钥，换个文件名（后续命令里的路径同步改）。

### 2.3 建资源组（**带标签建，别事后补**）

```bash
az group create -n "$RG" -l "$LOC" --tags $TAGS
az group show -n "$RG" --query "{名称:name, 区域:location, 标签:tags}" -o json
```

**期望输出**：`标签` 里同时有 `CostControl: Ignore` 和 `SecurityControl: Ignore`。

### 2.4 建 VM（带 cloud-init 自动装 Docker）

`cloud-init.yaml` 做四件事：装 Docker CE + compose 插件、把 `azureuser` 加进 `docker` 组、建 `/opt/ghcp-pool` 并 chown 给 azureuser、最后 `touch /opt/ghcp-pool/.cloud-init-done` 作为完成标记。

```bash
az vm create \
  --resource-group "$RG" \
  --name "$VM" \
  --image Ubuntu2404 \
  --size Standard_D2s_v5 \
  --admin-username azureuser \
  --ssh-key-values ~/.ssh/ghcp_pool_key.pub \
  --custom-data <本地仓库目录>/cloud-init.yaml \
  --public-ip-sku Standard \
  --os-disk-size-gb 64 \
  --nsg-rule SSH \
  --tags $TAGS
```

> `--custom-data` 的路径按 0.4 的检查结果填：文件在根目录就是 `<本地仓库目录>/cloud-init.yaml`，已经整理到 `deploy/` 就是 `<本地仓库目录>/deploy/cloud-init.yaml`。
> **admin-username 必须是 `azureuser`**——cloud-init 里 `usermod -aG docker azureuser` 和 `chown azureuser` 都写死了这个名字，改了会导致 docker 权限和目录属主不对。

**期望输出**：约 1–2 分钟后返回 JSON，含 `"publicIpAddress": "x.x.x.x"`、`"powerState": "VM running"`。**记下这个 IP**。

**失败处理**

| 现象 | 处理 |
|---|---|
| `The value of parameter imageReference is invalid` | 换完整 URN：`--image Canonical:ubuntu-24_04-lts:server:latest` |
| `SkuNotAvailable` 提示 `Standard_D2s_v5` | 换区域，或换 `Standard_D2as_v5` / `Standard_D2s_v4`（2 vCPU / 8 GB 即可） |
| `QuotaExceeded` | 订阅 vCPU 配额不足，提 quota 工单或换区域 |
| `--custom-data` 报文件找不到 | 用绝对路径；Git Bash 下 `/c/Users/...` 和 `C:/Users/...` 都行 |

### 2.5 记录公网 IP 与 PUBLIC_HOST

```bash
IP=$(az vm show -d -g "$RG" -n "$VM" --query publicIps -o tsv)
echo "公网IP     = $IP"
echo "PUBLIC_HOST= ${IP}.nip.io"
echo "API 入口   = https://api.${IP}.nip.io"
echo "Console    = https://console.${IP}.nip.io"
```

**期望输出**：四行都有值，IP 不为空。

> 用自有域名的话，把 `<PUBLIC_HOST>` 换成你的域名，并在 DNS 里把 `api.<域名>` 和 `console.<域名>` 两条 A 记录都指向 `$IP`。**两条都要**，Caddy 会分别申请证书。

### 2.6 给资源组下所有资源补标签

`az vm create` 顺带创建的 VNet / NIC / NSG / PublicIP / Disk **不会继承 VM 的标签**，必须补。

```bash
az resource list -g "$RG" --query "[].id" -o tsv | while read -r id; do
  az tag update --ids "$id" --operation merge --tags CostControl=Ignore SecurityControl=Ignore \
    >/dev/null 2>&1 && echo "OK   $id" || echo "FAIL $id"
done
```

**期望输出**：每个资源一行 `OK`。

**失败处理**：
出现 `FAIL` 或 `TooManyRequests` 是 **ARM 限流**——实测**报错但标签可能已经打上了**。
不要看返回码，**复查真实状态**：

```bash
az resource list -g "$RG" --query "[].{名称:name, 类型:type, 标签:tags}" -o json
```

对仍缺标签的资源，隔 30 秒单个重跑 `az tag update --ids <资源ID> --operation merge --tags CostControl=Ignore SecurityControl=Ignore`。

### 2.7 验证 cloud-init 跑完

```bash
ssh -i ~/.ssh/ghcp_pool_key -o StrictHostKeyChecking=no azureuser@"$IP" \
  'cloud-init status --wait; ls -l /opt/ghcp-pool/.cloud-init-done; docker --version; docker compose version; id'
```

**期望输出**（关键四行）：

```
status: done
-rw-r--r-- 1 root root 0 ... /opt/ghcp-pool/.cloud-init-done
Docker version 2x.x.x, build ...
Docker Compose version v2.x.x
uid=1000(azureuser) gid=1000(azureuser) groups=...,docker
```

> Docker / Compose 的具体版本号取决于安装当天 Docker 官方源里的版本，**不用和上面一致**，能打印出来就行。
> `cloud-init status --wait` 会**阻塞**到初始化结束，首次通常要 2–4 分钟，不要以为是卡死了。

**失败处理**

| 现象 | 处理 |
|---|---|
| SSH 连不上（超时） | NSG 22 端口没开或被策略清了 → 先做第 3 步再回来 |
| `status: running` | 还在装，等 2–3 分钟重跑 |
| `status: error` | `ssh -i ~/.ssh/ghcp_pool_key azureuser@"$IP" 'sudo tail -50 /var/log/cloud-init-output.log'` 看报错，通常是 apt / download.docker.com 不通 |
| `groups` 里没有 `docker` | `ssh ... 'sudo usermod -aG docker azureuser'` 后**断开重连**（组变更只在新会话生效） |
| `/opt/ghcp-pool/.cloud-init-done` 不存在但 status 是 done | cloud-init 中途失败过。看上面的日志，必要时手动补：`sudo mkdir -p /opt/ghcp-pool && sudo chown azureuser:azureuser /opt/ghcp-pool` |

## 第 3 步：开放 NSG 端口（**两层都要配**）

### 3.1 为什么是两层

Azure 的入站流量要**连续通过两个独立的 NSG**：

```
Internet → [子网 NSG] → [网卡 NSG] → VM
```

两层是 AND 关系，**任何一层拒绝就到不了**。实测被订阅策略破坏的第三种方式就是：
**策略新建一个零规则的子网 NSG 挂到 VNet 上**——网卡 NSG 完好无损，但流量全被子网这层吃掉。
而且新建的 NSG 天生没有标签，`SecurityControl=Ignore` **挡不住这种**。

所以：**主动建自己的子网 NSG 并挂上去**。这样策略再来时，你一眼就能看出「挂的不是我建的那个」。

### 3.2 找出网卡、网卡 NSG、VNet、子网

```bash
NIC=$(az vm show -g "$RG" -n "$VM" --query "networkProfile.networkInterfaces[0].id" -o tsv | xargs -n1 basename)
NIC_NSG=$(az network nic show -g "$RG" -n "$NIC" --query "networkSecurityGroup.id" -o tsv | xargs -n1 basename)
SUBNET_ID=$(az network nic show -g "$RG" -n "$NIC" --query "ipConfigurations[0].subnet.id" -o tsv)
VNET=$(echo "$SUBNET_ID" | awk -F/ '{print $9}')
SUBNET=$(echo "$SUBNET_ID" | awk -F/ '{print $11}')
printf "网卡      = %s\n网卡NSG   = %s\nVNet      = %s\n子网      = %s\n" "$NIC" "$NIC_NSG" "$VNET" "$SUBNET"
```

**期望输出**：四行都有值。名字随 az 版本变化（常见形如 `<虚拟机名>VMNic` / `<虚拟机名>NSG` / `<虚拟机名>VNET` / `<虚拟机名>Subnet`），**以实际输出为准，不要照抄**。

**失败处理**：任何一行为空 → `$RG` / `$VM` 没设或拼错，回 2.1。

### 3.3 配网卡 NSG

```bash
az network nsg rule create -g "$RG" --nsg-name "$NIC_NSG" -n allow-web-inbound \
  --priority 1000 --direction Inbound --access Allow --protocol Tcp \
  --source-address-prefixes Internet --source-port-ranges '*' \
  --destination-address-prefixes '*' --destination-port-ranges 80 443 \
  --description "Caddy HTTP/HTTPS"
```

**期望输出**：返回 JSON，`"provisioningState": "Succeeded"`、`"access": "Allow"`。

> **`--destination-address-prefixes` 为什么写 `*`**：普通 VM 的实例级公网 IP 会 DNAT 成私网 IP 后才到网卡，写 `*` 最稳。
> **注意**：这条经验**不适用于 AKS**。AKS 的 LoadBalancer 开了 `enableFloatingIP`（DSR），包到达节点时目标 IP 仍是**公网 IP**，那时 destination 必须写公网 IP，写子网网段不生效。本手册是单 VM 部署，用 `*`。

**失败处理**：报优先级冲突（`priority 1000 already used`）→ 换 1100。

### 3.4 建并挂上子网 NSG（**最容易漏的一层**）

```bash
SUBNET_NSG="${VM}-subnet-nsg"

az network nsg create -g "$RG" -n "$SUBNET_NSG" -l "$LOC" --tags $TAGS

az network nsg rule create -g "$RG" --nsg-name "$SUBNET_NSG" -n allow-web-inbound \
  --priority 1000 --direction Inbound --access Allow --protocol Tcp \
  --source-address-prefixes Internet --source-port-ranges '*' \
  --destination-address-prefixes '*' --destination-port-ranges 80 443

az network nsg rule create -g "$RG" --nsg-name "$SUBNET_NSG" -n allow-ssh-inbound \
  --priority 1010 --direction Inbound --access Allow --protocol Tcp \
  --source-address-prefixes Internet --source-port-ranges '*' \
  --destination-address-prefixes '*' --destination-port-ranges 22

az network vnet subnet update -g "$RG" --vnet-name "$VNET" -n "$SUBNET" \
  --network-security-group "$SUBNET_NSG"
```

**期望输出**：最后一条返回的 JSON 里 `networkSecurityGroup.id` 以 `/<虚拟机名>-subnet-nsg` 结尾。

> **子网 NSG 必须自己带 22**：网卡 NSG 上的 SSH 规则是 `az vm create --nsg-rule SSH` 建的，只在网卡那层；子网这层不放行 22，你会**在挂上 NSG 的瞬间把自己的 SSH 掐断**。上面两条规则的顺序已经保证先建规则再挂载，不要调换。
> **不要放行 3000 / 4000 / 7001 / 7003 / 7004。** 一旦放行 3000，任何人拿到 `API_KEY` 就能伪造任意身份，多租户隔离直接归零。
> SSH 想收紧的话，把 `--source-address-prefixes Internet` 换成你的出口 IP（`curl -s https://api.ipify.org`）。但 VPN 出口 IP 会变，现场自行权衡。

### 3.5 验证「两层合并后的最终结果」

这是唯一可信的检查，比分别看两个 NSG 靠谱：

```bash
az network nic list-effective-nsg -g "$RG" -n "$NIC" \
  --query "value[].effectiveSecurityRules[?direction=='Inbound' && access=='Allow'].{规则:name, 端口:destinationPortRange, 端口组:destinationPortRanges, 源:sourceAddressPrefix}" \
  -o table
```

**期望输出**：能看到 22、80、443 的 Allow 规则（可能来自两个 NSG，重复出现是正常的）。
`allow-web-inbound` 写的是**两个端口**，会出现在 `端口组` 列而不是 `端口` 列——两列都要看。

**失败处理**

| 现象 | 处理 |
|---|---|
| 命令报 `NicInUnprovisionedState` | VM 刚建好还没就绪，等 1 分钟重试 |
| 看不到 80/443 | 回 3.3 / 3.4 重新执行；注意 priority 别和已有规则撞（撞了换 1100/1110） |
| 规则都在，但外面还是连不上 | 走附录 B 的固定排查顺序 |

### 4.3 登进 VM，生成 .env


**以下全部在 VM 上执行。**

```bash

# ── 基础栈 ──
LOG_LEVEL=info
API_KEY=$(openssl rand -base64 32 | tr -d '=\n' | tr '+/' '-_')
INTERNAL_API_TOKEN=$(openssl rand -base64 32 | tr -d '=\n' | tr '+/' '-_')
SESSION_SECRET=$(openssl rand -base64 32 | tr -d '=\n' | tr '+/' '-_')

IDENTITY_HEADER_REQUIRED=true
CLAUDE_CODE_OPTIMIZED=true

CONSOLE_PORT=7004
SSO_CERT_DIR=./certs
ENTERPRISE_SHORTCODE=octo

# ── SSO / Login 的必填占位项 ──
# 本部署用「导入已有 OAuth token」接入账号，不走 SAML/SCIM 自动开通，
# 这些值仅用于让容器正常启动，不代表可用的企业配置。
```

**期望输出**：文件打印出来，`API_KEY` / `INTERNAL_API_TOKEN` / `SESSION_SECRET` 各是 **43 字符**的随机串，`LITELLM_DB_PASSWORD` 是 **32 字符**，`LITELLM_MASTER_KEY` 形如 `sk-` + 48 位十六进制，`PUBLIC_HOST` 是你的域名，**没有任何 `change-me`、没有空值**。

> 这里用的是 `<<EOF`（不加引号），命令替换才会执行。如果你复制成了 `<<'EOF'`，文件里会留下字面的 `$(openssl ...)`，容器起来会拿到一堆垃圾密钥。**生成后必须 `cat .env` 用眼睛确认**。

### 4.4 变量含义速查

| 变量 | 含义 | 怎么来 | 能不能改 |
|---|---|---|---|
| `API_KEY` | Proxy 的入站 API key。**只有 LiteLLM 用它**，绝不给租户 | `openssl rand -base64 32` | 改了要重启 proxy + litellm |
| `INTERNAL_API_TOKEN` | Proxy `/api`、`/internal` 和 SSO `/api` 的管理令牌 | 同上 | 改了全栈重启 |
| `SESSION_SECRET` | Console / SSO 的 cookie 签名密钥 | 同上 | 改了所有人重新登录 |
| `LITELLM_MASTER_KEY` | LiteLLM 管理密钥，用于建虚拟 key。**绝不给租户** | `sk-$(openssl rand -hex 24)`，**必须以 `sk-` 开头** | 改了要重启 litellm |
| `LITELLM_DB_PASSWORD` | PostgreSQL 密码 | `openssl rand -base64 24` | **建库后不要改**，改了连不上已有数据卷 |
| `PUBLIC_HOST` | 对外域名基名 | `<公网IP>.nip.io` 或自有域名 | 改了 Caddy 重新申请证书 |
| `IDENTITY_HEADER_REQUIRED` | 缺身份头就 400 | 固定 `true` | **不要改成 false** |
| `STORAGE_DRIVER` | 存储驱动 | `sqlite`（单机足够） | 多副本才需要 `mysql` |
| `REQUEST_STATS_PER_ACCOUNT_LIMIT` | **每个账号**保留多少条请求统计 | `200` | compose 里的默认值只有 **2**，保持默认的话第 12 步只能看到每账号最近 2 条，几乎没法验收。**必须显式设大** |
| `ENTERPRISE_SHORTCODE` | 企业短码 | `octo`（compose 默认值，占位用） | 导入模式下不影响 |
| `SP_ENTITY_ID` / `SP_ACS_URL` / `ENTERPRISE_SLUG` / `SCIM_BASE_URL` / `SCIM_TOKEN` / `SSO_PUBLIC_BASE_URL` | SAML / SCIM 配置 | **导入模式下是占位值**。compose 对这些用了 `${VAR:?}`，**为空容器直接启动失败** | 走自动开通链路时才需要填真值 |

> **没有 openssl 时**（本地生成再粘贴）：
> ```bash
> node -e "console.log(require('crypto').randomBytes(32).toString('base64url'))"
> node -e "console.log('sk-'+require('crypto').randomBytes(24).toString('hex'))"
> ```
> Ubuntu 24.04 自带 `openssl`，优先用 openssl。

`.env` 里的 `BIND_ADDR` 统一控制 3000 / 4000 / 7001 / 7003 / 7004 在宿主机上的绑定地址，

## 第 5 步：生成 SSO 自签证书（不生成会 CrashLoop）

SSO 容器启动时必须能读到 `/certs/idp-cert.pem` 和 `/certs/idp-key.pem`（compose 把 `${SSO_CERT_DIR:-./certs}` 只读挂到 `/certs`），**缺了会反复重启**。
导入 token 模式下不需要真跑 SAML 流程，自签证书就够。

```bash
cd /opt/ghcp-pool
CERT_DIR=/opt/ghcp-pool/certs bash scripts/gen-certs.sh
ls -l certs/
```

**期望输出**：

```
Wrote:
  /opt/ghcp-pool/certs/idp-key.pem
  /opt/ghcp-pool/certs/idp-cert.pem
```
外加 `ls` 列出两个文件，`idp-key.pem` 权限是 `-rw-------`（脚本最后会 `chmod 600`）。文件大小随密钥内容小幅浮动，不必对齐字节数。

**失败处理**

| 现象 | 处理 |
|---|---|
| `scripts/gen-certs.sh: bad interpreter: ...^M` | CRLF 没修干净，回 4.2 |
| `openssl: not found` | `sudo apt-get update && sudo apt-get install -y openssl` |
| `certs/` 里已有文件 | 脚本会直接覆盖，重跑无副作用 |
| 后面 SSO 容器报 `EACCES` 读不到 idp-key.pem | 四个业务镜像的 Dockerfile 都没有 `USER` 指令，容器以 root 运行，正常不会遇到。真遇到就先 `docker compose exec sso id` 确认容器内 uid，再决定是否 `chmod 640` |

## 第 6 步：构建镜像与启动全栈

### 6.1 定位 compose 文件并组合命令

三个 compose 文件叠加。为了后面少打字，先存成变量：

```bash
cd /opt/ghcp-pool
# 按你的仓库实际布局二选一
CADDY_YML=$( [ -f deploy/docker-compose.caddy.yml ] && echo deploy/docker-compose.caddy.yml || echo docker-compose.caddy.yml )
DC="docker compose -f docker-compose.yml -f docker-compose.litellm.yml -f $CADDY_YML"
echo "$DC"
```

**期望输出**：一行完整命令，第三个 `-f` 指向的文件确实存在（`ls -l $CADDY_YML` 复核）。

> **三条硬约束，破一条就出各种怪问题：**
> 1. **必须在 `/opt/ghcp-pool` 目录下执行**。docker compose 用**第一个 `-f` 文件所在目录**作为项目目录，`.env` 也是从那里读的。
> 2. **叠加顺序不能变**：`docker-compose.yml`（基础栈）→ `docker-compose.litellm.yml`（LiteLLM+PG+Redis）→ Caddy。后者的 `depends_on` 引用前者定义的 `proxy` / `litellm` / `console` 服务。
> 3. **`$DC` 是 shell 变量，SSH 断开就没了**。重连后先跑：
>    ```bash
>    cd /opt/ghcp-pool
>    CADDY_YML=$( [ -f deploy/docker-compose.caddy.yml ] && echo deploy/docker-compose.caddy.yml || echo docker-compose.caddy.yml )
>    DC="docker compose -f docker-compose.yml -f docker-compose.litellm.yml -f $CADDY_YML"
>    set -a; . ./.env; set +a
>    ```
>    这段是「**重连后的开机三件事**」，后面每一步都默认你已经跑过。

### 6.2 先校验配置解析（尤其是 Caddyfile 挂载路径）

```bash
$DC config > /tmp/compose-resolved.yml && echo "配置解析 OK"
grep -n "Caddyfile" /tmp/compose-resolved.yml
```

**期望输出**：`配置解析 OK`，且 Caddyfile 那行的**源路径真实存在**。

**关键坑**：Caddy 的 compose 文件里写的是相对路径 `./Caddyfile.pool`，而 compose 解析相对路径时**以项目目录（第一个 `-f` 文件所在目录）为根**，不是各文件自己的目录。
所以当 Caddy 的 compose 文件在 `deploy/` 下时，`./Caddyfile.pool` 会被解析成 `/opt/ghcp-pool/Caddyfile.pool`，而文件其实在 `/opt/ghcp-pool/deploy/Caddyfile.pool`。
**docker 遇到不存在的挂载源会自动建一个空目录**，然后 Caddy 会因为「配置文件是个目录」而起不来——错误信息很难往这上面想。

**验证并修**：

```bash
ls -ld /opt/ghcp-pool/Caddyfile.pool /opt/ghcp-pool/deploy/Caddyfile.pool 2>&1
```

只有 `deploy/` 下有真文件时，二选一：

```bash
# 方案 A（推荐）：改 compose 里的路径
sed -i 's|\./Caddyfile\.pool|./deploy/Caddyfile.pool|' "$CADDY_YML"
# 方案 B：在项目根做个软链
ln -sfn deploy/Caddyfile.pool /opt/ghcp-pool/Caddyfile.pool
```

如果之前已经被 docker 建出了空目录 `/opt/ghcp-pool/Caddyfile.pool/`，先 `rmdir` 掉再做上面任一方案。改完重跑 6.2 确认。

**顺手改一件事**：`Caddyfile.pool` 顶部的 `email admin@example.com` 是占位邮箱（实测用这个值也签发成功了）。想收到证书到期通知就换成真实邮箱：

```bash
sed -i 's|admin@example.com|<你的邮箱>|' "$(dirname "$CADDY_YML")/Caddyfile.pool"
```

### 6.3 构建

```bash
$DC build 2>&1 | tail -30
```

**期望输出**：最后能看到 `ghcp-sso:local` / `ghcp-login:local` / `ghcp-proxy:local` / `ghcp-console:local` / `ghcp-litellm:local` 各自 `naming to ...` 或 `writing image sha256:...`，没有 `ERROR`。

**首次构建 15–25 分钟**：四个业务镜像各自跑一遍 `npm ci`，其中 `login` 还要 `npx playwright install --with-deps chromium`，最大最慢。

**失败处理**

| 现象 | 处理 |
|---|---|
| 拉基础镜像超时 / TLS handshake timeout | 网络问题，重跑 `$DC build`；Docker 有层缓存，不会从头来 |
| `npm ERR! network` | 同上，重跑 |
| `npm ci` 报 lock 文件缺失/不同步 | `package-lock.json` 没传上去或版本不匹配，回 4.1 |
| 磁盘满 `no space left on device` | `df -h /`；OS 盘建议 ≥64 GB（2.4 已指定）。清理：`docker system prune -af` |
| `open ... docker-compose.caddy.yml: no such file` | 回 6.1 检查 `$CADDY_YML` |

### 6.4 启动

```bash
$DC up -d
```

**期望输出**：每个服务一行 `Created` / `Started`，包括 `sso` `login` `proxy` `console` `litellm-db` `litellm-redis` `litellm` `caddy`。

由于 `depends_on: service_healthy` 链（proxy 等 sso+login，litellm 等 db+redis+proxy），启动是串行的，**整体约 2–3 分钟**。

**失败处理**

| 现象 | 处理 |
|---|---|
| `error while interpolating ... required variable XXX is missing` | `.env` 里少了一项，回 4.3 |
| `dependency failed to start: container ... is unhealthy` | 被依赖的服务没起来，直接进第 7 步逐个看 |

## 第 9 步：导入 Copilot 账号

### 9.1 三个前置条件（缺一必失败）

1. **SSO 用户必须先存在**——导入时 Proxy 会先向 SSO 查 `GET /api/users/<name>`，404 就整行失败（查询**不区分大小写**）
2. **建 SSO 用户时用户名会被规范化**——`sanitizeSsoUser` 会：去空格 → **转小写** → 砍掉 `@` 及其后面 → 非法字符替换成 `-` → 截断到 32 字符。所以**直接用小写、纯字母数字**最省事
3. **CSV 必须是两列，表头字段去空格后精确等于 `name` 和 `copilotOauthToken`**——顺序不能换、不能加列、不能改拼写

> **account 的 identity = CSV 里 `name` 的原样写法**（不会被转小写），而 SSO 查找不区分大小写。也就是说 CSV 写 `Demo01` 也能导入成功，但账号 identity 就是 `Demo01`，后面加池成员必须写 `Demo01`。**统一用小写能省掉一整类问题。**

### 9.2 加载环境变量

```bash
cd /opt/ghcp-pool
set -a; . ./.env; set +a
echo "INTERNAL_API_TOKEN 长度 = ${#INTERNAL_API_TOKEN}"
echo "API_KEY 长度            = ${#API_KEY}"
```

**期望输出**：两个长度都是 **43**（按 4.3 生成的话）。出现 0 说明 `.env` 没加载或该项为空。

### 9.3 先建 SSO 用户

```bash
for u in demo01 demo02; do
  echo "--- $u ---"
  curl -sS -X POST http://127.0.0.1:7001/api/users \
    -H "X-Internal-Token: ${INTERNAL_API_TOKEN}" \
    -H 'Content-Type: application/json' \
    -d "{\"ssoUser\":\"${u}\"}" | python3 -m json.tool
done
```

**期望输出**：每个用户返回一个 JSON，含 `"ssoUser": "demo01"`（HTTP 201）。

**失败处理**

| 现象 | 处理 |
|---|---|
| `{"error":{"code":"internal_auth_failed"}}` 401 | `INTERNAL_API_TOKEN` 没加载或和容器里的不一致。重跑 9.2；`.env` 改过就要 `$DC up -d` 让容器吃到新值 |
| `SSO user "demo01" already exists.` | 已存在，跳过即可 |
| `Connection refused` | SSO 容器没起来，回第 7 步 |
| 报用户数上限 | `sso_user_limit_reached`，现场确认容量限制配置 |

**期望输出**：列出 `demo01`、`demo02`。

### 9.5 准备 CSV 并生成请求体

```bash

chmod 600 /opt/ghcp-pool/accounts.csv /opt/ghcp-pool/import-payload.json
```

**期望输出**：打印出 `{"csvText": "name,copilotOauthToken\ndemo01,gho_...` 的开头。

| 要素 | 值 |
|---|---|
| 方法与路径 | `POST /api/accounts/copilot-oauth-token/import` |
| 认证头 1 | `X-Internal-Token: <INTERNAL_API_TOKEN>` |
| 认证头 2 | `x-api-key: <API_KEY>` |
| 请求体 | `{"csvText": "name,copilotOauthToken\n<name>,<gho_token>\n..."}` |

> 源码里 `/api/*` 路由**只校验 `X-Internal-Token`**（`app.use('/api', requireInternalToken, ...)`）。实测过程中两个头是一起带的，为与实测保持一致这里也一起带——**多带 `x-api-key` 无副作用**，少带也能通。

**期望输出**：

```json

    "finishedAt": "...",
```

**关键**：`summary.failed` 必须是 `0`。导入会**实时向 Copilot 验证 token**，success 就代表 token 当时真的可用。

> `detail` 也可能是 `...imported with name as GH login fallback; sync SSO to GH to confirm ghLogin.`——这表示 SSO 用户还没有 `ghLogin`，用 CSV 里的 name 兜底了。**状态仍是 success，导入模式下不影响使用。**

| `rows[].detail` | 原因 | 处理 |
|---|---|---|
| `SSO user "xxx" was not found. Create it manually in SSO Users before importing this token.` | SSO 用户没建 | 回 9.3 |

| `Duplicate name "xxx" in import CSV.` | CSV 里重名（忽略大小写） | 去重 |
| 整个请求 401 `internal_auth_failed` | token 不对 | 回 9.2 |
| 整个请求 400 `invalid_import` | `csvText` 为空 | 检查 `import-payload.json` 是不是空的 |

## 第 10 步：创建账号池、加成员、选策略

### 10.1 选策略

| 策略 | 实际算法（源码） | 权重是否生效 | 什么时候用 |
|---|---|---|---|
| `least-loaded`（**默认**） | 在可用成员里挑 `lastUsedAt` 最早的（最久未使用） | **否** | **多租户共用一个池的默认选择** |
| `sticky-affinity` | 先查会话绑定，命中且可用就复用；否则 **Rendezvous(HRW) 哈希**选一个并写绑定 | **是** | 需要按会话审计追溯；或客户端用了 `/responses` 的 `previous_response_id` 这类有状态接口 |
| `round-robin` | 对 sessionKey 取 sha256，按成员名排序后取模 | **否** | 需要确定性哈希分配、又不想落会话绑定时 |

> **必须澄清的一点**：**Rendezvous 哈希与 `weight` 只在 `sticky-affinity` 下起作用**。第 13.1 步验证的四条性质（粘性、均匀、最小扰动、权重 8:1:1）验的就是这个放置函数。`least-loaded` 和 `round-robin` 走的是另外两个分支，`weight` 字段对它们**没有影响**。
> 另一个源码事实：`lastUsedAt` **只在请求成功后更新**。所以 `least-loaded` 下如果多个请求几乎同时打进来，可能短时间内连续选到同一个成员——这不是 bug，观察均分要看一段时间的累计。

> **一个反直觉但已实测确认的结论**：**prompt 缓存是跨 GHCP 账号共享的。**
> 实测 demo01 写入缓存 2000 token 后，demo02 发相同请求直接 `cache_read=1716` 命中。
> 原因是所有 GitHub Copilot 账号共用同一个 Anthropic 组织（从 thinking 块签名解出的组织 ID 为 `ced1f98e-0b51-4610-8282-4e5d88384574`）。
> **所以 `least-loaded` 按负载均匀分摊不会损失缓存**——不需要为了保缓存而牺牲负载均衡。
>
> 补充：缓存需要客户端显式声明 `cache_control: {"type":"ephemeral"}`，且内容要超过约 1024 token 才会缓存。Claude Code 自带该字段。
>
> 注意：`src/proxy/src/pool/` 里有些**注释仍写着「缓存按账号隔离」**，那是改造前的旧假设，已被上面的实测推翻。以实测结论为准。

### 10.2 建池

```bash
POOL=team-pool

curl -sS -X POST http://127.0.0.1:3000/api/pools \
  -H "X-Internal-Token: ${INTERNAL_API_TOKEN}" \
  -H 'Content-Type: application/json' \
  -d "{\"poolId\":\"${POOL}\",\"strategy\":\"least-loaded\",\"sessionTtlSeconds\":1800,\"cooldownSeconds\":300,\"failureThreshold\":3}" \
  | python3 -m json.tool
```

| 字段 | 含义 | 建议值 |
|---|---|---|
| `poolId` | 池名，也是对外暴露的 identity。正则 `^[A-Za-z0-9][A-Za-z0-9._:@-]{0,127}$` | `team-pool` |
| `strategy` | 选择策略，见 10.1。**省略则为 `least-loaded`** | `least-loaded` |
| `sessionTtlSeconds` | 会话绑定存活时间（秒），**仅 `sticky-affinity` 会读写绑定** | `1800`（30 分钟，够一次连续 Claude Code 会话） |
| `cooldownSeconds` | 成员冷却时长（秒） | `300`（与 Copilot 侧常见限流窗口相当） |
| `failureThreshold` | 连续失败几次进入冷却 | `3` |
| `enabled` | 池是否启用 | 省略即启用 |

> 这四个数值字段**必须是 JSON 数字**，写成字符串 `"1800"` 会被源码的 `readPositiveInt` 判为无效并**静默回落到默认值**（1800/300/3），不会报错。上面的命令已经是正确写法。

**期望输出**：HTTP 201，JSON 含 `"poolId": "team-pool"`、`"strategy": "least-loaded"`、`"members": []`、`"activeMembers": 0`、`"totalMembers": 0`、`"enabled": true`。

**失败处理**

| 现象 | 处理 |
|---|---|
| 409 `pool_id_conflicts_with_account` | 池名和已有账号 identity 撞了。换名，比如 `team-pool-01` |
| 400 `pool_id_invalid` | 池名含不支持字符（中文、空格、`/` 等）。只能用字母数字和 `.` `_` `:` `@` `-`，且首字符必须是字母或数字 |
| 400 `pool_strategy_invalid` | 策略拼错。只能是 `sticky-affinity` / `least-loaded` / `round-robin` |
| 400 `pool_id_required` | `poolId` 为空 |

### 10.3 加成员

**identity 必须与 9.7 输出的第一列完全一致（大小写敏感）。**

```bash
for id in demo01 demo02; do
  echo "--- $id ---"
  curl -sS -X POST "http://127.0.0.1:3000/api/pools/${POOL}/members" \
    -H "X-Internal-Token: ${INTERNAL_API_TOKEN}" \
    -H 'Content-Type: application/json' \
    -d "{\"identity\":\"${id}\",\"weight\":1}" | python3 -m json.tool
done
```

| 字段 | 含义 | 说明 |
|---|---|---|
| `identity` | 成员账号，必须是已导入的账号 | 大小写敏感 |
| `weight` | 相对权重 | 默认 1。**仅 `sticky-affinity` 生效**；实测 8:1:1 的权重得到 80.4% / 9.4% / 10.2% |
| `state` | `active` / `disabled` | 传 `disabled` 才是停用，其余值都按 `active` 处理 |

**期望输出**：每个成员 HTTP 201，含 `"identity"`、`"state": "active"`、`"weight": 1`、`"accountStatus": "valid"`、`"consecutiveFailures": 0`。

> `state` 是**池成员状态**（`active`），`accountStatus` 是**账号的 OAuth 状态**（`valid`）。两个都要对。

**失败处理**

| 现象 | 处理 |
|---|---|
| 404 `account_not_found` | identity 拼错或大小写不符。**回 9.7 复制粘贴** |
| 404 `pool_not_found` | 池名拼错，或 10.2 没成功 |
| 400 `member_cannot_be_pool` | 成员名和池名一样，改掉 |
| 400 `identity_required` | 请求体没带 identity |

### 10.6 故障转移行为（了解即可，无需配置）

| 上游返回 | 行为 |
|---|---|
| `429` / `402` | **立即冷却该成员**（`forceCooldown`），不必攒够失败次数 |
| 其他错误 | 累计到 `failureThreshold`（默认 3）才冷却 |
| 请求成功 | 失败计数清零、状态回 `active`、刷新 `lastUsedAt` |
| 冷却期满 | 下次选择时自动视为可用，**没有后台解冻任务** |
| 全员冷却 | 抛 `PoolAllCoolingError`，`retryAfterSeconds` = 最早解冻成员的剩余秒数 |

> **客户端看到的是什么**：`PoolAllCoolingError` 没有被单独映射状态码，会走默认分支返回 **HTTP 502**，body 里的 message 是 `All members of pool "team-pool" are cooling down.`。
> `retryAfterSeconds` 目前只存在于服务端的错误对象上，**源码里没有把它写进响应体或 `Retry-After` 头**——想让客户端拿到，需要改造，属于已知缺口。

手动解除某成员冷却（排障用）：

```bash
curl -sS -X POST "http://127.0.0.1:3000/api/pools/${POOL}/members/<identity>/resume" \
  -H "X-Internal-Token: ${INTERNAL_API_TOKEN}" | python3 -m json.tool
```

**期望输出**：返回整个池详情，该成员 `state` 变回 `active`、`consecutiveFailures` 归零。

## 第 11 步：创建 LiteLLM 虚拟 key（一租户一把）

### 11.1 为什么必须走虚拟 key

| 层 | 身份来源 | 能否伪造 |
|---|---|---|
| Proxy | 请求头 `X-User-Identity` | **能，随便改** |
| LiteLLM | 虚拟 key 的 `metadata.trusted_user_id` | **不能，客户端碰不到** |

`trusted_identity_hook` 做三件事：**先无条件删掉请求里所有的 `X-User-Identity`**（headers / extra_headers / proxy_server_request.headers / metadata.headers 全清）→ 校验必须是虚拟 key → 从 key 的 metadata 取 `trusted_user_id` 并注入。
配套的 `config.yaml` 里还有 `forward_client_headers_to_llm_api: false`，双保险。

实测行为：

| 场景 | 实测结果 |
|---|---|
| 无 key 调用 | **401** |
| 用 master key 直接推理 | **403** |
| 带伪造的 `X-User-Identity` 头 | **头被剥掉**，仍按 key 元数据走池分配，返回 **200** |

> 关于 master key 那条：hook 源码里这个分支抛的是 `HTTPException(401, "Inference requires a LiteLLM virtual key.")`，而实测观察到的是 403（LiteLLM 外层对 hook 异常有自己的处理）。
> **判据用「非 200」**——仓库里的 `tests/verify-litellm.mts` 断言的也是 `status !== 200`。看到 401 或 403 都算通过，看到 200 才是出事了。

### 11.2 建 key

```bash
cd /opt/ghcp-pool
set -a; . ./.env; set +a

curl -sS -X POST http://127.0.0.1:4000/key/generate \
  -H "Authorization: Bearer ${LITELLM_MASTER_KEY}" \
  -H 'Content-Type: application/json' \
  -d '{
    "key_alias": "tenant-a",
    "metadata": { "trusted_user_id": "team-pool" },
    "rpm_limit": 60,
    "tpm_limit": 200000,
    "max_parallel_requests": 5,
    "max_budget": 50,
    "budget_duration": "30d",
    "duration": "30d"
  }' | python3 -m json.tool
```

| 字段 | 含义 | 上限（`litellm/config.yaml` 的 `upperbound_key_generate_params`） |
|---|---|---|
| `key_alias` | 租户标识，用于对账。**全局唯一** | — |
| `metadata.trusted_user_id` | **注入给 Proxy 的身份**。填**池名**（多账号）或**账号 identity**（1:1） | 必须匹配 `^[A-Za-z0-9][A-Za-z0-9._:@-]{0,127}$`（hook 里校验） |
| `rpm_limit` | 每分钟请求数 | ≤ 600 |
| `tpm_limit` | 每分钟 token 数 | ≤ 1000000 |
| `max_parallel_requests` | 并发上限 | ≤ 20 |
| `max_budget` | 预算（USD） | ≤ 500 |
| `budget_duration` | 预算周期 | `30d` |
| `duration` | key 有效期 | ≤ `90d` |

**期望输出**：JSON 含 `"key": "sk-..."`（这就是交给租户的那把）、`"key_alias": "tenant-a"`、以及你设的各项限额。

**把这个 `sk-...` 记下来——LiteLLM 只在创建时返回一次明文。**

**失败处理**

| 现象 | 处理 |
|---|---|
| 401 `Invalid proxy server token` | `LITELLM_MASTER_KEY` 不对。`grep LITELLM_MASTER_KEY .env` 核对；`.env` 改过要 `$DC up -d` 让容器吃到新值 |
| 400 提到 `upperbound` | 某个参数超上限，按上表调小 |
| 400 提到 `key_alias` 已存在 | alias 重名，换一个（或加时间戳后缀） |
| 500 / 提到 db | PostgreSQL 没就绪。`$DC ps litellm-db`、`$DC logs litellm --tail 50` |

### 11.3 每个租户一把

```bash
for t in tenant-a tenant-b; do
  echo "=== $t ==="
  curl -sS -X POST http://127.0.0.1:4000/key/generate \
    -H "Authorization: Bearer ${LITELLM_MASTER_KEY}" \
    -H 'Content-Type: application/json' \
    -d "{\"key_alias\":\"${t}\",\"metadata\":{\"trusted_user_id\":\"team-pool\"},\"rpm_limit\":60,\"tpm_limit\":200000,\"max_parallel_requests\":5,\"max_budget\":50,\"budget_duration\":\"30d\",\"duration\":\"30d\"}" \
    | python3 -c "import sys,json; d=json.load(sys.stdin); print('  key   =', d.get('key')); print('  alias =', d.get('key_alias'))"
done
```

**期望输出**：两个租户各得一把 `sk-...`。若 11.2 已经建过 `tenant-a`，这里那一行会因重名失败，正常，改名或跳过。

> **多个租户可以共用同一个池**（`trusted_user_id` 都填 `team-pool`）——`least-loaded` 会把负载摊平，而缓存跨账号共享，所以不损失命中率。
> 需要**账号级隔离**时，就建多个池，每个池各自的成员，不同租户的 key 指向不同池。

### 11.4 列出所有 key 对账

```bash
curl -sS "http://127.0.0.1:4000/key/list?return_full_object=true&size=50" \
  -H "Authorization: Bearer ${LITELLM_MASTER_KEY}" \
  | python3 -c "
import sys,json
for k in json.load(sys.stdin).get('keys',[]):
    print('  %-16s spend=%-12s 预算=%-6s rpm=%-5s 身份=%s' % (
      k.get('key_alias'), k.get('spend') or 0, k.get('max_budget'),
      k.get('rpm_limit'), (k.get('metadata') or {}).get('trusted_user_id')))
"
```

**期望输出**：每把 key 一行，`身份` 列全部是 `team-pool`。

**失败处理**：`身份` 显示 `None` → 这把 key 建的时候漏了 `metadata.trusted_user_id`，用它推理会 403，删掉重建。

## 第 12 步：端到端冒烟测试

### 12.1 先确认可用模型名

不同 Copilot 账号可见的模型不同，**不要硬编码**。这条直接问 Proxy（在 VM 上，走 127.0.0.1）：

```bash
curl -sS http://127.0.0.1:3000/v1/models \
  -H "x-api-key: ${API_KEY}" \
  -H "X-User-Identity: team-pool" \
  | python3 -c "import sys,json; [print(' ', m.get('id')) for m in json.load(sys.stdin).get('data',[])]"
```

**期望输出**：一列模型名。本次实测用的是 `claude-opus-5`。**从这个列表里挑一个 `claude` 开头的**，后续命令里的 `claude-opus-5` 都替换成它。

> 为什么必须是 `claude` 开头：`litellm/config.yaml` 里 `claude-*` 才映射到 anthropic 形态的路由（`/v1/messages`），其余走 `*` → openai 形态。用非 claude 模型打 `/v1/messages` 行为需现场确认。

**失败处理**：返回 400 `missing_identity_header` → 忘了带 `X-User-Identity`。返回 401 → `API_KEY` 没加载（回 9.2）。

### 12.2 发一个真实请求（走完整公网链路）

在 **VM 上**（用 `--resolve` 避开公网回环）：

```bash
VKEY=<虚拟key>
PUBLIC_HOST=$(grep '^PUBLIC_HOST=' /opt/ghcp-pool/.env | cut -d= -f2)

curl -sS --resolve "api.${PUBLIC_HOST}:443:127.0.0.1" \
  -X POST "https://api.${PUBLIC_HOST}/v1/messages" \
  -H "x-api-key: ${VKEY}" \
  -H 'anthropic-version: 2023-06-01' \
  -H 'Content-Type: application/json' \
  -w '\nHTTP=%{http_code}\n' \
  -d '{"model":"claude-opus-5","max_tokens":32,"thinking":{"type":"disabled"},"messages":[{"role":"user","content":"回复OK"}]}'
```

**期望输出**：`HTTP=200`，响应体是 Anthropic Messages 格式，`content[0].text` 里有内容，`usage` 有 token 数。

**失败处理**

| HTTP | 含义 | 处理 |
|---|---|---|
| 401 | 无 key 或 key 无效 | 检查 `x-api-key` 是不是**虚拟 key**（第 11 步那把 `sk-`，不是 master key、也不是 Proxy 的 `API_KEY`） |
| 403 `Virtual key is missing trusted identity metadata.` | key 建的时候漏了 `metadata.trusted_user_id` | 重建 key，回 11.2 |
| 403 `Virtual key trusted identity metadata is invalid.` | `trusted_user_id` 不匹配身份正则 | 只用字母数字和 `.` `_` `:` `@` `-`，首字符为字母或数字 |
| 400 `missing_identity_header` | 请求绕过了 LiteLLM 直接打到了 Proxy | 确认 URL 是 `api.<PUBLIC_HOST>`，不是 `:3000` |
| 404 `Unsupported Copilot API path` | 路径不支持，见 14.3 的支持列表 | 改路径 |
| 502 `All members of pool ... are cooling down.` | 池全员冷却 | 看 10.4 池状态；`$DC logs proxy --tail 80`；必要时 10.6 手动 resume |
| 503 `oauth_not_ready` | 选中成员的 `copilotOauthStatus` 不是 `valid` | 回 9.7 看账号状态，token 可能已失效 |
| 502（其他） | 上游异常 | `$DC logs proxy --tail 80`；Console 的错误诊断页也有完整记录 |

### 12.3 确认落到了池成员（**这一步是关键验收**）

```bash
curl -sS "http://127.0.0.1:3000/api/request-stats?limit=10" \
  -H "X-Internal-Token: ${INTERNAL_API_TOKEN}" \
  | python3 -c "
import sys,json
for s in json.load(sys.stdin):
    print('  %-10s pool=%-12s %-16s %s' % (
      s.get('identity'), s.get('poolId') or '-', s.get('path'), s.get('success')))
"
```

**期望输出**（至少一行）：

```
  demo01     pool=team-pool    /v1/messages     True
```

**判据**（统计归因规则）：

| 字段 | 应该是什么 | 说明 |
|---|---|---|
| `identity` | **实际成员账号**（`demo01` / `demo02`） | 不是 `team-pool` |
| `poolId` | **对外池名**（`team-pool`） | 1:1 模式下这里没有该字段 |

如果 `identity` 显示成 `team-pool` 而没有 `poolId`，说明**池没生效**，请求被当成普通 1:1 账号处理了 → 回 10.4 检查 `enabled` 是否为 `True`、成员是否 `active`。

> 两个接口差异要知道：`GET /api/request-stats` 返回的是**一个数组**，且**只认 `limit` 参数**（默认 100）——传 `?identity=xxx` 会被忽略。要按账号过滤请用 `GET /api/accounts/<identity>/request-stats?limit=N`。
> 另外，每个账号最多保留 `REQUEST_STATS_PER_ACCOUNT_LIMIT` 条（我们在 4.3 设成了 200；**compose 默认只有 2**）。

### 12.4 多发几次，确认在成员之间分摊

**期望输出**：6 次全 200，归因统计里 `demo01` 和 `demo02` **都出现**（`least-loaded` 下大致均分，但不保证严格 3:3——见 10.1 关于 `lastUsedAt` 的说明）。

> ① 确认 `strategy` 不是 `sticky-affinity`——那样同一段上下文本来就会固定同一账号，属于预期行为；
> ② 确认另一个成员没在冷却（10.4 的 `可用` 是不是掉成了 1/2）。

### 12.5 安全边界验证（三条，一条都不能少）

**关键提示**

| 事项 | 说明 |
|---|---|
| **不要配 `X-User-Identity` 自定义头** | 配了也会被 `trusted_identity_hook` 剥掉，纯属噪音。身份完全由虚拟 key 决定 |

### 14.4 会话粘性控制（仅 `sticky-affinity` 池需要）

会话 key 的推导优先级（从强到弱，见 `src/proxy/src/pool/sessionKey.ts`）：

| 优先级 | 来源 | 说明 |
|---|---|---|
| 1 | `X-Session-Id` 请求头 | 客户端主动控制 |
| 2 | 请求体 `metadata.user_id` | Claude Code 会传 |
| 3 | `system` + 首条 user message（含 `instructions` / `input`）**前 4096 字节**的 sha256 | 兜底，无需客户端配合 |
| 4 | 固定兜底值 | `/v1/models` 这类取不到 prompt 的请求 |

显式指定会话：

```bash
curl -sS -X POST "https://api.<PUBLIC_HOST>/v1/messages" \
  -H "x-api-key: <虚拟key>" \
  -H 'anthropic-version: 2023-06-01' \
  -H 'X-Session-Id: proj-alpha-20260908' \
  -H 'Content-Type: application/json' \
  -d '{"model":"claude-opus-5","max_tokens":64,"messages":[{"role":"user","content":"继续上次的话题"}]}'
```

> `least-loaded` 和 `round-robin` 策略下，**会话绑定既不写也不读**（源码里只有 `sticky-affinity` 分支会 upsert / 查询 affinity）——这是设计如此，目的就是每次重新分配摊平负载。
> 需要会话固定同一账号时，把池策略改成 `sticky-affinity`（在 VM 上执行）：
> ```bash
> curl -sS -X PATCH "http://127.0.0.1:3000/api/pools/team-pool" \
>   -H "X-Internal-Token: ${INTERNAL_API_TOKEN}" -H 'Content-Type: application/json' \
>   -d '{"strategy":"sticky-affinity"}' | python3 -m json.tool
> ```
> **期望输出**：返回池详情，`"strategy": "sticky-affinity"`。改完立即生效，无需重启。

## 附录 B：Azure 订阅策略破坏环境 —— 固定排查顺序

这套环境**实测被订阅策略周期性破坏过三种方式**：

| # | 破坏方式 | 标签能否挡住 |
|---|---|---|
| a | 清空资源组下**全部 NSG 的自定义规则** | 有帮助 |
| b | 停止 AKS 集群与 MySQL/PostgreSQL 实例 | 有帮助 |
| c | **新建一个子网 NSG 挂到 VNet 上，里面零规则** | **挡不住**——新建的资源天生没标签 |

**（c）是最阴的一种**：你的网卡 NSG 完好无损，规则一条不少，但流量在子网那层就被吃掉了。
（b 里提到的 AKS / 托管数据库是上一代部署形态；本手册是单 VM + 容器内 PostgreSQL，对应的表现是 **VM 被停机**、**容器被停**。）

### 环境突然不通时，按这个顺序查，一步都不要跳

```bash
RG=<资源组>; VM=<虚拟机名>
NIC=$(az vm show -g "$RG" -n "$VM" --query "networkProfile.networkInterfaces[0].id" -o tsv | xargs -n1 basename)
SUBNET_ID=$(az network nic show -g "$RG" -n "$NIC" --query "ipConfigurations[0].subnet.id" -o tsv)
VNET=$(echo "$SUBNET_ID" | awk -F/ '{print $9}'); SUBNET=$(echo "$SUBNET_ID" | awk -F/ '{print $11}')

echo "=== ① 网卡 NSG 的规则 ==="
NIC_NSG=$(az network nic show -g "$RG" -n "$NIC" --query "networkSecurityGroup.id" -o tsv | xargs -n1 basename)
az network nsg rule list -g "$RG" --nsg-name "$NIC_NSG" \
  --query "[].{规则:name, 端口:destinationPortRange, 端口组:destinationPortRanges, 动作:access}" -o table

echo "=== ② 子网 NSG（最容易漏的一层）==="
SUB_NSG=$(az network vnet subnet show -g "$RG" --vnet-name "$VNET" -n "$SUBNET" --query "networkSecurityGroup.id" -o tsv | xargs -n1 basename)
echo "当前挂的子网 NSG = ${SUB_NSG:-（没挂）}"
[ -n "$SUB_NSG" ] && az network nsg rule list -g "$RG" --nsg-name "$SUB_NSG" \
  --query "[].{规则:name, 端口:destinationPortRange, 端口组:destinationPortRanges, 动作:access}" -o table

echo "=== ③ VM 电源状态 ==="
az vm get-instance-view -g "$RG" -n "$VM" \
  --query "instanceView.statuses[?starts_with(code,'PowerState')].displayStatus" -o tsv

echo "=== ④ 容器状态（本部署的 PG/Redis 都在容器里）==="
ssh -i ~/.ssh/ghcp_pool_key azureuser@"$(az vm show -d -g "$RG" -n "$VM" --query publicIps -o tsv)" \
  'docker ps --format "{{.Names}}\t{{.Status}}"'
```

### 判读与处置

| 步骤 | 异常表现 | 处置 |
|---|---|---|
| ① 网卡 NSG | 只剩默认规则，自定义规则没了 | 破坏方式 (a)。重跑 **3.3** |
| ② 子网 NSG | **名字不是你在 3.4 建的那个**（`<虚拟机名>-subnet-nsg`），或规则列表为空 | 破坏方式 (c)。**这是最容易漏的一层**。重跑 **3.4**，把你自己的 NSG 重新挂回去 |
| ③ VM 电源 | 不是 `VM running` | 破坏方式 (b)。`az vm start -g "$RG" -n "$VM"`，起来后 SSH 进去 `cd /opt/ghcp-pool && $DC up -d` |
| ④ 容器 | 少了容器，或有 Exited / Restarting | 先 `$DC up -d`（sso/login/console 没有自动重启策略，见 7.4），仍不行回第 7 步逐个排查 |

### 加固建议

- 资源组和**所有**资源打 `CostControl=Ignore` + `SecurityControl=Ignore`（2.3 / 2.6）
- 但要清醒：**这挡不住策略新建资源**。定期（或每次连不上时）跑一遍上面的 ①②③④
- 把 3.4 的 NSG 名字（`<虚拟机名>-subnet-nsg`）记在交接文档里，一眼就能看出被换了
